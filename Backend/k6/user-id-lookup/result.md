# 인증 요청의 회원 ID 변환 기준선 (user-id-lookup, GR-201)

> 공통 실행 환경·전제는 `../README.md` 참고. 운영 캐파시티 수치가 아니라 하한선 검증이다. 공식 성능 목표(NFR-006)가 없어 합격·불합격은 판정하지 않는다.

인증이 필요한 API는 모두 `CurrentUserIdProvider.currentUserId()`로 JWT의 public_id를 내부 ID(`users.id`)로 바꾼다(9개 컨트롤러 23곳).
변환은 `UserIdLookupService`의 `findIdByPublicId` 쿼리 1회지만, `open-in-view: false`와 클래스 단위 `@Transactional(readOnly = true)` 때문에
서비스 본 트랜잭션과 **별도 트랜잭션으로 커넥션을 한 번 더 빌린다**. public_id → id 대응은 바뀌지 않아 로컬 캐시 후보다.
`TECHSTACK.md`는 조회 캐시를 부하 테스트로 병목이 확인된 뒤 도입하도록 정하고 있어, 캐시를 넣기 전 기준선을 잰다.
애플리케이션 코드와 Flyway는 바꾸지 않았다.

## 요약

### 알고 싶었던 것

로그인한 사용자의 요청마다 붙는 ID 변환 조회가 실제로 부담이 되는가.

### 측정 조건에서 기억할 것: DB 지연속도가 3ms

ID 변환의 비용은 "DB를 몇 번 더 다녀오느냐"다. 로컬은 DB가 바로 옆이라 한 번 다녀오는 데 0.1ms라 비용이 거의 0으로 보인다.
운영은 DB(Supabase)가 한 번에 약 3.2ms가 걸린다. 그래서 DB 응답을 일부러 3ms 늦춰 운영의 거리를 흉내 냈다(netem).
나머지 설정(backend micro, DB nano)은 운영 서버 사양을 흉내 낸 것이다.

### 결과

1. **요청마다 DB를 4번 다녀오는데, 그중 2번이 ID 변환 때문이다.** `users/me`·`orders` 모두 같다. 요청 하나가 트랜잭션 2개(ID 변환, 본 조회)를 쓴다.
2. **DB 커넥션은 10개뿐이고, 요청 하나가 커넥션을 약 13ms 붙잡는데 그 절반이 ID 변환이다.** 창구가 10개인 은행에서 손님마다 본 업무 전에 "신분증 번호 조회"를 따로 하느라 창구를 두 배로 오래 쓰는 셈이다.
3. **그래서 동시에 많이 몰리면(초당 약 750건 이상) 커넥션이 모자라 줄이 생긴다.** VU 800에서 커넥션을 얻으려고 평균 29ms를 기다렸고, 응답시간 중앙값이 14ms(VU 400)에서 69ms로 늘었다. 사용자가 적을 때도 요청마다 약 6ms(응답시간의 약 3분의 1)가 ID 변환에 쓰인다.

CPU·메모리는 여유가 있었다(backend CPU 최대 115%/200%, postgres 27%/100%, 스왑 0). 병목은 커넥션 대기다.

### 어디까지 믿으면 되나

| 결과 | 믿는 정도 |
| --- | --- |
| 요청당 DB 4번(트랜잭션 2개), 그중 2번이 ID 변환 | **그대로 믿어도 된다.** 코드 구조라 환경과 관계없다(로그·`pg_stat_statements`로 확인) |
| 커넥션 사용 시간의 절반이 ID 변환 | **믿어도 된다.** 위 구조에서 나온다 |
| "초당 약 750건에서 줄이 생긴다", "69ms" 같은 숫자 | **참고만 한다.** 로컬에서 흉내 낸 값이라 운영 숫자는 다를 수 있다 |

### 결론

ID 변환이 커넥션 사용 시간의 절반을 차지하고, 사용자가 몰리면 그것이 병목이 된다. 개선하면 요청 하나가 커넥션을 쓰는 시간이 약 절반으로 줄어든다.
개선할 가치가 있다고 판단한다. 근거와 개선 방향은 [판단](#판단) 절에 적는다.

## 측정 절차

```
docker compose -f compose.yaml -f compose.loadtest-micro.yaml -f compose.loadtest-db-nano.yaml up -d --build
docker compose exec -T postgres psql -U grab -d grab -f - < k6/common/accounts-seed.sql
docker compose exec -T postgres psql -v ON_ERROR_STOP=1 -U grab -d grab -f - < k6/user-id-lookup/seed.sql
k6/user-id-lookup/statements.sh baseline 300    # 요청당 문장 수(pg_stat_statements) + 트랜잭션 경계(log_statement)
k6/user-id-lookup/roundtrips.sh baseline 50     # 요청당 왕복 수(netem 0·10ms 중앙값 차이)
# 조건마다: netem 적용 → check.sh → 워밍업 → 동시 접속
k6/drop-detail-scale/netem.sh 3
k6/db-nano/check.sh 500
(cd k6 && k6 run --quiet -e STEPS=25 -e STEP_S=60 user-id-lookup/concurrency.js > /dev/null 2>&1)
MSYS_NO_PATHCONV=1 STEPS=25,50,100,200,400,800 SCRIPT=user-id-lookup/concurrency.js OUT_BASE=k6/user-id-lookup/out \
  k6/drop-list-scale/concurrency.sh baseline-3ms me
k6/drop-detail-scale/netem.sh off
```

- `statements.sh`: 대상(`me`·`orders`)마다 통계를 비우고 300회(간격 0.1초) 보낸 뒤, 걸린 시간만큼 요청 없이 한 번 더 재서 스케줄러 배경 호출을 쿼리별로 뺀다. 차감값은 음수까지 그대로 합산한다. pgjdbc의 `COMMIT`은 `pg_stat_statements`에 집계되지 않아 트랜잭션 수만큼 더한다(로그로 확인).
- `roundtrips.sh`: 사용자 1명으로 지연 없음·10ms에서 각 50회(예열 5회). (10ms 중앙값 − 지연 없음 중앙값) ÷ 10ms = 요청당 왕복 수.
- 동시 접속: `concurrency.js`(GET `/api/v1/users/me`, 요청 후 1초 대기, VU ≈ 동시 접속자)를 `drop-list-scale/concurrency.sh`로 단계당 60초 실행. HikariCP·힙·GC는 Prometheus(15초 수집)에서 단계 구간별로 읽는다.
- Windows Git Bash: `concurrency.sh`는 `MSYS_NO_PATHCONV=1`이 필요하고, `statements.sh`·`roundtrips.sh`는 붙이면 안 된다(각 스크립트 상단 주석).

## 결과

### 요청당 문장 수 (`statements.sh`, 300회)

| 대상 | 구간 | 집계 문장 | COMMIT 더함 | **문장/요청** | 트랜잭션/요청 | 배경 규모 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| `users/me` | 51.76초 | 4.05 | 2.03 | **6.08** | 2.03 | 0.27 |
| `orders` | 51.56초 | 4.00 | 2.00 | **6.00** | 2.00 | 0.27 |

| 쿼리 | `users/me` | `orders` |
| --- | ---: | ---: |
| `BEGIN READ ONLY` | 2.00 | 2.00 |
| ID 변환 `select u1_0.id from users u1_0 where u1_0.public_id=$1` | 1.00 | 1.00 |
| 본 조회 | 회원 `users ... where u1_0.id=$1` 1.00 | 주문 목록 `orders ...` 1.00 |
| `COMMIT`(더함) | 2.03 | 2.00 |

- `users/me`의 6.08 중 0.08은 스케줄러 차감 잔차다(`BEGIN` +0.02, `payment_cancellations` 조회 +0.01 등. 스케줄러 `BEGIN`이 트랜잭션 수에 섞여 COMMIT 더함도 2.03). 요청 구조는 6문장·트랜잭션 2개다.
- 배경 규모 0.27은 배경 구간 전체 호출 수 ÷ 300으로, 요청당 값에 섞일 수 있는 오차의 크기다.

### 트랜잭션 경계 (`log_statement`, `users/me` 3회 중 1회)

```

03:34:54.690 [5674] execute S_13: select u1_0.id from users u1_0 where u1_0.public_id=$1
03:34:54.691 [5674] execute S_1: COMMIT
03:34:54.692 [5674] statement: BEGIN READ ONLY
03:34:54.692 [5674] execute S_14: select u1_0.id,u1_0.created_at,u1_0.email, ... from users u1_0 where u1_0.id=$1

```

ID 변환(`public_id` 조회)과 회원 조회(`id` 조회)가 같은 커넥션에서 **각각 별도 트랜잭션**으로 실행된다. 3회 모두 같다.

### 요청당 왕복 수 (`roundtrips.sh`, 50회, 지연 10ms)

| 대상 | 지연 없음 중앙값 (p25~p75) | 10ms 중앙값 (p25~p75) | **왕복/요청** |
| --- | ---: | ---: | ---: |
| `users/me` | 6.15ms (5.76~6.53) | 46.82ms (46.54~47.27) | **4.07** |
| `orders` | 6.32ms (5.98~6.58) | 47.15ms (46.90~49.18) | **4.08** |

- 문장 6개인데 왕복이 4회인 이유: pgjdbc는 `BEGIN READ ONLY`를 첫 SELECT와 한 번에 보낸다(로그에서 같은 ms). 트랜잭션마다 (BEGIN+SELECT) 1회 + COMMIT 1회 = 2회, 트랜잭션 2개라 4회다. 4를 넘는 0.07~0.08은 왕복당 약 0.2ms의 netem·Docker 네트워크 오버헤드로 본다.
- 지연 없음 중앙값은 호스트 curl 기준이라 k6 측정(아래 VU 25 중앙값 3.4ms)보다 크다. 왕복 수는 두 조건의 차이라 이 차이의 영향이 없다.

### 커넥션 점유로 본 처리량 천장

GR-164·181과 같이 **처리량 천장 ≈ 커넥션 10개 ÷ 요청당 커넥션 점유 시간**으로 보면:

| 조건 | 왕복 시간(p50) | 요청당 점유 ≈ 트랜잭션 2 × 왕복 2 × 왕복 시간 | 천장 | VU 800 실측 |
| --- | ---: | ---: | ---: | --- |
| 3ms | 3.200ms | 약 12.8ms (+ 처리 시간) | 약 750~780건/초 | 742.8건/초, 풀 포화 |
| 2.5ms | 2.641ms | 약 10.6ms (+ 처리 시간) | 약 900~940건/초 | 788.5건/초, 천장 아래 |

3ms에서 VU 800(걸린 부하 약 800건/초)은 천장을 넘어 풀이 포화됐고, 2.5ms에서는 천장 아래라 꼬리 지연만 늘었다. 실측과 계산이 맞는다.
ID 변환 트랜잭션이 요청당 점유의 절반(왕복 4회 중 2회)이므로, 이론상 ID 변환을 DB 밖으로 빼면 같은 조건에서 천장이 약 2배가 된다. 실제 효과는 개선 후 재측정으로 확인한다.

| 800 | 788.5 / 12.3 · 22.9 · 364.7 | 788.6 / 12.2 · 25.1 · 412.9 | 2 · 435ms | 0 · 487ms |

- 처리량·중앙값·p95·p99·획득 최대는 재현됐다.
- **pending 최대는 재현되지 않았다**(1 → 151, 2 → 0). 15초마다 한 번 찍는 순간값이라 VU가 몰려 들어오는 순간에 걸리느냐에 따라 크게 달라진다. pending은 "대기가 생긴다"는 신호로만 쓰고, 대기 규모는 획득 평균·최대와 p99로 읽는다.
- 3ms VU 800의 풀 포화는 획득 평균(29.35ms)과 중앙값(69.1ms)으로 확인한 것이라 이 흔들림의 영향을 받지 않는다. 3ms는 재현 실행을 하지 않았다.

- 3ms·재현 구간의 메모리·힙이 앞 조건보다 큰 것은 측정이 이어지며 JVM이 힙을 늘린 것으로 본다. 한도 안이고 스왑 0이다.

### 판단 기준 값 (M00-05 ①·③)

① 요청당 왕복 중 ID 변환 몫 (문장 구조 + 왕복 수):

| 대상 | 요청당 왕복 | ID 변환 왕복 | 몫 |
| --- | ---: | ---: | ---: |
| `users/me` | 4.07 | 2 | 약 50% |
| `orders` | 4.08 | 2 | 약 50% |

ID 변환 트랜잭션은 본 조회 트랜잭션과 같은 모양(BEGIN+SELECT, COMMIT)이라 왕복 2회로 본다. ID 변환만 따로 잰 값이 아니다.

③ 운영 모사 응답시간 중앙값 중 ID 변환 몫 (ID 변환 몫 = 왕복 2회 × 운영 모사 왕복 시간):

| 대상 | 조건 | 응답시간 중앙값 | ID 변환 몫 | 비율 |
| --- | --- | ---: | ---: | ---: |
| `users/me` | 3ms, VU 25 실측 | 17.7ms | 2 × 3.200 = 6.40ms | **약 36%** |
| `orders` | 3ms, 추정 | 6.32 + 4.08 × 3.200 = 19.38ms | 6.40ms | **약 33%** |
| `users/me` | 2.5ms, VU 25 실측(참고) | 15.3ms | 2 × 2.641 = 5.28ms | 약 35% |
| `orders` | 2.5ms, 추정(참고) | 6.32 + 4.08 × 2.641 = 17.10ms | 5.28ms | 약 31% |

`orders`는 동시 접속을 하지 않아, 지연 없음 중앙값(curl, 50회) + 요청당 왕복 × 왕복 시간으로 추정했다. curl 중앙값이 k6보다 커서 비율이 작게 나오는 쪽의 추정이다.

## 측정 환경의 한계

- **하한선 검증이다.** 로컬 PC에서 backend는 t3.micro, DB는 Supabase Nano를 흉내 낸 조건이다. 처리량·응답시간을 운영 캐파시티로 쓰지 않는다. 운영 EC2·Supabase에는 부하를 걸지 않았다.
- **DB nano 모사의 한계**(`k6/db-nano/result.md`와 같음)
  - 공유 CPU를 `cpus: 1` 가정값으로 근사했다. 이웃 부하에 따른 변동과 버스트 크레딧 소진은 재현하지 않는다. 이번 측정에서 postgres CPU는 최대 27%라 이 가정이 결과를 바꾸지는 않았다.
  - netem은 고정 지연이다. 운영 네트워크의 지터·TLS 비용은 재현하지 않는다(운영 실측 3.2~3.4ms에는 포함). 지터가 있으면 커넥션 점유 시간이 들쑥날쑥해져 대기는 이번보다 빨리 생길 수 있다.
  - 디스크 IO와 Supavisor 풀러는 모사하지 않았다. 측정 데이터는 작아 대부분 `shared_buffers` 안에 있다.
- **netem 보정값은 PC마다 다르다.** 같은 netem 2.5ms가 GR-186(macOS)에서는 `SELECT 1` p50 3.181ms, 이 PC(Windows)에서는 2.641ms였다. 이번 판정은 이 PC에서 운영 범위에 든 3ms(p50 3.200ms)로 했다. 다른 PC에서 다시 잴 때는 netem 값을 고정하지 말고 `check.sh`로 p50이 운영 실측 범위에 드는 값을 고른다. GR-181·183(postgres 제한 없음 + netem 3ms), GR-180(macOS 2.5ms)과는 조건이 달라 수치를 직접 비교하지 않는다.
- **계정 1개.** 모든 VU가 `k6-buyer`의 토큰 하나를 쓴다. ID 변환 쿼리 비용·왕복 수·커넥션 점유는 요청한 회원과 관계가 없어 기준선에는 영향이 없다. 다만 캐시를 넣은 뒤 재측정에서는 계정 1개면 적중률이 거의 100%가 되어 효과가 부풀려지므로, 그때는 계정 수를 다시 정해야 한다.
- **HikariCP 지표는 15초 수집 순간값이다.** active·pending 최대는 수집 순간에 걸린 값이라 실제보다 작게 나오거나(지연 없음 active 0) 회차마다 크게 흔들린다(재현 pending 1 → 151). pending은 대기가 생겼다는 신호로만 쓰고, 대기 규모는 획득 평균·최대와 p99로 읽었다.
- **3ms 조건은 재현 실행을 하지 않았다.** 재현은 2.5ms로만 했고 처리량·지연·획득 최대가 1회차와 비슷했다. 3ms VU 800의 풀 포화는 계산한 천장(약 750~780건/초)과 실측(742.8건/초)이 맞는 것으로 뒷받침했다.
- **ID 변환 몫은 따로 잰 값이 아니다.** ① 왕복 몫 50%는 ID 변환 트랜잭션이 본 조회 트랜잭션과 같은 모양이라는 문장 구조(로그·`pg_stat_statements`)와 전체 왕복 수로 나눈 값이다. ③ `orders`는 동시 접속을 하지 않아 지연 없음 중앙값(curl) + 왕복 수 × 왕복 시간으로 추정했다.
- **문장 수의 배경 오차.** 스케줄러(10초 주기)가 배경 쿼리를 내서, 구간에 스케줄러가 몇 번 걸리느냐에 따라 요청당 값이 흔들린다. 300회에서 배경 규모는 0.27, `users/me` 잔차는 0.08이었다. 요청 구조(6문장·트랜잭션 2개)는 로그로 따로 확인했다.
- **측정 대상은 가벼운 조회 두 개다.** 주문 생성처럼 행 잠금이 있는 쓰기 경로는 재지 않았다. 그런 경로에서도 ID 변환 트랜잭션은 똑같이 붙지만, 요청 전체에서 차지하는 몫은 더 작다.
- **로컬 환경 차이.** Docker Desktop(Windows)의 지연 없음 `SELECT 1` p50은 0.121ms로 GR-186(macOS) 0.059ms와 다르다. 문장 수·왕복 수는 이 영향을 받지 않고(구조와 차이로 계산), 응답시간 절대값만 다를 수 있다.

## 판단

### 기준 적용 (측정 전에 정한 기준, GR-201 M00-05)

판정 조건은 운영 모사 netem 3ms다. ①·③은 일반 경로인 `orders` 기준 20%를 판단선으로 정했다.

| 기준 | 결과 (3ms) | 판단선 | 해당 |
| --- | --- | --- | --- |
| ① 요청당 왕복 중 ID 변환 몫 | `orders` 약 50% (`users/me`도 약 50%) | 20% | 해당 |
| ② 커넥션 경합 (HikariCP 대기·처리량 꺾임) | VU 100부터 대기, **VU 800에서 풀 포화**(획득 평균 29.35ms, 중앙값 69.1ms, 처리량 걸린 부하의 93%) | 측정 범위(VU 800) 안에서 발생 | 해당 |
| ③ 응답시간 중앙값 중 ID 변환 몫 | `orders` 약 33%(추정), `users/me` 약 36% | 20% | 해당 |

정해 둔 결론 세 갈래 중 **"②가 해당한다 → 부하가 몰릴 때 병목이 확인됐다. 캐시 후속 이슈 초안을 쓴다"**에 해당한다.
참고 조건 2.5ms에서는 ②가 약하지만(꼬리 지연만 증가) ①·③이 판단선을 넘어 "응답시간 개선" 갈래가 되므로, 어느 조건으로 봐도 개선할 이유는 있다.

TECHSTACK의 "조회 캐시는 부하 테스트로 병목이 확인된 경로에만 도입한다"에 대해, 이 경로(인증 요청의 ID 변환)는 병목이 확인된 것으로 기록한다.

### 개선 방향 후보 (구현하지 않음)

| 후보 | 방법 | 요청당 커넥션 점유 (3ms, 이론) | 처리량 천장 (이론) | 따져 볼 것 |
| --- | --- | ---: | ---: | --- |
| 지금 | ID 변환 트랜잭션(왕복 2) + 본 트랜잭션(왕복 2) | 약 12.8ms | 약 750~780건/초 | |
| **A. ID 변환 로컬 캐시** | `UserIdLookupService`에서 public_id → id를 앱 메모리에 둔다. 적중하면 DB에 가지 않는다 | 약 6.4ms | 약 2배 | 대응이 바뀌지 않아 무효화가 필요 없다(`UserIdResolver` 주석에 이미 후보로 적혀 있음). 회원 수만큼 늘지 않도록 크기 한도가 필요하다. GR-183은 `ConcurrentHashMap`으로 앱 메모리 캐시를 만들었지만 TTL 짧은 DROP 응답이라 크기 문제가 달랐다. Caffeine 같은 의존성을 쓰면 팀 합의·`TECHSTACK.md` 반영이 필요하다. 첫 요청(캐시 없음)은 지금과 같다 |
| B. ID 변환을 트랜잭션 없이 실행 | `UserIdLookupService`의 `@Transactional(readOnly = true)`를 빼서 자동 커밋 SELECT 한 번으로 끝낸다(BEGIN·COMMIT 없음) | 약 9.6ms | 약 1.3배 | 의존성·코드 변경이 가장 작다. 커넥션을 두 번 빌리는 것은 그대로다. Spring Data는 직접 선언한 쿼리 메서드에 트랜잭션을 붙이지 않으므로 SELECT만 나갈 것으로 보지만, 실제 문장·왕복은 측정으로 확인해야 한다 |

A가 효과가 가장 크고 B는 가장 가볍다. 둘은 함께 쓸 수도 있다(캐시가 비었을 때만 트랜잭션 없이 조회). 어느 쪽으로 할지는 후속 이슈에서 정한다.

### 개선 후 재측정에서 확인할 것

- **같은 조건**: micro + DB nano, 이 PC는 netem 3ms(측정 전 `check.sh`로 p50이 운영 범위인지 확인), 같은 단계·워밍업. 이 문서의 결과가 개선 전 기준선이다.
- **문장·왕복 수**(`statements.sh`·`roundtrips.sh`): A면 캐시 적중 시 요청당 3문장·트랜잭션 1개·왕복 약 2회, B면 4문장·왕복 약 3회가 되는지.
- **동시 접속**(`concurrency.js`): 3ms VU 800의 풀 포화(획득 평균 29ms, 중앙값 69ms)가 사라지는지, 낮은 부하 중앙값(17.7ms)이 약 6ms 줄어드는지.
- **계정 수**: A는 계정 1개면 적중률이 거의 100%라 효과가 부풀려진다. 실제와 비슷한 수의 계정으로 재고, 첫 요청(캐시 없음) 비율을 함께 적는다.
- **메모리**: A는 캐시 크기 한도와 힙 사용을 확인한다.
