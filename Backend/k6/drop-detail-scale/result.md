# 공개 DROP 상세·재고 조회 대용량 기준선 (drop-detail-scale, GR-181)

> 공통 실행 환경·전제는 `../README.md` 참고. 측정 조건·seed는 `../drop-list-scale/result.md`(GR-164)와 같다(nano 제한 아님).

SSE 알림을 받은 상세 화면은 상세(`GET /api/v1/drops/{id}`)와 재고(`GET /api/v1/drops/{id}/stocks`)를 둘 다 다시 부른다(`REALTIME_STOCK.md` 4절).
동시 사용자 1000명이 한 인기 상품을 보면 재조회 부하의 대부분이 이 두 API로 가는데, 지금까지 대용량 데이터에서 잰 적이 없었다(GR-153은 DROP 15건).
요청당 쿼리 수·실행 계획·응답시간·동시 접속 천장을 기록하고, 운영(EC2 → Supabase)처럼 DB가 네트워크 너머에 있을 때를 지연 주입으로 확인한다.
애플리케이션 코드와 Flyway는 바꾸지 않았다.

## 측정 환경

| --- | --- |
| 머신 | Apple M5(10코어), Docker Desktop VM 8GB / 10 CPU |
| 컨테이너 | `compose.yaml` + `drop-list-scale/compose.swapoff.yaml` — backend·postgres 메모리 2GiB = 스왑 0, **CPU 제한 없음(backend·DB 모두)** |
| 코드 | main `7ca3f5a` + GR-164·176(목록 쿼리만 변경). 상세·재고 경로는 main과 같다 |
| 자원 | 스왑 498샘플(지연 주입 포함) 모두 0. 최대 메모리 backend 863MiB·postgres 211MiB |
| 부하 경로 | k6 컨테이너 → compose 네트워크 `http://backend:8080` |

운영(무료 티어 가정: EC2 t3.micro 수준 + Supabase Nano)보다 backend·DB 모두 강한 조건이다. 조합 간·전후 비교와 왕복 지연의 영향을 보는 용도이며, 무료 티어 판정은 GR-180·186에서 별도로 한다.

## seed 보강

`drop-list-scale/seed.sql`에 옵션 그룹·값·SKU 매핑을 추가했다(GR-181). 이전에는 0건이라 상세 조회가 실제보다 가볍게 측정될 뻔했다.
SKU 1개는 그룹 없음, 2~3개는 색상 1그룹, 4개는 색상 2값 × 사이즈 2값이다(그룹 5,000 / 값 11,250 / 매핑 16,250).
목록 쿼리는 이 테이블을 읽지 않아 GR-164·176 수치에는 영향이 없다.

## 측정 절차

```
docker compose -f compose.yaml -f k6/drop-list-scale/compose.swapoff.yaml up -d
docker compose exec -T postgres psql -U grab -d grab -f - < k6/common/accounts-seed.sql
docker compose exec -T postgres psql -U grab -d grab -v ON_ERROR_STOP=1 -f - < k6/drop-list-scale/seed.sql
k6/drop-detail-scale/measure.sh baseline pair_hot pair_random stock_hot   # 지연 없음
k6/drop-detail-scale/latency.sh 1 pair_hot stock_hot                       # DB 왕복 +1ms
k6/drop-detail-scale/latency.sh 3 pair_hot stock_hot                       # DB 왕복 +3ms
```

- `targets.sh`: hot = 판매 중·재고 있음·SKU 4개(그룹 2개) 중 활성 WISH 최다, simple = SKU 1개, pool = seed 공개 DROP 4,500건.
- `combos.js`: `detail_*`, `stock_*`, `pair_*`(상세 + 재고 한 쌍 = SSE 재조회 한 번) × hot / simple / random.
- `explain.sh`: auto_explain으로 요청 구간의 쿼리를 모아 배치 쿼리를 걸러내고 요청당 쿼리 수·시간·버퍼를 구한다.
- `measure.sh` / `latency.sh`: 각 측정 전에 `warmup.js`(60초)를 돌린다. GR-176에서 쿼리가 같은 조합도 회차마다 p95가 11~42% 흔들린 원인으로 JVM 워밍업 차이가 추정돼, 측정마다 같은 상태에서 시작하게 했다.
- `netem.sh`: postgres 컨테이너 송신에 고정 지연을 걸어 DB 왕복 시간이 늘어난 상황을 흉내 낸다(postgres 컨테이너 자체는 바꾸지 않음). 측정이 끝나거나 실패하면 해제한다.
- 동시 접속은 `drop-list-scale/concurrency.sh`(SCRIPT·OUT_BASE로 일반화)로 VU 25→800, 단계당 60초, 요청 후 1초 대기.

## 해석

- **처리량 천장 = 커넥션 10개 ÷ 요청당 커넥션 점유 시간**(GR-164)이 여기서도 그대로 맞는다. 다만 상세·재고는 쿼리가 아니라 **DB 왕복 횟수**가 점유 시간을 정한다.
  한 쌍은 왕복 약 15번이라, 3ms 지연이면 점유 약 45ms → 10 ÷ 0.045 ≈ 초당 220쌍(HTTP 약 440건)이다. 실측 431건과 같다. 1ms면 점유 약 17~18ms → 초당 약 560~590쌍(HTTP 약 1,150건), 실측 1,161건과 같다.
- 로컬처럼 DB가 같은 머신이면 상세·재고는 병목이 아니다. **운영처럼 DB가 네트워크 너머면 왕복 시간 × 왕복 수가 곧 천장**이다.
  예를 들어 1000명이 SSE 알림마다 상세+재고를 1초 간격으로 다시 부르면 초당 1,000쌍이 필요한데, 왕복 1ms만으로 약 580쌍에서 막힌다.
- 대응 후보는 두 가지다.
  - **왕복 수 줄이기(GR-184):** 상세 쿼리 9개를 줄이면 같은 지연에서 천장이 비례해서 오른다. 캐시 정합성 문제가 없어 먼저 볼 후보다.
  - **응답 캐시(GR-183):** 인기 상품에 몰린 재조회를 DB까지 보내지 않는다. 왕복과 함께 Supabase egress(무료 티어 월 5GB)도 줄인다.
- 어느 쪽이 필요한지는 실제 EC2↔Supabase 왕복 시간(GR-186)과 성능 목표(GR-182)로 정한다.

## 개선 결과 — 상세·재고 DB 왕복 수 축소 (GR-184, 2026-10-27)

운영 EC2↔Supabase 왕복이 3.2~3.4ms로 실측돼(GR-186) 3ms 지연 조건을 운영 근사로 보고 전후를 비교했다. 같은 seed·`compose.swapoff.yaml`·워밍업, 코드는 main `eb09a78` 기준. 원자료 `out/gr184-before-3ms/`, `out/gr184-after-3ms/`, `out/gr184-after/explain/`.

**바꾼 것**

- 상세: DROP과 이미지를 한 쿼리로 읽는다(`findWithImagesById`, `@EntityGraph`). 옵션·옵션 그룹은 `List`라 함께 fetch join하면 `MultipleBagFetchException`이 나서 기존 `@BatchSize` 지연 로딩에 둔다.
- 상세: 브랜드·카테고리·활성 WISH 수를 판매자·카테고리·WISH 도메인 service 세 번 대신 네이티브 쿼리 한 번으로 읽는다(`findPublicDetailExtras`). 공개 목록 쿼리가 이미 같은 방식(다른 도메인의 엔티티·repository가 아니라 테이블을 네이티브로 읽음)이다. 값은 기존 조회와 같다.
- 재고: DROP과 옵션을 한 쿼리로 읽는다(기존 `findWithOptionsById`).
- 응답 형태·필드는 바꾸지 않았다.

**요청당 쿼리** (`explain.sh`, 5회 평균)

DB 실행 시간 합·버퍼는 거의 같다(상세 hot 0.13 → 0.14ms, 버퍼 27 → 31). 쿼리를 무겁게 만들지 않고 왕복만 줄였다. 개선 후 상세 요청 하나가 보내는 문장은 `BEGIN READ ONLY`(첫 쿼리와 함께 전송) → 쿼리 6개 → `COMMIT`이다.

**남은 것**

## 개선 결과 — 상세·재고 응답 캐시 (GR-183, 2026-10-27)

SSE 알림을 받은 화면들이 같은 상품을 한꺼번에 다시 조회하는 상황을 DB까지 보내지 않도록 공개 상세·재고 응답을 캐시했다. GR-184 위에서 측정했고 조건(seed, `compose.swapoff.yaml`, 워밍업, DB 왕복 3ms)은 같다. 원자료 `out/gr183-none-3ms/`, `out/gr183-memory-3ms/`.

**구조**

- `PublicDropReadService`: 트랜잭션을 열지 않는 조회 계층. 캐시를 맞히면 DB 커넥션을 쓰지 않고, 빗나갈 때만 `DropService`(읽기 전용 트랜잭션)를 부른다.
- `PublicDropCache`: 같은 키의 동시 조회를 한 번으로 합친다. 재고·판매·상태 변경이 커밋된 뒤(`StockChangedEvent`, AFTER_COMMIT, SSE 알림보다 먼저) 해당 DROP 캐시를 지운다. 지우기 전에 시작한 조회가 지우기 뒤에 끝나면 그 값은 저장하지 않고, 지우기 뒤의 요청은 그 조회에 합류하지 않는다(재조회가 옛 값을 받지 않게).
- `actions`(WISH·주문 가능 여부)와 `serverTime`은 조회 시각에 따라 달라지므로 캐시한 응답을 꺼낼 때마다 다시 계산한다. 규칙은 `Drop` 엔티티와 같은 정적 메서드를 공유한다.
- 저장소: `grab.drop-cache.store` = `memory`(기본) | `redis` | `none`(캐시 계층 전체를 건너뜀). TTL은 상세·재고 모두 5초다. 변경 이벤트가 없는 값(상세의 활성 WISH 수·브랜드명)과 같은 인스턴스 밖의 커밋(blue/green 전환 중)의 지연 상한이다.

**저장소 선택: 앱 메모리.** 운영 EC2↔Redis(Aiven Valkey) 왕복이 105ms로 측정돼 Redis 캐시는 맞혀도 DB 직접 조회(상세 약 28ms)보다 느리다. 단일 인스턴스 운영이라 인스턴스 간 공유도 필요 없다. 그래서 Redis는 측정하지 않았다(구현은 설정으로 바꿀 수 있게 남김).

**결과 — 여러 상품 분산 (`pair_random`, 4,500개)**

| VU | 동시 조회 합치기만 | 앱 메모리 캐시 |
| ---: | ---: | ---: |
| 400 | 628 / 263.2ms | **775 / 32.4ms** |
| 800 | 666 / 1,063.9ms | **1,375 / 303.2ms** |

**응답시간 (VU 10 × 20초)**: 상세 hot 중앙값 30.1ms → **0.2ms**, 재고 hot 9.3ms → **0.2ms**, 상세+재고 한 쌍 hot p95 44.8ms → **1.0ms**. 분산 조회(detail_random)는 21.1ms로, 캐시가 빗나간 요청은 GR-184의 DB 경로 그대로다.

**해석**

- 인기 상품 몰림은 **동시 조회 합치기**만으로 처리량 천장 대부분이 풀렸다(약 604 → 1,528건/초). 1000명이 같은 상품을 동시에 다시 불러도 DB 조회는 동시에 하나만 나가기 때문이다.
- **저장(앱 메모리)** 은 응답시간을 없앴다. 캐시를 맞히면 상세 응답이 약 28ms → 0.2ms이고 VU 800에서도 p95 18.6ms다.
- 여러 상품에 흩어진 조회는 동시에 겹치는 일이 적어 합치기만으로는 천장(약 666건/초)이 남았고, 저장해야 효과가 났다(VU 800 1,375건/초).
- 드롭 오픈처럼 재고가 계속 바뀌면 커밋마다 캐시를 지우지만, 지운 뒤의 재조회도 한 번으로 합쳐지므로 DB 조회는 재고 변경 횟수를 넘지 않는다. 이 측정에는 주문이 없어 인기 상품은 캐시가 계속 맞는 최선의 경우다. 주문과 함께 거는 측정은 GR-180에서 한다.
- 두 측정 모두 실패 0, 스왑 0. 요청 none 111,020건(조합별) + 동시 접속, memory 3,941,874건(조합별) + 동시 접속.

**측정 조건 주석**

- "동시 조회 합치기만"은 `store=none`으로 잰 값이다. 측정 당시 `none`은 저장만 끄고 합치기는 켜진 상태였다. 이후 `none`은 장애 시 끄기 스위치로 쓰도록 캐시 계층 전체를 건너뛰게 바꿨다. 진짜 캐시 없음은 GR-184 후 측정값이다.
- 앱 메모리 측정의 재고 TTL은 30초였다(측정 이미지 빌드 뒤 5초로 변경). 이 측정에는 재고 변경이 없어 결과 차이는 작다.
- JVM 힙 최대 사용량은 앱 메모리 캐시에서 약 270~340MB(캐시 없음 약 135~250MB)였다. 차이는 대부분 처리량이 약 2.6배로 늘면서 생긴 단명 객체로 본다. 캐시 자체는 상세+재고 JSON이 DROP당 평균 2.1KB(공개 DROP 200개 표본, 최대 2.8KB)라 객체로 DROP당 약 6~10KB, 로컬 공개 DROP 4,753개 전부를 담아도 약 30~50MB로 추정한다(힙 직접 측정 아님). 다시 읽히지 않는 만료 항목은 저장 시 10초마다 훑어 지우므로, 남는 항목은 최근 약 15초 안에 조회된 DROP으로 한정된다. micro(1GiB, `-Xmx550m`) 최종 측정(GR-180)에서 GC 후 live 힙으로 다시 확인한다.

## 한계

- backend·DB 모두 CPU 제한이 없다. Supabase Nano(공유 CPU)에서는 쿼리 자체도 느려져 천장이 더 낮을 수 있다.
- netem은 postgres 송신(응답 방향)에만 고정 지연을 건다. 실제 네트워크의 지연 편차·패킷 손실은 흉내 내지 않는다.
- 단일 상품 집중(hot)과 고른 분산(random) 두 패턴만 봤다. 실제 트래픽 비중은 GR-182 목표 정의를 따른다.
- SSE 연결 자체와 재조회를 함께 거는 측정은 GR-180 범위다.
