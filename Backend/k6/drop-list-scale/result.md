# 공개 DROP 목록 쿼리 대용량 기준선 (drop-list-scale, GR-164)

> 공통 실행 환경·전제는 `../README.md` 참고. 이 시나리오는 다른 시나리오와 달리 **nano 제한 환경이 아니다**(아래 측정 환경).

GR-153(steady-read)은 DROP 15건 seed라 공개 목록 쿼리의 실제 비용이 드러나지 않았다. DROP 수천 건 규모에서
정렬(날짜 / 인기 WISH / 인기 GRAB) × 필터(없음 / categoryId / keyword / soldOut) 12개 조합의 실행 계획과
응답시간을 기록하고, 측정 전 병목 후보마다 개선할지 판단한다. 이 단계에서는 애플리케이션 코드와 Flyway를 바꾸지 않았다.

## 측정 환경

| 항목 | 값 |
| --- | --- |
| 머신 | Apple M5(10코어), Docker Desktop VM 8GB / 10 CPU |
| 컨테이너 | `compose.yaml` + `compose.swapoff.yaml` — backend·postgres `mem_limit` 2GiB = `memswap_limit`(스왑 0), CPU 제한 없음 |
| 자원 기록 | `stats.sh` 2초 간격. 스왑 72샘플 모두 0, 최대 메모리 backend 555MiB·postgres 197MiB(2GiB 한도에 닿지 않음) |
| 부하 경로 | k6 컨테이너를 compose 네트워크에 붙여 `http://backend:8080`으로 직접 호출 |

nano(512MiB) 제한이 아니므로 다른 시나리오의 수치와 직접 비교하지 않는다. 같은 조건에서의 **조합 간 상대 비교와 개선 전후 비교**가 목적이다.

## seed (`seed.sql`, 기본값)

| 항목 | 규모·분포 |
| --- | --- |
| DROP | 5,000 — WISH 1,750 · GRAB 1,750(품절 221) · ENDED 1,000(품절 404) · DRAFT 250 · CANCELED 250 |
| 옵션 | 12,500(DROP당 1~4개, 비활성 417) |
| 이미지 | GALLERY 1~3장 + DETAIL 1장 |
| WISH | 64,316(활성 51,504). DROP당 `60 × random()^3`로 소수 상품에 쏠림 |
| 주문 | 26,481(결제 확정·미취소 18,499, 결제 후 취소 10%, 미결제 만료 20%) |
| 키워드·카테고리 | 이름 끝 단어 19종(n % 19), 카테고리 8종((n / 20) % 8) — 상태(n % 20)와 겹치지 않는 주기 |

`setseed`로 분포를 고정하고 마지막에 `VACUUM (ANALYZE)`를 실행한다. WISH·GRAB은 판매 시작·종료를 3일 이후로 두고 미결제 주문은 `EXPIRED`로 넣어, 측정 중 상태 전환·결제 만료 배치가 데이터를 바꾸지 않게 했다.

## 측정 절차

```
docker compose -f compose.yaml -f k6/drop-list-scale/compose.swapoff.yaml up -d
docker compose exec -T postgres psql -U grab -d grab -f - < k6/common/accounts-seed.sql
docker compose exec -T postgres psql -U grab -d grab -v ON_ERROR_STOP=1 -f - < k6/drop-list-scale/seed.sql
k6/drop-list-scale/stats.sh "$PWD/k6/drop-list-scale/out/<이름>/stats.txt" &   # 측정 후 종료
k6/drop-list-scale/explain.sh <이름> 5
docker run --rm -i --network backend_default -v "$PWD/k6:/k6" -w /k6 -e BASE_URL=http://backend:8080 \
  grafana/k6 run --summary-export drop-list-scale/out/<이름>/k6-summary.json drop-list-scale/drop-list.js
```

- `explain.sh`: auto_explain(ANALYZE·BUFFERS)을 잠시 켜고 조합마다 워밍업 1회 후 5회 호출해, 앱이 실제로 보낸 SQL·바인딩 값 그대로의 본 쿼리·count 쿼리 계획을 모은다. 끝나면 설정을 되돌린다.
- `drop-list.js`: 조합마다 VU 10 × 20초를 순서대로 실행(조합 간 간섭 없음). page=0, size=20.
- `concurrency.sh <이름> mix grab_none date_soldout`: 대상마다 `concurrency.js`로 VU 25→50→100→200→400→800을 단계당 60초씩 올리고(요청 후 1초 대기, VU ≈ 동시 접속자), 단계 구간의 HikariCP 지표를 Prometheus에서 읽어 `out/<이름>/concurrency/summary.tsv`로 합친다. `stats.sh`를 자체적으로 함께 띄운다.
- keyword는 `스니커즈`(약 5% 선택도), categoryId는 1(FASHION), soldOut은 `false`(후보가 많은 쪽).
- 원자료는 `out/<이름>/`에 남는다(gitignore).

## 병목 분석

### 1. 인기 GRAB 정렬 — 판매 수량 집계 (`grab_none` 계획)

- 정렬 키 `((SubPlan 6)) DESC`가 판매 수량 합(`orders` ⋈ `order_items`)이라, LIMIT 20 전에 판매 기간·재고 조건을 통과한 후보 **1,531건마다** 서브쿼리가 실행된다.
- `orders`는 `idx_orders_drop_status (drop_id, status, id)`로 `drop_id`만 찾고 `paid_at IS NOT NULL AND canceled_at IS NULL`은 힙에서 거른다(후보당 약 6.8행).
- `order_items`를 `uq_order_items_order_option`으로 **10,367회** 조회한다.
- 본 쿼리 버퍼 60,442 중 **48,524(80%)**가 이 정렬 키 계산이다.

### 2. soldOut 필터 — 가용 재고 합계 반복 계산 (`date_soldout` 계획)

- 필터 `(SELECT COALESCE(SUM(total - reserved - sold - withheld), 0) = 0 …) = :soldOut`가 후보 **4,503건마다** 실행된다(필터 없는 날짜 정렬은 후보를 읽기만 하고 서브쿼리는 LIMIT 이후 20행에만 실행된다).
- 본 쿼리 버퍼 512 → 14,099(약 28배), count 쿼리 210 → 13,812(약 66배). count 쿼리도 같은 필터를 다시 계산한다.
- 서브쿼리 1회 비용은 작지만(약 0.001ms) 후보 전체에 곱해져, API p95가 날짜 정렬 9.0ms → 49.2ms, 인기 WISH 13.6ms → 30.8ms로 오른다.

### 3. 병목이 아닌 후보

- **keyword**(`ILIKE '%스니커즈%'`, 약 5% 선택도): 본 쿼리 0.5~3.2ms, p95 9.7~12.2ms. 이 규모에서 순차 스캔 비용이 작다.
- **활성 WISH 집계**: `wish_none`은 기존 `idx_wishes_drop_active`로 Index Only Scan(후보 1,750건, 버퍼 5,730), p95 13.6ms.

### 해석

- **처리량 천장 = 커넥션 풀 크기 ÷ 요청당 DB 점유 시간.** 인기 GRAB은 요청 하나가 커넥션을 약 50ms 쥔다(VU 25 중앙값 52ms). 풀 10개로는 10 ÷ 0.05s ≈ **초당 200건**이 한계이고, 실측도 VU 400·800에서 199.5·199.8건으로 그대로 멈췄다. 날짜 + soldOut은 약 35~40ms라 천장이 약 257건으로 조금 높다. 같은 날짜 정렬에서 필터만 뺀 `date_none`은 VU 800까지 천장에 닿지 않아(초당 798건, p95 38.8ms) **soldOut 필터 하나가 천장을 3배 이상 낮춘다**. `date_none`의 실제 천장은 측정 범위 밖이다.
- **천장을 넘으면 대기열이 응답시간이 된다.** 천장을 넘긴 VU 400에서 커넥션 대기가 190건(Tomcat 요청 스레드 대부분이 커넥션을 기다림)까지 쌓이고, 커넥션 획득에만 평균 약 1초가 걸려 p95가 155ms → 2.1s로 무너진다. 에러·타임아웃은 없었다(HikariCP 대기 한도 30초 안).
- **병목은 커넥션 점유 시간이다.** 천장에서 커넥션 대기가 쌓이고 획득 시간이 응답시간 증가분 대부분을 차지하므로, 요청이 커넥션을 쥐는 시간을 줄이면(GR-176·177) 천장이 그만큼 올라간다. 풀을 늘리는 방법도 있지만 쿼리 비용을 그대로 둔 채 DB 동시 실행만 늘리는 것이라 우선순위가 낮다.
- **CPU 포화 여부는 이 측정으로 판단하지 않는다.** `stats.sh`의 `docker stats` 순간 샘플(약 5초 간격)로는 postgres CPU 최대 약 99%(10코어 중 약 1코어), backend 약 10%였다. 커넥션 10개가 쿼리를 계속 실행했다면 더 높아야 해서, 순간 샘플이 실행 구간을 놓쳤거나 커넥션 점유 시간 중 DB 실행 외 시간(트랜잭션 안 매핑 등)이 섞였을 수 있다. 구분하려면 `pg_stat_statements`의 쿼리 시간 합이나 연속 CPU 지표가 필요하다(미측정).
- **혼합 트래픽은 VU 800까지 버텼다.** 무거운 조합이 15~25%만 섞이면 평균 점유 시간이 짧아 초당 780건까지 늘었고, VU 800에서 p95가 42 → 84ms로 꺾이기 시작했다. 인기 GRAB·soldOut 비중이 큰 순간(드롭 오픈 직후 인기순 진입 등)에는 위 단독 곡선에 가까워진다.

### JVM 힙·GC

기준선 측정 때는 `concurrency.sh`가 JVM 지표를 남기지 않아, Prometheus(15초 스크랩, 15일 보관)에 쌓인 actuator 지표를 단계 구간별로 다시 조회했다. 이후 `concurrency.sh`는 같은 지표를 `summary.tsv`에 함께 남긴다(`heap_max_mb`, `gc_count`, `gc_pause_sum_ms`, `gc_pause_max_ms`, `alloc_mb_s`, `alloc_kb_per_req`).
힙 한도는 512MB다(`-Xmx` 미지정 → 컨테이너 메모리 2GiB의 1/4). 운영 배포(`deploy/compose.prod.yaml`)도 JVM 옵션이 없어 인스턴스 메모리 2GB면 같은 한도가 된다.

| --- | ---: | ---: | ---: | ---: | ---: | ---: |

| 혼합 | 800 | 177MB | 584 | 1,535ms | 8ms | 641MB/s |

- **힙·GC는 병목이 아니다.** 힙은 한도 512MB에 닿지 않았고, 천장 근처(인기 GRAB VU 200)에서도 GC 멈춤은 60초 중 0.55초(0.9%), 요청당 평균 0.05ms다. 천장을 넘긴 VU 400에서 힙이 300MB대로 오른 것은 커넥션을 기다리는 요청 약 190개가 객체를 붙잡고 있기 때문으로 보인다. 대상별 힙 최대값 차이(180MB대 vs 340MB대)는 부하보다 G1의 영역 크기 조정 시점 차이로 보이며 부하에 비례하지 않았다.
- **요청당 할당량이 약 0.8MB로 크다.** 할당 속도 ÷ 처리량이 모든 대상에서 약 0.8MB/요청(예: 날짜 필터 없음 VU 25에서 20.1MB/s ÷ 초당 25건)으로 비슷해, 특정 쿼리가 아니라 목록 API 공통 경로에서 생긴다. 20건짜리 목록 응답에 비해 큰 편이라 이후 응답 경로를 볼 때의 단서로 남긴다(지금은 GC 시간이 작아 병목은 아님).

## 개선 결과 — 인기 GRAB 판매 수량 집계 (GR-176, 2026-10-27)

기준선과 같은 조건(seed 후 `VACUUM (ANALYZE)`, `compose.swapoff.yaml`)에서 두 방식을 실제 앱에 적용해 비교했다. 원자료 `out/after-index/`, `out/after-sold/`.

- **A — 부분 인덱스(명세 정의 그대로):** `orders (drop_id, id) WHERE paid_at IS NOT NULL AND canceled_at IS NULL` + `order_items (order_id, drop_id) INCLUDE (quantity)`. 측정용으로 psql에서 만들고 측정 후 지웠다.
- **B — 채택:** 정렬 키를 `SUM(drop_options.sold_quantity)`(비활성 SKU 포함)로 계산한다. `sold_quantity`는 결제 확정·결제 후 취소에서만 주문 상태와 같은 트랜잭션으로 바뀌어 "결제 확정·미취소 주문의 `order_items.quantity` 합"과 값이 같다(`api-spec/DROP.md` 1.2에 근거 명시). 측정 시점 로컬 DB 전체 DROP 5,003건에서 두 값 불일치 0. 마이그레이션 없음.

| 인기 GRAB | 기준선 | A 부분 인덱스 | B `sold_quantity` |
| --- | ---: | ---: | ---: |
| 본 쿼리 `grab_none` / `grab_soldout` | 17.5 / 18.2ms | 10.7 / 10.9ms | **5.5 / 7.1ms** |
| 본 쿼리 버퍼 `grab_none` / `grab_soldout` | 60,442 / 61,992 | 35,762 / 37,323 | **16,532 / 18,082** |
| VU 25 응답 중앙값 | 52.3ms | 39.8ms | **24.8ms** |
| 처리량 천장 | 초당 약 200건 | 약 244건 | **약 495건 (2.5배)** |
| VU 200 p95 | 154.9ms | 79.1ms | **43.0ms** |
| VU 400 p95 | 2,116.8ms | 695.7ms | **45.7ms** |
| VU 800 p95 | 4,344.4ms | 3,389.2ms | 1,320.1ms |
| VU 800 커넥션 대기 최대 | 190 | 190 | 190 |

- B는 VU 400까지 커넥션 대기가 거의 없고(최대 6) p95 46ms를 유지한다. VU 800에서 천장(초당 약 495건)에 닿아 다시 대기가 쌓인다.
- A는 버퍼를 40% 줄였지만 후보마다 주문 항목을 찾는 구조가 남아 천장이 22%만 올랐다.
- 혼합 트래픽은 세 경우 모두 VU 800까지 천장 없이 버텼다(초당 780~790건, p95 39~84ms). 인기 GRAB 비중이 15%라 전체 처리량 차이는 측정 편차 수준이다.
- 다른 조합(날짜·인기 WISH)은 쿼리가 바뀌지 않아 버퍼가 기준선과 같다(예: `date_soldout` 14,099 → 14,099). 시간은 회차 편차로 흔들렸다(`date_soldout` 5.2 → 7.7ms).
- 조합별 p95(`drop-list.js`, VU 10 × 20초)도 B 적용 후 다시 측정했다(418,217건, 실패 0, 스왑 0). 원자료 `out/after-sold/k6-summary.json`.

  인기 GRAB(필터 없음)의 감소폭(-59%)이 가장 크다. 다만 쿼리가 바뀌지 않은 조합(날짜·인기 WISH)도 11~42% 줄었다. 이 조합들은 실행 계획·버퍼가 기준선과 같으므로 이 감소는 개선 효과가 아니라 회차 편차다. 기준선은 `explain.sh`가 백엔드를 재시작한 직후 측정했고 이번에는 여러 측정으로 JVM이 충분히 데워진 뒤라, 워밍업 차이가 원인일 가능성이 높다(확인하지 않음). 그래서 개선 효과의 근거는 이 표보다 버퍼 수와 동시 접속 천장으로 본다.
- 예측과의 차이: A 결과만 보고 "요청 중앙값과 쿼리 시간의 차이(약 30ms)는 쿼리 밖 고정 시간"이라 보고 B의 천장을 +30~40%로 예상했지만, 실제로는 요청 중앙값이 쿼리 감소폭(12ms)보다 크게(27ms) 줄어 2.5배가 됐다. 이 차이의 원인은 따로 확인하지 않았다.
- 검증: `DropRepositoryTest`의 주문 픽스처가 실제 원장처럼 결제 확정·미취소 주문 수량만큼 `sold_quantity`를 올리도록 고쳤고, 비활성 SKU 판매분 포함 테스트를 추가했다. 결제 확정·결제 후 취소의 `sold_quantity` 이동은 기존 결제 통합 테스트(`PaymentServiceIntegrationTest`, `OrderPaidCancelIntegrationTest`)가 검증한다. 전체 테스트 2,051건 통과.

## 측정 중 바로잡은 것

1. **k6 접속 경로**: 처음엔 `host.docker.internal`(Docker Desktop 포트 포워딩)로 보냈는데 `dial: i/o timeout` 42건이 나왔다. 백엔드 로그는 정상이어서 측정 경로 문제로 보고 compose 네트워크 직접 호출로 바꿨다(이후 실패 0).
2. **스왑**: 처음엔 기본 `compose.yaml`로 돌려 스왑이 허용된 상태였다(측정 후 스왑 사용량은 0). 조건을 명확히 하려고 `compose.swapoff.yaml`로 스왑을 막고 자원 사용량을 기록하며 다시 측정했다. 위 결과가 이 측정이다.
3. **visibility map**: seed 직후 `ANALYZE`만 하면 autovacuum 시점에 따라 `wish_none`이 Index Only Scan ↔ Bitmap Heap Scan으로 바뀌었다. seed 마지막을 `VACUUM (ANALYZE)`로 바꿔 매번 같은 상태에서 측정한다.
4. **seed 분포**: 키워드 단어와 상태를 같은 주기(n % 20)로 정해 단어 하나가 한 상태에만 걸렸다. 단어 n % 19, 카테고리 (n / 20) % 8로 바꿨다.

## 한계

- 로컬 단일 머신(Apple M5)이고 운영·nano 사양이 아니다. 절대값은 운영 응답시간이 아니라 조합 간·전후 비교용이다.
- auto_explain의 ANALYZE 계측 오버헤드가 시간에 포함된다. k6 측정 중에는 꺼져 있다.
- 첫 페이지(page=0, size=20)만 측정했다. 깊은 페이지의 OFFSET 비용은 보지 않았다.
- 동시 접속 측정은 목록 조회만 보낸다. 주문·상세 조회·SSE와 섞인 실제 드롭 오픈 트래픽은 아니며(GR-152·GR-113), 혼합 비중은 실측이 아닌 가정값이다.
- CPU를 제한하지 않아(10코어) 운영(t3, vCPU 2개)보다 DB 연산 여유가 크다. 천장이 커넥션 풀에서 생긴다는 구조는 같지만, CPU가 적은 환경에서는 쿼리가 느려져 천장이 더 낮아질 수 있다.
- HikariCP `acquire_seconds_max`는 감쇠하는 최댓값 게이지라 이전 대상의 꼬리가 다음 대상 첫 단계에 섞인다. 그래서 표에는 넣지 않고(원자료 `summary.tsv`에만 있음) 누적 합 기반 평균만 썼다.
- seed 규모(DROP 5,000)를 넘는 데이터에서의 증가 추세(선형 여부)는 측정하지 않았다.
