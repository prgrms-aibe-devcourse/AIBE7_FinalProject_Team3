# 평상시 조회 (steady-read, GR-153)

> 공통 실행 환경·전제는 `../README.md` 참고.

## 2026-10-26 재검증: `cpus: 2`(올바른 t3.nano 스펙) 적용 후에도 통과

`compose.loadtest-nano.yaml`의 `cpus`를 2로 고친 뒤(이전엔 1로 잘못 제한) 다시
실행. 체크 3384/3384(100%) 성공, `http_req_failed` 0.00%, `verify.sql` 예상치
못한 주문·재고 변동 0건 — **통과**. 응답시간이 눈에 띄게 빨라짐(avg 3.83ms,
p95 5.49ms — `cpus: 1`일 때보다 한 자릿수 더 빠름). 다만 메모리는 **506MiB/512MiB
(98.83%)**로 거의 한계치였다 — 이 실행 전에 같은 컨테이너에서 stock-race·
idempotency·expiry·drop-open-spike를 연달아 돌린 누적 효과가 크다(drop-open-spike
직후라 이미 505MiB였음).

## 2026-10-26 재검증(이전): `memswap_limit` 추가(스왑 차단) 후에도 통과 — 이때는 아직 `cpus: 1`

`memswap_limit: 512m`으로 스왑을 막은 뒤 재실행. 체크 1964/1964(100%) 성공,
`http_req_failed` 0.00%, `verify.sql` 예상치 못한 주문·재고 변동 0건 — **통과**.
메모리 440.1MiB/512MiB(85.95%), OOM-kill 없음.

## 2026-10-23 최초 실행 (호스트 스왑 켜진 환경 — `memswap_limit` 추가 전)

조회 캐시(Redis)는 아직 없다(TECHSTACK.md 87절, "문제를 확인한 뒤 적용"). 이
결과는 캐시 없이 DB가 평상시 목록·상세 조회를 얼마나 버티는지의 하한선이며,
병목이 확인되면 캐시 도입 판단 근거로 쓴다. 인기 드롭 1개 반복 상세조회
(`hot_read`, VU 10)와 매번 다른 드롭 조회(`random_read`, VU 10)를 30초간
steady-state로 동시 실행, **2회 통과**.

- 체크 3214~3329건(100%) 성공, `http_req_failed` 0.00%
- 응답시간 매우 낮음: p90 ~8~19ms, p95 ~9~43ms — 캐시 없이도 nano에서 충분히
  빠름(단, 최대 6.04s 아웃라이어 1건 — 첫 요청 JIT/커넥션 워밍업 추정)
- HikariCP 커넥션: `max=10` 중 Prometheus 15초 스크랩 구간에서 관측된 active
  최댓값은 1 — 쿼리가 스크랩 간격보다 훨씬 빨리 끝나 동시 사용량을 못 잡음
  (GR-151의 `pg_stat_activity` 관측 한계와 동일한 샘플링 문제). `pending`은
  시종 0으로, 풀 고갈은 없었음
- 리소스: backend CPU 34~36%, **메모리 96.8~96.9%**(512MiB 중) — 호스트 스왑이
  만든 여유 메모리(최대 1GiB)가 섞인 수치라 `memswap_limit` 추가 후 85.95%로
  다시 측정됐다. 컨테이너 재시작 0회, OOM 없음. 이전 시나리오들을 같은
  컨테이너에서 연달아 돌린 누적 효과일 수 있어, 단일 시나리오만 단독 실행 시
  수치는 더 낮을 가능성이 있음(검증 안 함)
- `verify.sql`: 예상치 못한 주문 0건, 재고 변동 0건(읽기 전용 시나리오가
  실제로 쓰기를 하지 않았음을 확인)

## 2026-10-26(이어서): G1GC 명시 재검증 — nano·micro 둘 다 통과

`JDK_JAVA_OPTIONS`에 `-XX:+UseG1GC`를 명시하고 nano·micro 양쪽에서 다시 실행. 둘 다 **통과**(체크 100%). 결과·수치에 의미 있는 차이는 없었다(nano 메모리 90.71%, micro 58.39%).

## 결론

에러 **미발생**, 응답시간 p95 한 자릿수 ms로 캐시 없이도 충분히 빠름. 최신
(2026-10-26, 스왑 차단 + 올바른 CPU 2개) 수치는 메모리 98.83%까지 올라갔는데,
이는 같은 컨테이너에서 여러 시나리오를 연달아 돌린 누적 효과가 크게 작용한
결과로 보인다(단독 실행 시 수치는 더 낮을 가능성이 높음, 검증 안 됨). HikariCP
풀 고갈은 없었음(샘플링 한계로 동시 사용량 자체는 못 잡음).
