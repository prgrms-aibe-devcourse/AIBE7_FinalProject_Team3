# 평상시 조회 (steady-read, GR-153)

> 공통 실행 환경·전제는 `../README.md` 참고.

조회 캐시(Redis)는 아직 없다(TECHSTACK.md 87절, "문제를 확인한 뒤 적용"). 이
결과는 캐시 없이 DB가 평상시 목록·상세 조회를 얼마나 버티는지의 하한선이며,
병목이 확인되면 캐시 도입 판단 근거로 쓴다. 인기 드롭 1개 반복 상세조회
(`hot_read`, VU 10)와 매번 다른 드롭 조회(`random_read`, VU 10)를 30초간
steady-state로 동시 실행, **2회 통과**.

- 체크 3214~3329건(100%) 성공, `http_req_failed` 0.00%
- 응답시간 매우 낮음: p90 ~8~19ms, p95 ~9~43ms — 캐시 없이도 nano에서 충분히
  빠름(단, 최대 6.04s 아웃라이어 1건 — 첫 요청 JIT/커넥션 워밍업 추정)
- HikariCP 커넥션: `max=10` 중 Prometheus 15초 스크랩 구간에서 관측된 active
  최댓값은 1 — 쿼리가 스크랩 간격보다 훨씬 빨리 끝나 동시 사용량을 못 잡음
  (GR-151의 `pg_stat_activity` 관측 한계와 동일한 샘플링 문제). `pending`은
  시종 0으로, 풀 고갈은 없었음
- 리소스: backend CPU 34~36%, **메모리 96.8~96.9%**(512MiB 중) — 지금까지
  시나리오 중 가장 높음. 컨테이너 재시작 0회, OOM 없음. 이전 시나리오들을 같은
  컨테이너에서 연달아 돌린 누적 효과일 수 있어, 단일 시나리오만 단독 실행 시
  수치는 더 낮을 가능성이 있음(검증 안 함)
- `verify.sql`: 예상치 못한 주문 0건, 재고 변동 0건(읽기 전용 시나리오가
  실제로 쓰기를 하지 않았음을 확인)

## 결론

에러 **미발생**, 응답시간 p95 수십ms로 캐시 없이도 충분히 빠름. 다만 메모리
96.8~96.9%로 다섯 시나리오 중 가장 높아, nano에서 가장 빠듯한 케이스.
HikariCP 풀 고갈은 없었음(샘플링 한계로 동시 사용량 자체는 못 잡음).
