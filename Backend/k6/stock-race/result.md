# 재고 경쟁 (stock-race, GR-151)

> 공통 실행 환경·전제는 `../README.md` 참고.

## 2026-10-26 재검증: `cpus: 2`(올바른 t3.nano 스펙) 적용 후에도 통과

`compose.loadtest-nano.yaml`의 `cpus`를 AWS 실제 스펙대로 2로 고친 뒤(이전엔 1로
잘못 제한) 다시 실행. 재고 5개에 VU 20명 동시 주문 → **통과**(성공 5건, 나머지 422
`INSUFFICIENT_STOCK`, `verify.sql` 초과판매·음수재고 0행, threshold
`stock_race_success_total count==5` 통과). CPU 여유가 생기면서 처리 속도도 빨라져
`http_req_duration` max가 2.54s(`cpus: 1`) → 1.26s(`cpus: 2`)로 줄었다. 메모리
419.6MiB/512MiB(81.96%), OOM-kill 없음.

## 2026-10-26 재검증(이전): `memswap_limit` 추가(스왑 차단) 후에도 통과 — 이때는 아직 `cpus: 1`

`compose.loadtest.yaml`에 `memswap_limit: 512m`을 추가해 호스트 스왑에 기대지
않는 순수 512MB 한도로 다시 실행. 재고 5개에 VU 20명 동시 주문 → **통과**
(성공 5건, 나머지 422 `INSUFFICIENT_STOCK`, `verify.sql` 초과판매·음수재고 0행,
threshold `stock_race_success_total count==5` 통과). 실행 직후 메모리
416.7MiB/512MiB(81.39%), OOM-kill 없음. (같은 조건에서 [drop-open-spike](../drop-open-spike/result.md)는
서버가 죽었으니, 이 시나리오가 통과했다고 nano 전체가 안전하다는 뜻은 아니다.)

재고 5개에 VU 20명이 동시 주문. **3회 실행, 전부 통과** (성공 5건 / 나머지 422
`INSUFFICIENT_STOCK`, `verify.sql` 음수재고·초과판매 0행).

| 실행 | HTTP 요청 | 성공(201) | 실패(422, 정상) | 완료까지 |
|---|---|---|---|---|
| 1회차 | 22 | 5 | 15 | 1.1s~7s(그레이스풀 스톱 포함) |
| 2회차 | 22 | 5 | 15 | 1.1s |
| 3회차(관찰용) | 22 | 5 | 15 | 1.3s |

자격증명 오류(401/403)는 전 실행에서 0건 — 백엔드 로그에 `INSUFFICIENT_STOCK` 비즈니스
경고만 있고 인증/CSRF 실패는 없었다.

> 이 1회차 실행은 `cpus: 1`로 제한했던 시점의 기록이다. 실제 t3.nano는 vCPU 2개라
> CPU 코어 수 제한이 틀린 전제였음을 2026-10-26에 확인·수정했다(`../README.md` 참고).
> 측정값 자체(100.20% 포화)는 그 잘못된 제한 하에서 나온 결과라 그대로 둔다.

리소스(1회차, `docker stats`):

| 컨테이너 | CPU | 메모리 |
|---|---|---|
| backend | 100.20% (1 vCPU 한도에 포화) | 459.9MiB / 512MiB (89.82%) |
| postgres | 9.60% | 73.5MiB / 7.7GiB |

**`pg_stat_activity` 관찰 결과**: 외부에서 `docker compose exec`로 폴링하는 방식은
프로세스 기동 오버헤드가 수백ms라, 재고 행 잠금이 걸리는 임계구간(전체 레이스가
1초 안에 끝남)을 한 번도 포착하지 못했다. 락 경합 자체는 `verify.sql`의 정합성
결과(초과판매·음수재고 0건)로 간접 확인했다 — t3.nano 수준에서도 레이스가 1초
내로 해소될 만큼 빠르다는 뜻이며, 정합성 검증의 신뢰도를 낮추지 않는다.

## 결론

초과판매·음수재고 **미발생**(cpus:1 3회 + cpus:2 재검증 1회, 총 4회 반복 확인). 2026-10-23
최초 실행 땐 CPU를 1개로 잘못 제한해 100.20%로 포화됐었는데, 2026-10-26에 올바른
스펙(2개)으로 고치고 나니 같은 부하에서도 CPU 포화 없이 더 빠르게 처리됨. 메모리는
두 경우 모두 80%대로 여유 있었음.
