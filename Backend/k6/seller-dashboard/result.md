> 공통 실행 환경·전제는 `../README.md` 참고. steady-read(GR-153)와 같은 성격 — 정확한
> 캐파시티가 아니라 캐시 없이 집계 쿼리가 평상시 수준 동시 조회를 버티는 하한선을 본다.

## 2026-10-27 최초 실행: micro, 30초

`compose.loadtest-micro.yaml`(vCPU 2개, 1GiB, `-Xmx550m`)로 기동, `seed.sql` 실행
(DROP 200개·DROP당 결제 완료 주문 5건·위시 20명 = 주문 1000건, 위시 4000건) 후
`summary_read`(VU 10)·`drop_stats_read`(VU 10)를 30초간 동시 실행.

- 체크 1634/1634(100%) 성공, `http_req_failed` 0.00%
- 응답시간: avg 17.28ms, med 13.34ms, p90 18.75ms, **p95 22.04ms**(max 465.62ms는
  초반 로그인 직후 1건의 워밍업 아웃라이어로 추정 — 재검증 필요)
- 메모리 568.6MiB/1GiB(55.53%), OOM·에러 로그 없음
- `verify.sql`: 주문 1000건·위시 4000건(seed.sql 기대값과 정확히 일치), 재고 카운터
  변동 0건 — 읽기 전용 시나리오가 실제로 쓰기를 하지 않았음을 확인

`findDropStats`의 DROP당 LATERAL 조인 2개(재고 집계 + 주문 집계 서브쿼리)가 DROP
200개·주문 1000건 규모에서도 steady-read 수준(p95 한 자릿수~20ms대)을 유지했다 —
이 규모에서는 집계 쿼리가 뚜렷한 병목이 아니다.

## 측정 환경의 한계

- VU 20(summary 10 + drop_stats 10)·30초는 steady-read와 같은 축소판 하한선이며,
  운영 트래픽 규모를 반영한 수치가 아니다.
- seed.sql의 DROP 200개·판매자 1명은 "평상시보다 훨씬 많은" 수준을 임의로 정한 값이라,
  실제 상위 판매자의 DROP·주문 규모와 다를 수 있다.
- max 465.62ms 아웃라이어 1건의 원인(JIT/커넥션 워밍업 추정)은 별도로 확인하지 않았다.
