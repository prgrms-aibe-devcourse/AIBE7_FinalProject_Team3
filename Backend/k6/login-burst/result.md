# 로그인 동시 폭주 결과 (GR-161)

로그인 요청이 동시에 몰릴 때 서버가 어느 지점에서 무너지는지, 그 원인이 무엇인지 측정했다.

> **하한선 검증이다.** 운영(t3.small, 2GB)보다 약한 로컬 제한 환경(t3.micro 메모리 기준)에서 측정했다.
> 응답시간·처리량·한계 VU를 운영 캐파시티로 쓰지 않는다. 공식 목표(NFR-006)가 없어 합격·불합격은 판정하지 않는다.

| 항목 | 내용 |
|---|---|
| 측정일 | 2026-10-26, 2026-10-27 |
| 조건 | 메모리 1GiB(스왑 없음)에서 세 조건: **CPU1·Serial**, **CPU2·Serial**, **micro·G1** ([1.1절](#11-조건)) |
| 시나리오 | 지속 실행(30초 동안 계속 로그인), 일제히 실행(VU마다 1회), 실패 로그인(없는 계정) |
| 실행 방법 | [login-burst.js](login-burst.js) 상단 주석 |

## 요약

### 한계 단계

| 실행 | CPU1·Serial | CPU2·Serial | micro·G1 |
|---|---|---|---|
| 지속 실행 | **VU 40** (VU 20은 정상) | **VU 80** (VU 40은 정상) | **VU 80** (VU 40은 경계, 3회 중 2회 힙 OOM) |
| 일제히 실행 | VU 80까지 한계 없음 (최대 대기 9.0초) | **VU 80** (VU 40은 정상) | **VU 80** (VU 40은 정상) |
| 실패 로그인(지속) | **VU 40** | **VU 80** | **VU 80** (VU 40은 정상) |

- 실패 원인은 모두 힙 `OutOfMemoryError` 또는 Redis 명령 타임아웃(2초)이었다. 본 측정에서 컨테이너 OOM-kill은 한 번도 없었다.
- micro·G1 일제히 VU 80 2회차에서는 Tomcat Poller 스레드가 힙 OOM으로 죽어, 컨테이너가 `running`인 채로 재시작 전까지 응답하지 않았다([2.5절](#25-응답-불가)).

### 핵심 수치

| 항목 | 값 |
|---|---|
| 로그인 1건당 힙 할당 | **약 20.5MiB** (조건·VU·성공/실패와 관계없이 19.8~20.6MiB) |
| 힙 512MiB에 동시에 들어가는 해시 | **약 21건** (Serial GC 로그 기준, [3절](#3-원인-분석-argon2의-힙-사용)) |
| 최대 처리량 | CPU1·Serial **17.4회/초**(VU 1), CPU2·Serial **27.5회/초**(VU 5), micro·G1 **26.3회/초**(VU 1) |
| 한계 단계의 GC 정지 합계 | Serial 15.8~43.9초, micro·G1 20.2~36.3초 (약 30초 실행 기준. 측정 방법이 달라 직접 비교하지 않는다) |

### 결론

1. **원인은 Argon2의 힙 사용이다.** 해시 1건이 진행되는 동안 힙 약 19MiB가 붙잡혀 있다. 동시에 진행 중인 해시가 힙 한도를 넘으면(512MiB 힙에서 약 21건) Full GC가 반복되고, 처리량이 떨어지며, Redis 타임아웃이나 힙 OOM으로 요청이 실패한다.
2. **동시 처리를 늘려도 처리량은 늘지 않는다.** 처리량은 동시 처리 수가 CPU 수 근처일 때 가장 높았고, 그보다 많으면 GC 때문에 줄었다(CPU1·Serial은 VU 1의 17.4 → VU 40의 8.5회/초, micro·G1은 VU 1의 26.3 → VU 80의 5.7회/초).
3. **CPU는 처리 속도를, 힙은 버틸 수 있는 양을 정한다.** CPU를 2개로 늘리자 처리량은 최대 2.3배, 지속 실행 한계는 VU 40 → 80이 됐다. 하지만 일제히 80명은 CPU 1개에서는 모두 성공했고 CPU 2개에서는 실패했다. 설정을 G1·힙 550MiB로 바꿔도 한계는 VU 80으로 같았다.
4. **힙 OOM은 요청 하나로 끝나지 않을 수 있다.** 대부분은 OOM이 난 요청만 500으로 끝났지만, Tomcat 내부 스레드가 OOM으로 죽으면 서버 전체가 응답을 멈춘다. 컨테이너 상태로는 알 수 없고 재시작해야 회복된다.
5. **틀린 비밀번호도 같은 비용이 든다.** 없는 계정도 더미 해시로 Argon2를 실행하고, 로그인 시도 제한이 없다. 실패 로그인만 동시에 보내도(CPU1·Serial 40개, 나머지 80개) 힙 OOM과 5xx가 났다.
6. **저장소 nano 설정은 로그인 부하를 버티지 못한다.** nano(512MiB, `-Xmx384m`)는 힙 밖 메모리만 약 300MiB라, 스왑 없이는 로그인 1명 부하에서도 컨테이너가 OOM-kill됐다([부록 B](#부록-b-nano-예비-측정과-환경-변경-경위)). 그래서 1GiB(t3.micro) 기준으로 측정했다.

대응 후보는 [4절](#4-개선-방향-구현하지-않음)에 정리했다. 로그인 동시 처리 수 제한이 1순위다.

## 1. 측정 조건

### 1.1 조건

| 이름 | 측정일 | 설정 | CPU | 힙 | GC | GC 수치 출처 |
|---|---|---|---|---|---|---|
| CPU1·Serial | 10-26 | 임시 설정 | 1개 | 512MiB | Serial | GC 로그 |
| CPU2·Serial | 10-26 | 임시 설정 | 2개 | 512MiB | Serial | GC 로그 |
| **micro·G1** | 10-27 | 저장소 [compose.loadtest-micro.yaml](../../compose.loadtest-micro.yaml) | 2개 | 550MiB | G1 | actuator 지표 |

**micro·G1이 앞으로 개선 효과를 비교할 기준선이다.** 저장소 설정 그대로라 누구나 같은 조건으로 다시 잴 수 있다.

| 항목 | 임시 설정 (CPU1·Serial, CPU2·Serial) | micro·G1 |
|---|---|---|
| 실행 | `docker compose -f compose.yaml -f compose.loadtest.yaml -f <임시 설정> up -d backend` | `docker compose -f compose.yaml -f compose.loadtest-micro.yaml up -d --build backend` |
| 메모리 | 1GiB, 스왑 없음(`memswap_limit` = `mem_limit`) | 같음 (`Memory` = `MemorySwap` = 1073741824 확인) |
| JVM 옵션 | `-Xmx512m -Xlog:gc` | `-Xmx550m -XX:+UseG1GC` (JDK 17.0.20) |
| CPU | `cpus: 1` 또는 `cpus: 2` | `cpus: 2` (`NanoCpus` 2000000000 확인) |
| 실행 시각(KST) | CPU 1개 14:04~14:44, CPU 2개 15:43~15:54 | 09:37~09:52 |

- **임시 설정**: 10-26에는 저장소에 micro 설정이 없었다. 그래서 저장소 `compose.loadtest.yaml`(nano 설정, 지금의 `compose.loadtest-nano.yaml`)은 그대로 두고, 아래 파일을 저장소 밖에 만들어 세 번째 `-f`로 얹었다(작업자 결정). 이후 GR-154(#180)에서 저장소에 `compose.loadtest-micro.yaml`이 생겨 10-27에 다시 측정했다.
  ```yaml
  services:
    backend:
      mem_limit: 1g
      memswap_limit: 1g        # 스왑 없음
      environment:
        JDK_JAVA_OPTIONS: -Xmx512m -Xlog:gc
  ```
- **GC 선택**: JVM은 CPU 2개 이상이면서 메모리 1792MB 이상일 때만 G1을 기본으로 고른다. 그래서 임시 설정은 CPU 2개에서도 Serial이었다(`UseSerialGC = true {ergonomic}`). micro 설정은 `-XX:+UseG1GC`로 G1을 고정한다(지표에 `G1 Young Generation`·`G1 Old Generation`이 나오는 것으로 확인).

### 1.2 공통 조건

| 항목 | 값 |
|---|---|
| 비밀번호 해시 | Argon2id (메모리 19MiB, 반복 2, 병렬도 1) |
| Redis 명령 타임아웃 | 2초 (`spring.data.redis.timeout`) |
| k6 | 로컬 바이너리 v2.2.0(Windows), `BASE_URL=http://localhost:8080` |
| 계정 | `k6-buyer@loadtest.local` 하나 (`users.id` 1058) |
| postgres·redis | 로컬 개발 환경과 같은 컨테이너 |

- **계정 1개로 측정한 이유**: 로그인 경로에 회원 행 갱신, 회원당 세션 제한, 계정별 잠금, 회원 캐시가 없어 계정 수가 결과에 영향을 주지 않는다.

### 1.3 시나리오

| 이름 | k6 설정 | 내용 |
|---|---|---|
| 지속 실행 | `SHAPE=steady` (`constant-vus`, 30초) | VU N명이 30초 동안 쉬지 않고 "CSRF 발급 → 로그인"을 반복한다 |
| 일제히 실행 | `SHAPE=burst` (`per-vu-iterations`, 1회) | VU N명이 같은 순간에 로그인을 1번씩 한다(드롭 오픈 직전 상황) |
| 실패 로그인 | `MODE=fail` | 없는 이메일로 로그인한다. 401 `INVALID_CREDENTIALS`가 기대 응답이다 |

- VU 단계는 5 → 10 → 20 → 40 → 80이다(지속 실행은 VU 1도 실행). 한계 단계가 나오면 그 위 단계는 실행하지 않았다.
- 실패 로그인은 success의 한계 단계와 바로 아래 단계에서만 실행했다.
- 한계 단계와 바로 아래 단계는 한 번 더 실행해 재현을 확인했다([2.4절](#24-재현-확인)).

### 1.4 한계 단계 판정 기준

처음으로 아래 중 하나가 나온 단계를 한계 단계로 기록한다. 응답시간은 판정에 쓰지 않는다.

- 5xx 응답
- 응답 없음(타임아웃·연결 실패)
- 힙 `OutOfMemoryError`(backend 로그)
- 컨테이너 종료·OOM-kill
- 응답 불가: 컨테이너는 살아 있지만 `/actuator/health`가 응답하지 않는 상태(10-27에 추가)

### 1.5 측정 방법

- **실행 순서**: 단계 사이에 backend를 재시작하지 않았고, 실행 사이에 10초를 쉬었다. CPU2·Serial과 micro·G1은 시작 전에 backend를 새로 띄웠다. 예외로 micro·G1은 응답 불가가 된 뒤 재시작했고, 지속 VU 40 3회차는 재시작 직후에 실행했다.
- **GC 수치(Serial)**: `-Xlog:gc` 로그에서 셌다.
- **GC 수치(micro·G1)**: 저장소 설정에 `-Xlog:gc`가 없어, 설정을 바꾸지 않고 실행 전후 `/actuator/prometheus` 값의 차이로 셌다.
  - GC 횟수·정지 합계는 `jvm_gc_pause_seconds`, 1건당 할당은 `jvm_gc_memory_allocated_bytes_total`이다.
  - Full은 `G1 Old Generation`(`G1 Compaction Pause`) 횟수다.
  - JDK 17 지표에는 G1 Remark·Cleanup 정지가 없어 정지 합계에서 빠진다.
  - 측정 방법이 달라 Serial 조건의 GC 수치와 직접 비교하지 않는다.
- **5xx 원인**: backend 로그의 `ERROR` 줄과 그 아래 예외로 힙 OOM과 Redis 타임아웃을 나눴다.
- **CPU·메모리**: `docker stats`를 약 1~2초 간격으로 기록했다.

### 2.5 응답 불가

micro·G1 일제히 VU 80 2회차 도중, 힙 OOM으로 Tomcat Poller 스레드가 죽어 backend가 요청을 처리하지 못하게 됐다. Serial 조건에서는 나오지 않았다.

| 시각(KST) | 상태 |
|---|---|
| 09:48:00 무렵 | `Exception in thread "http-nio-8080-Poller" java.lang.OutOfMemoryError: Java heap space` |
| 09:48~09:51 | 컨테이너 `running`(`OOMKilled=false`), CPU 1% 미만. `/actuator/health`도 응답 없음(5초 타임아웃). 다음 k6 실행은 요청을 1건도 끝내지 못함 |
| 09:51 | backend 재시작 후 회복 |

- 재시작 전 스레드 목록에 Poller·Acceptor 스레드가 없었다.
- 컨테이너는 살아 있으므로 "컨테이너 종료" 기준으로는 잡히지 않는 실패다. 그래서 판정 기준에 "응답 불가"를 추가했다.
- 이 회차는 실행 후 GC 지표를 수집하지 못했다.

## 3. 원인 분석: Argon2의 힙 사용

가설은 "Argon2가 로그인 1건마다 힙을 약 19MiB 쓰고, 동시에 처리 중인 로그인이 늘면 힙이 찬다"였다. Serial 조건의 GC 로그(`-Xlog:gc`)로 확인했다. micro·G1은 GC 로그가 없어 이 분석에 넣지 않았지만, actuator 지표로 본 1건당 할당(19.8~20.6MiB)은 같았다.

### 계산 방법

- **로그인 1건당 할당량**: 두 GC 사이에 새로 할당된 양("이번 GC 직전 사용량 − 직전 GC 직후 사용량")을 모두 더해 할당 속도(MiB/초)를 구하고, 초당 로그인 수로 나눴다. CSRF 요청 등 다른 할당도 섞여 있다.
- **살아 있는 힙**: Full GC 직후 사용량이다. 그 순간 처리 중인 로그인의 Argon2 메모리가 여기에 들어간다.

### 결과 (지속 실행, success)

| VU | CPU1·Serial: 1건당 할당 | Full GC 직후 힙 중앙값 (최대) | CPU2·Serial: 1건당 할당 | Full GC 직후 힙 중앙값 (최대) |
|---|---|---|---|---|
| 1 | **20.5MiB** | 71MiB (86) | **20.5MiB** | 74MiB (84) |
| 5 | **20.5MiB** | 134MiB (159) | **20.4MiB** | 129MiB (165) |
| 10 | **20.4MiB** | 188MiB (240) | **20.4MiB** | 212MiB (255) |
| 20 | **20.6MiB** | 290MiB (356) | **20.6MiB** | 304MiB (387) |
| 40 | **20.5MiB** | 403MiB (**494**) | **20.6MiB** | 436MiB (**494**) |
| 80 | - | - | 19.9MiB | 475MiB (**494**) |

- CPU2·Serial VU 80의 1건당 할당이 조금 낮은 것은 실패 요청이 섞여서다.
- 494MiB는 힙이 실제로 확보한 최대 크기다(최대 512MiB 중).

### 해석

1. **로그인 1건당 힙 할당은 약 20.5MiB로 일정하다.** Argon2 메모리 19MiB(19,456KiB)에 객체 머리 정보와 요청 처리분이 더해진 값이다.
   - BouncyCastle 1.86 바이트코드(`Argon2BytesGenerator.allocateMemory`)를 확인했다. 해시를 시작할 때 `Block[19456]` 배열을 만들고 1KiB 블록(`long[128]`)을 하나씩 할당하며, 해시가 끝나면 `reset()`에서 참조를 놓는다. 즉 **해시 1건이 진행되는 동안 약 19MiB가 힙에 붙잡혀 있다.**
2. **동시 처리가 늘면 살아 있는 힙이 늘어 결국 한도에 닿는다.** Full GC 직후 힙은 VU 1에서 약 70MiB였고, VU 40에서는 400MiB를 넘어 최대값이 한도(494MiB)에 닿았다.
   - VU 1의 Full GC 직후 힙에는 처리 중인 해시가 최대 1건 들어 있으므로, 로그인과 무관한 평소 힙은 **약 50~60MiB**로 본다.
   - 그러면 힙에 동시에 들어갈 수 있는 해시는 약 (494 − 55) ÷ 20.5 ≈ **21건**이다. VU 20(CPU1·Serial)의 중앙값 290MiB는 처리 중인 해시 약 11건에 해당한다. VU 수보다 적은 것은 나머지 VU가 그 순간 CSRF 요청, 네트워크, 스레드 대기 중이었기 때문으로 본다.
3. **힙이 차면 GC가 시간을 잡아먹어 처리량이 떨어진다.** 한계 단계에서는 GC 대부분이 Full GC였고(CPU1·Serial VU 40에서 78회 중 65회), 30초 중 절반 넘게 멈춰 있었다. 이 상태에서 요청이 두 가지로 실패했다.
   - **Redis 타임아웃**: 로그인 성공 뒤 세션을 저장하는 Redis 명령(`evalSha`)이 2초 타임아웃에 걸렸다(`QueryTimeoutException`). Redis 서버보다는 GC로 멈춘 backend가 응답을 제때 처리하지 못한 것으로 본다(추정).
   - **힙 OOM**: Argon2 블록을 할당하다 `OutOfMemoryError: Java heap space`가 났다. 대부분은 JVM이 죽지 않고 그 요청만 500으로 끝났다. 다만 OOM이 Tomcat 내부 스레드에서 나면 서버 전체가 멈출 수 있다(2.5절).
   - 두 실패는 겉모습은 다르지만 같은 힙 포화 상태에서 나왔다. 어느 쪽이 먼저 나는지는 회차마다 달랐다.
4. **OOM이 나지 않은 단계도 안전하다는 뜻은 아니다.** CPU1·Serial 일제히 80명에서는 `OutOfMemoryError`가 없었지만, Full GC 직후 힙이 한도에 붙는 순간(`494M->494M`)이 있었다. 블록을 1KiB씩 할당하므로 GC가 끝난 해시의 블록을 회수하며 버틴 것으로 보인다. 같은 단계가 CPU2·Serial에서는 실패했다.

## 4. 개선 방향 (구현하지 않음)

이번 이슈에서는 정리만 하고, 진행할 항목은 별도 이슈로 다룬다. 개선 효과는 micro·G1 결과를 기준선으로, 같은 설정과 같은 단계로 다시 측정해 비교한다.

| 순서 | 방향 | 막는 문제 | 근거 |
|---|---|---|---|
| 1 | 로그인 동시 처리 수 제한 | 힙 OOM, GC 폭주, 처리량 저하, 응답 불가 | 동시 해시 수가 힙 천장을 넘으면 실패. 처리량은 동시 처리 수가 CPU 수 근처일 때 최대 |
| 2 | 로그인 시도 제한(레이트리밋) | 틀린 비밀번호 반복 요청 | 실패 로그인만으로 힙 OOM과 5xx 발생 |
| 3 | Argon2 파라미터 조정 | 로그인 1건당 힙 사용 | 힙 사용이 메모리 파라미터(19MiB)에 비례. 단, 보안 기준과 충돌 |
| 4 | 운영 메모리 설정 점검 | 운영 OOM 위험 | 힙 밖 메모리만 약 300MiB, 운영에 `-Xmx`·메모리 제한 없음 |
| 5 | 부하테스트 환경 정리 | 측정 환경 왜곡 | nano 설정은 로그인 1명 부하에서도 OOM-kill |

### 1. 로그인 동시 처리 수 제한

- **방법**: Argon2 검증을 동시에 N건까지만 실행한다(예: 세마포어). 넘치는 요청은 짧게 기다리게 하거나 503/429와 `Retry-After`로 거절한다.
- **기대 효과**: 힙 OOM과 GC 폭주를 막고, 처리량과 응답시간을 일정하게 유지한다. CPU를 늘려도 힙 천장은 그대로였으므로(2.6절), 서버를 키우는 것만으로는 해결되지 않는다.
- **정할 것**: N 값(CPU 수와 힙 여유로 정하고 측정으로 확인), 기다릴지 바로 거절할지, 거절 응답 코드와 프론트엔드 처리. 인스턴스마다 따로 적용된다.

### 2. 로그인 시도 제한 (레이트리밋)

- **방법**: IP 단위, 계정(이메일) 단위로 일정 시간 안의 시도 횟수를 제한한다. 비슷한 선례로 재고 SSE의 IP 요청 제한(REALTIME_STOCK.md 12절)이 있다.
- **1번과의 관계**: 1번은 서버를 지키고, 2번은 특정 출처의 반복 시도를 막는다. 2번만으로는 여러 IP에서 오는 정상 폭주를 막지 못한다.
- **정할 것**: 제한 수치, 저장 위치(인스턴스 메모리 또는 Redis), 초과 시 응답, 계정 단위 제한이 계정 존재 여부를 드러내지 않게 하는 방법.

### 3. Argon2 파라미터 조정

- **주의**: 현재 값은 `SecurityConfig` 주석에 "OWASP 최소 권장값"으로 적혀 있고, NFR-001(Argon2id)의 근거다. 메모리만 낮추면 보안 기준을 어기게 된다.
- **참고**: OWASP 권장표에는 메모리를 줄이고 반복 횟수를 늘린 동등 설정들이 있는 것으로 안다(예: 12MiB·3회, 9MiB·4회, 7MiB·5회). 확인하지 않았다. 이 경우 힙 사용은 줄지만 로그인 1건당 CPU 시간이 늘어난다.
- **정할 것**: 요구사항·보안 문서 수정 여부를 먼저 정해야 한다. 기존 해시는 저장된 파라미터로 검증되므로, 바꿔도 기존 회원 로그인은 유지된다.

### 4. 운영 메모리 설정 점검

- 저장소의 운영 설정(`deploy/compose.prod.yaml`, `Dockerfile`)에는 `-Xmx`와 컨테이너 메모리 제한이 없다. 그래서 힙 최대는 JVM 기본값(RAM의 1/4, 2GB에서 약 512MiB)이 된다. blue/green 배포 중에는 backend 2개가 같은 서버에서 함께 뜰 수 있다.
- **할 일**: 서버 `deploy/.env`에 JVM 옵션이 있는지 확인한다. 배포 중 두 JVM이 함께 떴을 때 메모리 여유가 있는지 확인한다. 이번 측정에서는 운영 서버를 보지 않았다.

### 5. 부하테스트 환경 정리

- main의 GR-149 수정(#177)에서 nano 설정(당시 `compose.loadtest.yaml`)에 `memswap_limit: 512m`이 추가돼 스왑이 꺼졌다. #177에서 다른 시나리오를 다시 검증했고, drop-open-spike가 OOM-kill됐다(커밋 메시지 기준).
- 이 측정 결과(nano 무스왑에서는 로그인 1명 부하로도 OOM-kill, 힙 밖 메모리 약 300MiB)를 GR-149 담당자와 공유해, nano 설정을 계속 쓸지 함께 정한다.

### 그 밖의 관찰

- Redis 타임아웃으로 500이 난 로그인 요청도 Redis에는 세션이 저장됐다([부록 A](#부록-a-redis-세션-증가와-정리)). 클라이언트가 받지 못한 세션은 TTL(14일)이 지나면 사라진다. 영향이 작아 기록만 한다.

## 5. 측정 환경의 한계

- **하한선 검증이다.** 운영보다 약한 조건에서 무너지는 지점을 본 것이다.
- **로컬 PC 한 대에서 측정했다.** k6, backend, postgres, redis가 같은 PC의 CPU를 나눠 썼고, 네트워크 지연은 거의 없다. 로컬 개발용 postgres·redis를 함께 썼고, 측정 중 다른 요청은 없었다고 보지만 확인하지 않았다.
- **CPU 조건이 실제 EC2와 다르다.** 알려진 바로는 t3 계열은 vCPU 2개에 크레딧 기반 버스트 방식이라, 크레딧을 다 쓰면 기준 성능으로 떨어진다. 이를 확인하거나 재현하지 않았다.
- **GC·힙이 운영과 다를 수 있다.** 운영(2 vCPU/2GB)은 G1에 힙 기본값 약 512MiB가 쓰일 것으로 보지만 확인하지 않았다. micro·G1은 힙이 550MiB다.
- **Serial 조건은 저장소에 없는 임시 설정이다.** micro·G1만 저장소 설정 그대로다.
- **단계 사이에 backend를 재시작하지 않았다.** 앞 실행에서 늘어난 힙과 컨테이너 메모리가 다음 실행에 이어졌다. micro·G1 지속 VU 40 3회차만 재시작 직후(JIT 예열 전)라 다른 회차와 조건이 다르다.
- **반복 횟수가 적다.** 한계 단계와 바로 아래 단계만 2회(micro·G1 지속 VU 40은 3회) 실행했고, 나머지 단계와 실패 로그인은 1회씩이다.
- **계정 1개로 측정했다.** 계정별 잠금, 세션 제한, 로그인 시 회원 행 갱신이 생기면 다시 검토해야 한다.
- **메모리 분석은 GC 로그와 actuator 지표로만 했다.** backend 이미지가 JRE라 `jcmd`가 없어, 영역별 네이티브 메모리(NMT)는 재지 않았다.
- **Grafana(Prometheus 15초 수집)는 근거로 쓰지 않았다.** 30초 실행에는 해상도가 부족하다.

## 부록 B. nano 예비 측정과 환경 변경 경위

10-26 본 측정 전에, 당시 저장소 설정 그대로 nano 환경에서 측정했다: `mem_limit 512m`, `-Xmx384m -Xlog:gc`, `cpus 1`, `memswap_limit` 지정 없음. 이후 main의 GR-149 수정(#177)에서 `memswap_limit: 512m`이 추가돼, 지금의 저장소 nano 설정은 아래 "스왑을 막은 확인 실행"과 같은 조건이다.

| 시각 | 실행 | 결과 |
|---|---|---|
| 11:47 | 스모크 (VU 1, 10초) | 128회 모두 성공, 평균 74ms, 12.8회/초 |
| 12:04 | 지속 실행 VU 5 | 200회 모두 성공했지만 평균 680ms, 최대 5.9초, 6.6회/초. GC 정지 합계 15.9초, 최대 **4.67초** |
| 12:09 | 스왑을 막고 VU 1 | 약 13초(로그인 181회) 만에 **컨테이너 OOM-kill** |
| 12:48 | 임시 설정(1GiB, `-Xmx512m`)으로 VU 1 | 30초 동안 522회 모두 성공 |

### 스왑에 가려진 문제 (12:04)

VU 5에서 4초대 GC 정지 동안 CPU가 15~20%로 낮았다. 측정 직후 cgroup을 확인하니 **컨테이너가 스왑을 쓰고 있었다**: `memory.current` 512MiB(한도), `memory.swap.current` 253MiB, `memory.events max` 5,956, `pgmajfault` 127,069.

Compose는 `memswap_limit`을 지정하지 않으면 메모리 한도의 2배를 메모리+스왑 한도로 잡는다(`MemorySwap` 1GiB). 그래서 512MiB를 넘은 JVM 메모리가 OOM-kill되지 않고 스왑으로 밀려났고, 4초대 GC 정지는 스왑된 힙을 다시 읽느라 생긴 것으로 본다.

### 스왑을 막은 확인 실행 (12:09)

`memswap_limit: 512m`을 임시로 넣어 backend만 다시 띄웠다.

- 대기 상태에서 이미 456MiB/512MiB(cgroup `anon` 403MiB)였다.
- VU 1 지속 실행 약 13초 뒤 **컨테이너가 OOM-kill됐다**(`exited`, `OOMKilled=true`, `ExitCode=137`). backend 로그에 `OutOfMemoryError`는 없었다.
- 마지막 GC 줄은 `179M->137M(199M)`이다. 힙은 한도 384MiB의 절반 정도였으므로, 512MiB를 넘긴 것은 **힙 밖 메모리**다.

### 힙 밖 메모리 (12:48, 임시 설정)

임시 설정(1GiB)으로 같은 시험을 하고, 부하가 끝난 뒤 JVM이 보고한 확보량(`/actuator/prometheus`)을 확인했다.

| 영역 | 확보량 |
|---|---|
| 힙 (Eden 57.5 + Survivor 7.1 + Tenured 143.3) | 207.9MiB |
| 메타스페이스 | 136.4MiB |
| 코드 캐시 (2.4 + 8.1 + 29.1) | 39.6MiB |
| 압축 클래스 공간 | 18.8MiB |
| 다이렉트 버퍼 | 1.3MiB |
| 스레드 | 45개 (스택은 이 지표에 없음) |
| **합계(스택 제외)** | **약 404MiB** |

- cgroup `anon` 514MiB와의 차이 약 110MiB는 스레드 스택, GC·JIT 내부 자료구조, `malloc` 등 이 지표에 없는 네이티브 메모리다. 영역별로 측정(NMT)하지는 않았다.
- 메모리는 약 20초 동안 500MiB에서 586MiB로 오른 뒤 멈췄고, 부하가 끝난 뒤 1분 동안 `anon`은 513~514MiB로 변화가 없었다.

### 정리

- 이 애플리케이션은 **힙 밖에서만 약 300MiB**를 쓴다(메타스페이스·코드 캐시·압축 클래스 공간 약 195MiB + 보이지 않는 네이티브 메모리 약 110MiB). nano 설정은 힙 384MiB에 이 값을 더하면 512MiB를 넘으므로, 스왑이 있어야만 버틴다.
- 메모리는 부하 초반에 올라 일정 수준에서 멈췄고 부하 뒤에도 늘지 않았다(30초 범위). 그래서 nano 무스왑 OOM-kill은 누수라기보다 필요한 메모리가 512MiB보다 크기 때문으로 본다. 더 긴 시간의 누적 여부는 확인하지 않았다.
- 같은 nano 설정으로 측정한 다른 시나리오(GR-151·152)의 "서버 다운 없음"도 스왑 덕분이었을 수 있었다. 이 부분은 #177에서 스왑을 막고 다시 검증됐다.
- 작업자 결정으로 GR-161 본 측정은 1GiB 기준(임시 설정)으로 처음부터 다시 했다.
