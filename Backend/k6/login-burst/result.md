# 로그인 동시 폭주 결과 (GR-161)

> 이 결과는 **운영 캐파시티 수치가 아니라 하한선 검증**이다. 운영(t3.small, 2GB)보다 약한
> t3.micro(1GiB) 메모리 기준 제한 환경에서, 로그인이 동시에 몰릴 때 어느 VU 단계부터 무너지는지를 본다.
> 공식 목표(NFR-006)가 없어 합격·불합격은 판정하지 않고, 한계 단계와 관찰값만 기록한다.
> 실행 방법은 [login-burst.js](login-burst.js) 상단 주석을 따른다.
> 처음에는 저장소의 nano 설정(512MiB)으로 측정했으나, 측정 환경 문제가 드러나 micro 기준으로 다시 측정했다. 경위는 [부록](#부록-nano-예비-측정과-환경-변경-경위)에 있다.

## 요약

- **한계 단계**
  - 지속 실행(30초 동안 계속 로그인): **VU 40**. 2회 모두 5xx가 났다(Redis 타임아웃 1건, 힙 `OutOfMemoryError` 2건). VU 20은 2회 모두 5xx 없이 끝났다.
  - 일제히 실행(VU마다 1회): 계획한 VU 80까지 **한계 없음**. 다만 마지막 응답은 약 9초 걸렸다.
  - 실패 로그인(없는 계정)도 **VU 40**에서 5xx(힙 `OutOfMemoryError`)가 났다.
- **원인은 Argon2의 힙 사용이다.** 로그인 1건당 힙 할당은 VU와 관계없이 약 20.5MiB로 일정하다. 힙(512MiB)에 동시에 들어가는 해시는 약 21건이다. 동시 처리량이 이를 넘으면 Full GC가 반복되고(VU 40에서 30초 중 15.8~18.9초 정지), 처리량이 줄며(17.4 → 8.5회/초), 결국 Redis 타임아웃이나 힙 OOM으로 요청이 실패한다.
- **동시 처리 수를 늘려도 처리량은 늘지 않는다.** CPU 1개에서는 VU 1(동시 1건)일 때 처리량이 가장 높았다.
- **틀린 비밀번호도 같은 비용이 든다.** 없는 계정도 더미 해시로 Argon2를 실행하고 로그인 시도 제한도 없다. 그래서 실패 로그인 40개를 동시에 보내는 것만으로 이 환경에 힙 OOM과 5xx를 낼 수 있었다.
- **측정 환경 자체의 문제도 드러났다.** 저장소의 nano 설정(512MiB, `-Xmx384m`)은 힙 밖 메모리만 약 300MiB라서 스왑 없이는 로그인 1명 부하에서도 OOM-kill됐다. 그래서 micro 기준(1GiB, 스왑 없음, `-Xmx512m`) 임시 설정으로 측정했다.

## 환경

- `docker compose -f compose.yaml -f compose.loadtest.yaml -f <임시 오버라이드> up -d backend`
  - 저장소 `compose.loadtest.yaml`(nano 설정)은 바꾸지 않았다. 아래 임시 오버라이드 파일을 저장소 밖에 만들어 세 번째 `-f`로 얹었다(작업자 결정: micro 설정은 저장소에 넣지 않고 임시 설정으로 쓴다). 만드는 방법은 [login-burst.js](login-burst.js) 상단 주석에 있다.
    ```yaml
    services:
      backend:
        mem_limit: 1g
        memswap_limit: 1g        # 스왑 없음
        environment:
          JDK_JAVA_OPTIONS: -Xmx512m -Xlog:gc
    ```
  - backend: CPU 1개(`compose.loadtest.yaml` 그대로), 메모리 1GiB, 스왑 없음, 힙 최대 512MiB.
  - JVM이 고른 GC는 **Serial**이다(`[gc] Using Serial`). CPU가 2개 미만이면 JVM은 G1 대신 Serial을 쓴다. 운영(2 vCPU/2GB)은 G1이 쓰일 것으로 보지만 확인하지 않았다.
  - postgres·redis는 로컬 개발 환경과 같은 컨테이너를 쓴다.
- k6: 로컬 바이너리 v2.2.0(Windows), `BASE_URL=http://localhost:8080`. k6도 같은 PC에서 돌아 CPU를 나눠 쓴다.
- 계정: `k6-buyer@loadtest.local`(`users.id` 1058) 하나. 로그인 경로에 회원 행 갱신·회원당 세션 제한·계정별 잠금·회원 캐시가 없어 계정 수가 결과에 영향을 주지 않는다.
- 비밀번호 해시: Argon2id(메모리 19MiB, 반복 2, 병렬도 1). 없는 계정도 더미 해시로 같은 검증을 한다.
- Redis 명령 타임아웃: `spring.data.redis.timeout: 2s`.
- 단계 사이에 backend를 재시작하지 않았다. 실행 사이에는 10초를 쉬었다.
- 실행일: 2026-10-26(지속 실행 14:04~14:08 KST, 일제히 실행 14:09~14:14 KST)

### 한계 단계 판정 기준

처음으로 아래 중 하나가 나온 단계를 한계 단계로 적는다. 응답시간은 판정에 쓰지 않고 기록만 한다.

- 5xx 응답(`login_server_error_total`)
- 응답 없음: 타임아웃·연결 실패(`login_no_response_total`)
- 힙 `OutOfMemoryError`(backend 로그)
- 컨테이너 종료·OOM-kill(`docker inspect`의 `Status`·`OOMKilled`)

- **실패 로그인도 성공 로그인과 거의 같은 지점에서 무너진다.** 처리량·응답시간·GC 부담이 비슷하고, VU 40에서 똑같이 5xx가 났다. 로그인 1건당 힙 할당도 20.2~20.4MiB로 success(20.5MiB)와 같다. 없는 계정도 더미 해시로 Argon2를 실행하기 때문이다.
- 로그인 비용은 거의 Argon2다. 실패 모드에는 `sellers` 조회, JWT 발급, Redis 세션 저장이 없지만 처리량 차이가 거의 없다.
- **VU 40의 5xx는 힙 `OutOfMemoryError`였다**(14:25:59, `Java heap space`). 이번 측정에서 처음 나온 힙 OOM이다.
  - 위치: `UserCredentialService.authenticate` → `Argon2PasswordEncoder.matches` → `Argon2BytesGenerator.allocateMemory` → `Block.<init>`. 해시용 블록을 할당하다가 힙이 모자랐다.
  - 직전 GC: `494M->494M`, `494M->489M` 같은 Full GC가 이어졌다. 힙이 진행 중인 해시로 가득 찬 상태였다.
  - JVM은 죽지 않았다. 그 요청만 500으로 끝났고, 이후 health는 200이다. 컨테이너도 running이다.
  - success VU 40의 5xx(Redis 타임아웃)와 원인은 다르지만, 둘 다 같은 힙 포화 상태에서 나왔다. 어느 지점에서 먼저 실패하는지는 그때그때 다를 수 있다.
- Redis 키 수는 실행 전후 5,078개로 같다. 실패 로그인은 세션을 만들지 않는다. backend 로그에는 실패마다 WARN이 1줄씩 남았다(VU 40에서 `INVALID_CREDENTIALS` 272줄).
- **의미**: 로그인 시도 제한(레이트리밋)이 없으므로, 틀린 비밀번호를 보내는 쪽(무차별 대입, 크리덴셜 스터핑)도 정상 사용자와 같은 비용을 서버에 지운다. 이 환경에서는 동시에 40개 정도의 실패 로그인 요청만으로 힙 OOM과 5xx가 났다. 그동안 정상 사용자의 로그인도 같은 대기열에서 수 초씩 기다리게 된다(정상·공격 혼합 실행은 하지 않았다).

## Argon2 메모리 분석 (M02-03)

가설: Argon2가 로그인 1건마다 힙을 약 19MiB 쓰고, 동시에 처리 중인 로그인이 늘면 힙이 찬다.
위 측정의 GC 로그(`-Xlog:gc`)로 확인했다. 따로 측정을 더 하지는 않았다.

### 계산 방법

- **로그인 1건당 할당량**: 두 GC 사이에 새로 할당된 양은 "이번 GC 직전 사용량 − 직전 GC 직후 사용량"이다. 첫 GC부터 마지막 GC까지 합해 할당 속도(MiB/초)를 구하고, k6의 초당 로그인 수로 나눴다. CSRF 요청 등 다른 할당도 섞여 있다.
- **살아 있는 힙**: Full GC 직후 사용량은 그 순간 살아 있는 객체의 양이다. 처리 중인 로그인의 Argon2 메모리가 여기에 들어간다.

### 결과 (지속 실행)

| VU | 할당 속도 | 초당 로그인 | **로그인 1건당 할당** | Full GC 직후 힙(최소 / 중앙 / 최대) | GC 직전 힙 최대 |
|---|---|---|---|---|---|
| 1 | 356.5MiB/s | 17.4 | **20.5MiB** | 59 / 71 / 86MiB | 207MiB |
| 5 | 249.2MiB/s | 12.2 | **20.5MiB** | 91 / 134 / 159MiB | 358MiB |
| 10 | 235.8MiB/s | 11.5 | **20.4MiB** | 114 / 188 / 240MiB | 473MiB |
| 20 | 217.5MiB/s | 10.6 | **20.6MiB** | 155 / 290 / 356MiB | 494MiB |
| 40 | 174.1MiB/s | 8.5 | **20.5MiB** | 141 / 403 / 494MiB | 494MiB |

일제히 실행(VU 20·40·80)도 로그인 1건당 20.7~22.5MiB로 같은 수준이었다. GC 횟수가 5~24회뿐이라 오차가 더 크다.

### 해석

1. **로그인 1건당 힙 할당은 VU와 관계없이 약 20.5MiB로 일정하다.** Argon2 메모리 19MiB(19,456KiB)에 블록 객체 머리 정보 등 부가분이 더해지고, 나머지 요청 처리분이 붙은 값으로 본다. 추정이 실측으로 확인됐다.
   - BouncyCastle 1.86 바이트코드(`Argon2BytesGenerator.allocateMemory`) 확인 결과, 해시 시작 시 `Block[19456]` 배열을 만들고 1KiB 블록(`long[128]`)을 하나씩 할당한다. 해시가 끝나면 `reset()`이 참조를 놓는다. 즉 **해시 1건이 진행되는 동안 약 19MiB가 힙에 붙잡혀 있다.**
2. **동시 처리량이 늘면 살아 있는 힙이 늘어 결국 한도에 닿는다.** Full GC 직후 힙의 중앙값은 VU 1에서 71MiB였고, VU 20에서 290MiB, VU 40에서 403MiB로 늘었다. VU 40에서는 최대값이 494MiB로 힙 확보 한도에 닿았다.
   - VU 1의 Full GC 직후 힙(약 60~70MiB)에는 처리 중인 해시가 최대 1건 들어 있다. 그래서 로그인과 무관한 평소 힙은 **약 50~60MiB**로 본다. 체크리스트와 Linear에 처음 적은 "약 140MiB"는 nano 측정 때의 값을 잘못 옮긴 추정이었다.
   - 이 기준이면 힙(494MiB 확보)에 동시에 들어갈 수 있는 해시는 약 (494 − 55) ÷ 20.5 ≈ **21건**이다. VU 20의 중앙값 290MiB는 처리 중인 해시 약 11건, VU 40의 중앙값 403MiB는 약 17건에 해당한다. VU 수보다 적은 것은 나머지 VU가 그 순간 CSRF 요청, 네트워크, 스레드 대기 중이었기 때문으로 본다.
3. **힙이 차면 GC가 처리 시간을 잡아먹어 처리량이 떨어진다.** 지속 실행의 초당 로그인은 17.4회(VU 1)에서 8.5회(VU 40)로 줄었다. VU 40에서는 GC 78회 중 65회가 Full GC였고, 30초 중 15.8초가 정지였다. 같은 구간에서 Redis 2초 타임아웃으로 5xx가 났다(1절). 힙 포화 → Full GC 반복 → 요청 처리 지연이라는 흐름이 측정값과 맞는다.
4. **80명 일제히 실행에서도 `OutOfMemoryError`가 나지 않았다.** 로그상 64개 요청 스레드가 로그인을 처리했고, Full GC 직후 힙이 494MiB로 한도에 붙는 순간도 있었다(`494M->494M`). 블록을 1KiB씩 할당하므로, 할당이 막히면 GC가 끝난 해시의 블록을 회수해 조금씩 진행한 것으로 보인다. 다만 진행 중인 해시만으로 힙이 가득 차면 `OutOfMemoryError`가 날 수 있다. 이번 단계에서는 나지 않았을 뿐, 안전하다는 근거는 아니다.

### 그 밖의 관찰

- 응답시간은 VU 수에 거의 비례해 늘었다. CPU 1개가 Argon2를 나눠 처리하므로, 동시 요청이 많을수록 각 요청이 오래 걸린다.
- GC는 Serial(CPU 1개 조건)이다. 운영에서 G1이 쓰이면 GC 정지 양상이 다를 수 있다.

## 측정 환경의 한계

이 결과를 읽을 때 아래를 함께 봐야 한다.

- **하한선 검증이다.** 운영(t3.small, 2GB)보다 약한 조건에서 무너지는 지점을 본 것이다. 응답시간·처리량·한계 VU를 운영 캐파시티로 쓰지 않는다.
- **로컬 PC 한 대에서 측정했다.** k6와 backend, postgres, redis가 같은 PC의 CPU를 나눠 썼다. 네트워크 지연도 거의 없다.
- **CPU 조건이 실제 EC2와 다르다.** `cpus: 1`로 CPU 1개를 줬다. 알려진 바로는 t3 계열은 vCPU 2개에 크레딧 기반 버스트 방식인데, 이번에는 확인하지 않았다. CPU 1개 조건이라 JVM이 Serial GC를 골랐다. 운영(2 vCPU/2GB)은 G1이 쓰일 것으로 보며, GC 정지 양상이 다를 수 있다.
- **micro 설정은 저장소에 없는 임시 설정이다.** 저장소 `compose.loadtest.yaml`만으로 실행하면 nano 설정이 되어 결과가 달라진다(부록).
- **스왑이 없는 조건이다.** 실제 EC2처럼 메모리가 넘치면 OOM-kill되는 조건으로 맞췄다. nano 예비 측정은 스왑이 켜진 상태였다.
- **단계 사이에 backend를 재시작하지 않았다.** 앞 실행에서 늘어난 힙과 컨테이너 메모리가 다음 실행에 이어졌다. 그래서 일제히 실행의 메모리는 900MiB대에서 시작한다.
- **반복 횟수가 적다.** 한계 단계(VU 40)와 바로 아래 단계(VU 20)만 2회 실행했다. 나머지 단계는 1회씩이다.
- **계정 1개로 측정했다.** 지금 로그인 경로에는 회원 행 갱신, 회원당 세션 제한, 계정별 잠금, 회원 캐시가 없어 계정 수가 결과에 영향을 주지 않는다. 이 중 하나라도 생기면 다시 검토해야 한다.
- **메모리 분석은 GC 로그와 actuator 지표로만 했다.** backend 이미지가 JRE라 `jcmd`가 없어, 영역별 네이티브 메모리(NMT)는 재지 않았다. "로그인 1건당 20.5MiB"는 GC 사이 할당량을 초당 로그인 수로 나눈 값이라 CSRF 요청 등 다른 할당도 섞여 있다.
- **Grafana(Prometheus 15초 수집)는 근거로 쓰지 않았다.** 30초 실행에서는 해상도가 부족해서다. CPU·메모리는 `docker stats`(약 1~2초 간격), 힙은 GC 로그를 썼다.
- **로컬 개발용 postgres·redis를 함께 썼다.** 측정 중 다른 요청은 없었다고 보지만 확인하지는 않았다.

## 개선 방향 (구현하지 않음)

측정에서 드러난 문제에 대한 대응 후보다. 이번 이슈에서는 정리만 하고, 진행할 항목은 별도 이슈로 다룬다.

### 1. 로그인 동시 처리 수 제한

- **근거**: 처리량은 동시 1건일 때 가장 높았고(17.4회/초), 동시 처리가 늘수록 GC 때문에 줄었다(VU 40에서 8.5회/초). 힙에 동시에 들어가는 해시는 약 21건이고, 이를 넘으면 OOM이 난다.
- **방법**: Argon2 검증을 동시에 N건까지만 실행한다(예: 세마포어). 넘치는 요청은 짧게 기다리게 하거나 503/429와 `Retry-After`로 거절한다.
- **기대 효과**: 힙 OOM과 GC 폭주를 막고, 처리량과 응답시간을 일정하게 유지한다.
- **정할 것**: N 값(CPU 수와 힙 여유로 정하고 측정으로 확인), 기다릴지 바로 거절할지, 거절 시 응답 코드와 프론트엔드 처리 방식. 인스턴스마다 따로 적용된다.

### 2. 로그인 시도 제한 (레이트리밋)

- **근거**: 실패 로그인도 성공 로그인과 같은 비용(로그인 1건당 힙 약 20MiB)이 든다. 실패 로그인 40개를 동시에 보내는 것만으로 힙 OOM과 5xx가 났다(3절). 지금은 로그인 시도 제한이 없다.
- **방법**: IP 단위, 계정(이메일) 단위로 일정 시간 안의 시도 횟수를 제한한다. 비슷한 선례로 재고 SSE의 IP 요청 제한(REALTIME_STOCK.md 12절)이 있다.
- **1번과의 관계**: 1번은 서버를 지키고, 2번은 특정 출처의 반복 시도를 막는다. 2번만으로는 여러 IP에서 오는 정상 폭주를 막지 못한다.
- **정할 것**: 제한 수치, 저장 위치(인스턴스 메모리 또는 Redis), 초과 시 응답, 계정 단위 제한이 계정 존재 여부를 드러내지 않게 하는 방법.

### 3. Argon2 파라미터 조정

- **근거**: 힙 사용량은 Argon2 메모리 파라미터(19MiB)에 정비례한다.
- **주의**: 현재 값은 `SecurityConfig` 주석에 "OWASP 최소 권장값"으로 적혀 있고, NFR-001(Argon2id)의 근거다. 메모리만 낮추면 보안 기준을 어기게 된다.
- **참고**: OWASP 권장표에는 메모리를 줄이고 반복 횟수를 늘린 동등 설정들이 함께 있는 것으로 안다(예: 12MiB·3회, 9MiB·4회, 7MiB·5회). 이번에는 확인하지 않았다. 이 경우 힙 사용은 줄지만 로그인 1건당 CPU 시간은 늘어난다.
- **정할 것**: 고르려면 요구사항·보안 문서 수정 여부를 먼저 정해야 한다. 기존 해시는 저장된 파라미터로 검증되므로 바꿔도 기존 회원 로그인은 유지된다.

### 4. 운영 메모리 설정 점검

- **근거**: 이 애플리케이션은 힙 밖에서만 약 300MiB를 쓴다(부록). 저장소의 운영 설정(`deploy/compose.prod.yaml`, `Dockerfile`)에는 `-Xmx`와 컨테이너 메모리 제한이 없다. 그래서 힙 최대는 JVM 기본값(RAM의 1/4, 2GB에서 약 512MiB)이 된다. 또 blue/green 배포 중에는 backend 2개가 같은 서버에서 함께 뜰 수 있다.
- **할 일**: 서버 `deploy/.env`에 JVM 옵션이 있는지 확인한다. 배포 중 두 JVM이 함께 떴을 때 메모리 여유가 있는지 확인한다. 이번 측정에서는 운영 서버를 보지 않았다.

### 5. 부하테스트 환경 정리

- 저장소 nano 설정은 스왑 없이는 로그인 부하를 버티지 못한다(부록). 측정 뒤 main에 들어온 GR-149 수정(#177)에서 `compose.loadtest.yaml`에 `memswap_limit: 512m`이 추가돼 저장소 nano 설정도 스왑이 꺼졌다. #177에서 다른 시나리오를 다시 검증했고, drop-open-spike가 OOM-kill됐다(커밋 메시지 기준). 이 결과(nano 무스왑에서는 로그인 1명 부하로도 OOM-kill, 힙 밖 메모리 약 300MiB)를 GR-149 담당자와 공유해, nano 설정을 계속 쓸지 함께 정한다.
- micro 설정을 저장소에 넣을지는 이번에 정하지 않고 임시 설정으로 두었다.

### 6. 그 밖의 관찰

- Redis 타임아웃으로 500이 난 로그인 요청도 Redis에는 세션이 저장됐다(1절). 클라이언트가 받지 못한 세션은 TTL(14일)이 지나면 사라진다. 영향은 작아 기록만 한다.

## 부록: nano 예비 측정과 환경 변경 경위

처음에는 당시 저장소 설정 그대로 nano 환경에서 측정했다: `mem_limit 512m`, `-Xmx384m -Xlog:gc`, `cpus 1`, `memswap_limit` 지정 없음. 이후 main의 GR-149 수정(#177)에서 `memswap_limit: 512m`이 추가돼, 지금의 저장소 nano 설정은 아래 "스왑을 막은 확인 실행"과 같은 조건이다.

### 스모크 (2026-10-26 11:47, VU 1, 10초)

128회 모두 성공, 평균 73.6ms, p95 187ms, 최대 588ms, 12.8회/초. 10초 동안 GC 약 62회, `Pause Full` 1회(114ms).

### 지속 실행 VU 5 (12:04:35)

200회 모두 성공했지만 평균 680ms, p95 1,671ms, 최대 5,926ms였고 처리량은 6.6회/초로 스모크보다 낮았다. GC 62회 중 Full 18회, 정지 합계 15.9초, 최대 4.67초였다. 4초대 정지 동안 CPU는 15~20%로 낮았다.

측정 직후 cgroup을 확인하니 **컨테이너가 스왑을 쓰고 있었다**: `memory.current` 512MiB(한도), `memory.swap.current` 253MiB, `memory.events max` 5,956, `pgmajfault` 127,069. Compose는 `memswap_limit`을 지정하지 않으면 메모리 한도의 2배를 메모리+스왑 한도로 잡는다(`MemorySwap` 1GiB). 그래서 512MiB를 넘은 JVM 메모리가 OOM-kill되지 않고 스왑으로 밀려났다. 4초대 GC 정지는 스왑된 힙을 다시 읽느라 생긴 것으로 본다.

### 스왑을 막은 확인 실행 (12:09~12:10)

임시 오버라이드 `memswap_limit: 512m`으로 backend만 다시 띄웠다.

- 대기 상태에서 이미 456MiB/512MiB(cgroup `anon` 403MiB)였다.
- VU 1 지속 실행 시작 약 13초 뒤, 로그인 181회 성공 후 **컨테이너가 OOM-kill됐다**(`exited`, `OOMKilled=true`, `ExitCode=137`). backend 로그에 `OutOfMemoryError`는 없었다.
- 마지막 GC 줄은 `179M->137M(199M)`이다. 힙은 한도 384MiB의 절반 정도였으므로, 512MiB를 넘긴 것은 힙 밖 메모리다.

### micro 기준 확인 (12:48~12:51)

위 환경 절의 오버라이드로 같은 시험(스왑 없음, VU 1, 30초)을 다시 했다. 522회 모두 성공했다(1절 VU 1 행).

- 메모리는 약 20초 동안 500MiB에서 586MiB로 오른 뒤 멈췄다. 부하가 끝난 뒤 1분 동안 cgroup `anon`은 513~514MiB로 변화가 없었다.
- 부하 뒤 JVM이 보고한 확보량(`/actuator/prometheus`):

  | 영역 | 확보량 |
  |---|---|
  | 힙 (Eden 57.5 + Survivor 7.1 + Tenured 143.3) | 207.9MiB |
  | 메타스페이스 | 136.4MiB |
  | 코드 캐시 (2.4 + 8.1 + 29.1) | 39.6MiB |
  | 압축 클래스 공간 | 18.8MiB |
  | 다이렉트 버퍼 | 1.3MiB |
  | 스레드 | 45개 (스택은 이 지표에 없음) |
  | **합계(스택 제외)** | **약 404MiB** |

  cgroup `anon` 514MiB와의 차이 약 110MiB는 스레드 스택, GC·JIT 내부 자료구조, `malloc` 등 이 지표에 없는 네이티브 메모리다. 영역별로 측정(NMT)하지는 않았다.

### 경위 정리

- 이 애플리케이션은 힙 밖에서만 약 300MiB를 쓴다(메타스페이스·코드 캐시·압축 클래스 공간 약 195MiB + 보이지 않는 네이티브 메모리 약 110MiB). nano 설정은 힙 384MiB에 이 값을 더하면 512MiB를 넘으므로, 스왑이 있어야만 버틴다.
- 메모리는 부하 초반에 올라 일정 수준에서 멈췄고 부하가 끝난 뒤에도 늘지 않았다(30초 범위). 그래서 nano 무스왑 OOM-kill은 누수라기보다 필요한 메모리가 512MiB보다 크기 때문으로 본다. 더 긴 시간의 누적 여부는 확인하지 않았다.
- 같은 nano 설정으로 측정한 다른 시나리오(GR-151·152)의 "서버 다운 없음"도 스왑 덕분이었을 수 있었다. 이 부분은 GR-149 수정(#177)에서 스왑을 막고 다시 검증됐다(drop-open-spike OOM-kill, 커밋 메시지 기준).
- 작업자 결정으로 GR-161 본 측정은 micro 기준으로 처음부터 다시 했다. micro 설정은 저장소 `compose.loadtest.yaml`에 넣지 않고 임시 설정으로 쓴다.
