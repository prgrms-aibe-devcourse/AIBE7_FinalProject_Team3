# SSE 동시 연결 부하테스트 결과 (GR-157)

> 운영 캐파시티 수치가 아니라 micro(vCPU 2개/1GiB) 환경의 **하한선 검증**이다(공통 전제는 `../README.md`).
> 실행 방법은 각 스크립트 상단 주석과 `run.sh` 참고.

## 결론

**micro(`-Xmx550m -XX:+UseG1GC`, 스왑 0)에서 SSE 800 연결 + 주문 50/초 × 5분까지 버텼다.** 12회차 모두 OOM-kill·재시작 0,
주문 실패 0, 놓친 알림 0, 재고 이상 0행이다. 컨테이너 메모리는 200 연결까지 47~57%, 800 연결에서 최대 68.7%였다.

- SSE 활성 시 주문 p95: 0 연결 평균 9.2ms → 100 연결 9.6ms(+4%) → 200 연결 9.8ms(+7%). 13.2 기준(10% 이내) 안이지만,
  0 연결 회차끼리도 8.6~9.6ms로 흔들려 이 차이가 SSE 때문인지 회차 편차인지는 구분되지 않는다.
- 전달 지연 p95는 연결 수와 무관하게 약 985ms(1초 병합 창). 600·800 연결에서 최대 9.2초가 나왔지만 각 773만·1,028만 쌍 중
  20여 쌍이고 p99는 1,029ms 이하다.
- 전송 시 재검증 쿼리는 연결 수에 정비례한다(200 연결 5분간 약 5.8만 회, 800 연결 약 23만 회). GR-163 기준선으로 남긴다.
- 800 연결은 한계가 아니라 측정한 최대치다. 한계를 찾으려면 더 늘려야 한다.

이전에 nano(512MiB)에서 측정한 결과는 [아래](#이전-측정-nano-참고용)에 남겨 두었다. CPU 제한(1개)과 GC(SerialGC 자동 선택)가
지금 기준과 달라 직접 비교하지 않는다.

## 상세 (micro 기준)

### 측정 조건

실행일 2026-10-27. GR-155 병합 이후의 `compose.loadtest-micro.yaml`(backend vCPU 2개, 1GiB, `memswap_limit: 1g`,
`JDK_JAVA_OPTIONS=-Xmx550m -XX:+UseG1GC`)에 `compose.loadtest-sse.yaml`(SSE IP 제한 완화, `pg_stat_statements`)을 겹쳐 띄웠다.
Prometheus GC 지표로 G1(`G1 Young Generation`) 동작을 확인했다.

- 회차마다 backend 컨테이너를 새로 만들고 시드 → 워밍업(주문 20/초 × 60초) → `run.sh <이름> <연결 수> 50 300`.
- 기준선: 연결 0·100·200을 각 3회. 한계 탐색: 서버 연결 상한(`GRAB_STOCKSTREAM_MAXCONNECTIONS`)을 1000으로 올리고
  400·600·800을 각 1회.
- 연결 구성(상세 70% / 목록 30%), 주문 구성(인기 상품 80%), 결제 없음은 nano 측정과 같다.

2초를 넘은 쌍은 c200-3 8쌍, lim400 1쌍, lim600 23쌍, lim800 21쌍이다(lim600 전체 773만 쌍 중). 값이 2,064·3,137·4,109·
5,157·9,247ms처럼 "정수 초 + 약 100ms"로 나타나, 그 연결이 병합 창 몇 번을 건너뛴 모양이다. 같은 구간 G1 정지는 최대 21ms라
GC는 아니다. 서버 송신 쪽인지 Node 클라이언트(한 프로세스가 600~800 연결 수신) 쪽인지는 확인하지 않았다.

### 한계 (micro 측정)

- 부하 발생기가 모두 한 IP라 IP 제한을 오버라이드했고, 유지 시간을 5분으로 줄였다. 느린 수신자·수명 만료 재연결·프록시
  경유는 다루지 않았다(GR-180 범위).
- 운영(t3.small, 2GiB)은 컨테이너 메모리 제한 없이 OS·blue/green 백엔드 2개와 메모리를 나눠 쓴다. 이 결과를 운영 수치로
  옮기지 않는다.
- 지연은 커밋 시각이 아닌 주문 응답 수신 시각 기준 근사값이다(`analyze.mjs` 주석).
- 한계 탐색 회차는 각 1회다.
- `run.sh`의 Prometheus 지표(HikariCP 커넥션 획득 수 등)는 주문 구간보다 15초 늦은 구간(시작 후 15초 ~ 종료 후 15초)을
  집계한 근사값이다. 모든 회차가 같은 방식이라 회차끼리 비교는 유효하고, GR-163 전후 비교도 같은 방식을 유지하려고
  고치지 않았다. 재검증 쿼리 호출 수는 `pg_stat_statements` 기준이라 이 영향이 없다.

## 이전 측정: nano (참고용)

> 2026-10-26 측정. 당시 `compose.loadtest.yaml`은 `cpus: 1`이었고(GR-154에서 2로 수정), JVM 옵션에 GC를 지정하지 않아
> 512MiB 컨테이너에서 JDK17이 **SerialGC**를 자동 선택했다. 지금 기준(vCPU 2개, G1GC)과 조건이 달라 수치를 직접 비교하지 않는다.

### 요약

**스왑을 끈 nano에서 SSE 200 연결 + 주문 50/초는 현재 JVM 설정(`-Xmx384m`)으로는 OOM으로 죽는다.** 150 연결까지는
버텼다(메모리 최대 98.5%). JVM 옵션만 `-Xmx256m -Xss512k`, `MALLOC_ARENA_MAX=2`로 바꾸면 200 연결도 버텼다(1회, 메모리
최대 97.6%). 실제 사용 힙은 150MiB 이하로 작고, 힙 상한이 컨테이너 크기에 비해 커서 한도를 넘은 것으로 판단한다.
연결 상한을 풀고 늘려 보면 250은 죽고 300은 버티고 400은 8초 만에 죽었다. 같은 조정 옵션에서도 200~300은 힙 확보량에 따라
생사가 갈리는 경계 구간이라, 안정적인 한계를 말하려면 JVM 메모리 예산을 더 줄여야 한다.
처음 측정(아래 "1차 측정")은 `compose.loadtest.yaml`이 `memswap_limit` 없이 `mem_limit`만 둬서, Docker 기본값대로
메모리만큼(512MiB) 스왑이 허용된 상태였다. 200 연결이 512MiB 한도에 붙은 채 OOM 없이 버틴 것은, 스왑을 끄자 같은 조건이 OOM-kill된 점으로 보아 스왑 덕분이었다고 판단한다(당시 스왑 사용량은 기록하지 않았다).
t3.nano는 기본 스왑이 없으므로 `memswap_limit: 512m`으로 스왑을 끄고 다시 측정한 결과를 nano 측정의 기준으로 삼았다.

- 버틴 구간(100·150 연결)에서는 연결 실패·알림 유실·재고 이상 **미발생**, SSE 활성 시 주문 p95 악화 없음,
  전달 지연 p95 약 1초(병합 창).
- 통과 회차도 메모리가 95~98.5%로 여유가 거의 없다. 회차마다 컨테이너가 거친 이전 부하가 달라 연결 수별 메모리를
  직접 비교하지는 않았다.
- 전송 시 재검증 쿼리는 150 연결 기준 5분간 약 4.3만 회 실행돼 당시 GR-163 기준선으로 잡았던 값이다(지금 기준선은 위 micro 절).

### 스왑 제거 재측정

실행일 2026-10-26. `memswap_limit: 512m`(스왑 0) 외 조건은 아래 1차 측정과 같다. 모든 회차 주문 50/초 × 5분,
`run.sh`로 실행했고 측정 중 backend cgroup `memory.swap.current`를 3초 간격으로 기록해 스왑 0을 확인했다.
200 회차는 컨테이너 재기동 + 워밍업(20/초 × 60초) 직후, 나머지는 재기동 + 워밍업 뒤 연달아 실행했다.

| SSE 연결 | 결과 | 주문 p95 | 전달 지연 p50 / p95 / 최대 | backend 메모리 최대 |
| --- | --- | --- | --- | --- |
| 0 (비활성 기준선) | 통과, 15,000건 | 10.7ms | — | 95.1% |
| 100 | 통과, 15,001건 | 11.2ms | 523 / 988 / 1,171ms | 97.9% |
| 150 | 통과, 15,001건 | 9.8ms | 519 / 986 / 1,066ms | 98.5% |
| 200 | **OOM-kill** (주문 시작 24초) | — | — | 99.8% 후 종료 |

- 통과 회차: 주문 실패 0, 서버 쪽 연결 종료 0, 놓친 알림 0(150 연결 1,926,960쌍), `verify.sql` 이상 0행,
  HikariCP timeout 0. 주문 p95는 SSE 비활성 대비 악화 없음(13.2 기준 10% 이내).
- 200 회차: SSE 200 연결이 ready된 시점 메모리가 이미 93%(477~481MiB)였고, 주문 투입 후 98%를 넘어
  24초 만에 512MiB에 닿아 커널 OOM-kill(`OOMKilled=true`). 그 전까지 성공한 주문 1,182건의 재고 정합성은
  이상 없었다. 1회만 실행했다.
- 151~199 사이 정확한 한계는 찾지 않았다. 아래 JVM 옵션 조정으로는 200 연결도 버텼다.

**JVM 옵션 조정 실험 (200 연결 재시도)**

OOM 직전 JVM 지표를 보면 실제 사용 힙은 147MiB였지만, `-Xmx384m`(힙 상한 371MiB) + 힙 외 영역 약 215MiB
(Metaspace 140MiB, 코드 캐시 약 60MiB) + JVM 밖 네이티브 메모리를 합치면 512MiB를 넘게 쓸 수 있는 설정이었다.
부하로 확보 힙이 188MiB까지 늘자 컨테이너 한도를 넘었다. 코드는 그대로 두고 임시 오버라이드로
`JDK_JAVA_OPTIONS=-Xmx256m -Xss512k`, `MALLOC_ARENA_MAX=2`만 바꿔 같은 조건(스왑 0, 200 연결, 50/초 × 5분)을 다시 돌렸다.

| 항목 | 결과 |
| --- | --- |
| 생존 | **통과** — OOM-kill 0, 재시작 0, 서버 쪽 연결 종료 0 |
| 주문 | 15,001건 실패 0, p95 10.0ms(최대 521ms) |
| 전달 지연 | p50 521 / p95 986 / 최대 4,134ms, 놓친 알림 0(2,587,200쌍) |
| 메모리 | 컨테이너 최대 97.6%, 힙 사용 최대 144MiB / 확보 198MiB, 힙 외 확보 219MiB |
| GC | minor 317회/5분(누적 정지 0.96초), full GC 0회 |
| CPU | 평균 28% / 최대 78% |

- 200 연결의 OOM은 SSE 코드가 아니라 **JVM 메모리 예산 설정**(힙 상한이 컨테이너에 비해 큼) 문제로 판단한다.
- 다만 1회 실행이고 메모리 최대 97.6%로 여유가 여전히 작다. 세 옵션 중 어느 것이 효과를 냈는지는 나눠 보지 않았다.
- 이 옵션은 레포에 반영하지 않았다. 운영 배포(`Dockerfile`, `deploy/`)에는 JVM 메모리 옵션이 없어 기본값(사용 가능
  메모리의 25%를 힙 상한)으로 돌고, 부하테스트의 `-Xmx384m`도 운영과 다른 값이다. 운영 JVM 옵션은 별도로 정한다.

**JVM 옵션 조정 후 연결 한계 탐색 (250·300·400)**

위 조정 옵션에 서버 전체 연결 상한만 `GRAB_STOCKSTREAM_MAXCONNECTIONS=1000`으로 올려(전송 큐 크기도 이 값을 따른다)
같은 조건(스왑 0, 주문 50/초 × 5분)으로 연결 수를 늘렸다. 회차마다 컨테이너를 새로 띄우고 워밍업(20/초 × 60초) 뒤 실행했다.

| SSE 연결 | 결과 | 힙 확보 최대 | 힙 사용 최대 | 힙 외 확보 | 컨테이너 메모리 최대 |
| --- | --- | --- | --- | --- | --- |
| 200 (위 실험) | 통과 | 198MiB | 144MiB | 219MiB | 97.6% |
| 250 | **132초에 응답 없음** (주문 6,313건 성공 후) | 243MiB | 172MiB | 217MiB | 99.8% |
| 300 | 통과 (주문 15,001건 실패 0, 전달 지연 p95 990ms) | 201MiB | 156MiB | 219MiB | 97.7% |
| 400 | **8초 만에 OOM-kill** (`OOMKilled=true`) | — | — | — | 99.99% |

- 결과가 연결 수 순서대로 나오지 않았다. 생존을 가른 것은 연결 수보다 **JVM이 힙을 얼마나 확보했느냐**였다.
  250 회차는 확보 힙이 243MiB(상한 256MiB 근처)까지 늘어 컨테이너 한도에 닿았고, 300 회차는 201MiB에 머물러 버텼다.
  `-Xmx256m`이어도 힙 256 + 힙 외 약 220 + JVM 밖 네이티브 메모리를 합치면 512MiB를 넘을 수 있어, 여전히 경계에 있는 설정이다.
- 250 회차의 종료 사유는 확인하지 못했다(다음 회차를 위해 컨테이너를 다시 만들어 기록이 사라졌고, Docker 이벤트에도
  남지 않았다). 메모리가 99.8%까지 오른 직후 응답이 끊겨 OOM으로 추정한다. 400 회차는 `OOMKilled=true`를 확인했다.
- 각 1회 실행이다. 이 설정에서 **200~300 연결은 힙 확보량에 따라 살 수도 죽을 수도 있는 구간**이고, 400은 확실히 버티지 못한다.
  연결 수 한계를 안정적으로 올리려면 힙 상한을 더 낮추거나(실제 사용 힙은 최대 172MiB) 힙 외 영역을 줄이는 조정이 먼저다.

**GR-163 기준선 — 전송 시 공개 여부 재검증 쿼리**(`countPublicDropsForSubscription`, `pg_stat_statements`)

| SSE 연결 | 쿼리 호출 | 구독 시점 | 전송 시점 | 주문 1건당 | HikariCP 커넥션 획득 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 0 | 0 | 59,789 |
| 100 | 28,984 | 100 | 28,884 | 1.9 | 85,815 |

- 전송 시점 호출은 연결 수 × 초당 1회(병합 창)가 상한이다(150 × 300초 = 45,000).
- 쿼리 자체는 회당 0.01~0.08ms로 가볍지만 매번 커넥션 획득 + `BEGIN READ ONLY`가 따라온다. 150 연결의
  커넥션 획득은 같은 주문량의 SSE 비활성보다 약 1.7배(+42,761)다.

  효과를 응답시간보다 DB 왕복·커넥션 획득 수로 보는 판단은 같다.

### 1차 측정 (스왑 허용 — 참고용)

> 이 절의 메모리·생존 판정은 스왑이 허용된 상태라 nano 판정 근거로 쓰지 않는다. 응답시간·전달 지연·
> 쿼리 호출 수는 참고로 남긴다.

실행일 2026-10-26. 다른 시나리오와 같은 nano 제한(backend 1 vCPU/512MiB, `-Xmx384m`)이며, 이 시나리오만
`compose.loadtest.yaml`의 SSE IP 제한 오버라이드와 postgres `pg_stat_statements`를 함께 썼다.
SSE 연결은 Node(`sse-clients.mjs`), 주문은 로컬 k6 v2.3.0(`order-load.js`, 결제 없이 주문 생성만)으로
같은 Mac에서 실행했다. 연결 구성은 상세 구독 70%(인기 상품 1개) / 목록 구독 30%(24개),
주문은 80%가 인기 상품. REALTIME_STOCK.md 13.2의 유지 시간(워밍업 2분 + 측정 10~15분)은
nano에서 줄여 **회차당 주문 5분**으로 실행했다.

| 회차 | SSE 연결 | 주문 | 주문 p95 | 전달 지연 p50 / p95 / 최대 | 비고 |

- 전달 지연 p95 약 1초는 서버의 1초 병합 창(`coalesce-window`) 때문이다. 13.1 목표(평시 2초, 피크 3초)
  안쪽이다. 최대 7.2초는 2회차의 단발 아웃라이어(p99 1,025ms)로 원인은 확인하지 않았다(GC 추정, 검증 안 함).

### 정리·제한 동작 (1차 측정 때 확인)

- 클라이언트 200개 일괄 종료 후 서버 연결·구독·pending이 0이 되기까지 약 57초(52초 시점 65개 잔존).
  서버는 다음 쓰기(heartbeat 15초)가 실패해야 끊긴 연결을 알아서, 13.2 목표(60초 후 0)에 근소하게 들어왔다.
- 같은 IP 21번째 연결 429(`reason=ip`), 60초 창 31번째 요청 429(`reason=rate`), 201번째 연결 503(`capacity`)
  모두 기대대로 동작. 서버는 IP 제한을 전체 상한보다 먼저 검사하므로, 503을 보려면 IP 상한을 200보다 크게
  둬야 한다(첫 시도에서 IP 상한 200으로 429가 먼저 나서 오버라이드 기본값을 1000으로 고쳤다).

### 한계 (nano 측정)

부하 발생기가 모두 한 IP라 IP 제한을 오버라이드했고, 유지 시간을 5분으로 줄였으며, 느린 수신자·
수명 만료 재연결·프록시 경유는 다루지 않았다(GR-180 범위). k6와 Node가 같은 Mac 시계를 써서 시계 오차는
없지만, 지연은 커밋 시각이 아닌 주문 응답 수신 시각 기준 근사값이다.
