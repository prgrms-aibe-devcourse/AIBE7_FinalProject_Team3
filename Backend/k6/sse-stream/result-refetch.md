# SSE 재조회 포함 통합 부하테스트 결과 (GR-180)

> GR-157은 SSE 연결 비용만 쟀다(클라이언트가 알림을 받기만 함). 여기서는 프론트처럼 **알림마다 기존 조회 API를 다시 부르는**
> 클라이언트로 SSE 연결·재조회·주문을 함께 걸고, GR-183 응답 캐시 전후를 같은 조건으로 비교했다.
> 환경은 운영(EC2 t3.small + Supabase 무료 티어 Nano)을 모사한 로컬 하한선 조건이다(GR-186, `../db-nano/result.md`).
> Nginx 경유 검증은 `../sse-nginx/result.md`.

## 결론

> **GR-198 이후:** 목록 count 쿼리를 본 쿼리에 합친 뒤 같은 조건에서 400연결까지 기준을 충족했다(600부터 미달). [아래](#개선-결과--목록-전체-건수를-본-쿼리에서-함께-계산-gr-198-2026-10-28) 참고. 이 절의 결론은 GR-180 측정 시점 기준이다.

**DB CPU 1개로 제한한 로컬 모사 조건에서, 앱 메모리 캐시 적용 후 100연결은 고정 기준(재조회 p95 각 200ms 이하 등)을 충족했고 150연결은 목록 p95 206ms로 미달했다. 캐시가 없으면 100연결에서 미달이며, 더 작은 연결 수는 재지 않아 통과 가능한 최대치는 확인하지 않았다.**
참고 목표(800~1000)와는 거리가 크다. 운영 Supabase·EC2의 실제 수용 인원으로 옮겨 해석하지 않는다.

- **SSE 전달은 병목이 아니다.** 1000 연결에서도 알림 전달 p95 약 1초(기준 3초), 화면 반영 p95 5.2초 이하(기준 8초), 서버 전송 실패·정체·큐 거절 0.
- **병목은 HTTP 재조회, 그중 캐시가 없는 목록 재조회다.** 400 연결에서 SSE 구독 구성은 그대로 두고 목록 재조회 HTTP만 끄면
  주문 p95 630 → **44ms**, 상세 326 → **30ms**, 재고 267 → **16ms**, HikariCP 대기 최대 91 → **0**, 주문 구간 DB CPU 평균 37 → **7%**였다(SSE 전송 수는 같음).
- **결과는 DB CPU 가정에 매우 민감하다.** 지연 2.5ms를 유지한 채 DB vCPU만 1 → 2개로 늘리면 400 연결에서 주문 p95 202ms, 재조회 p95 131 / 115 / 187ms로
  기준을 모두 충족했고 목록 p50도 약 250 → 92ms로 줄었다. 목록 비용은 DB CPU 쪽에 있을 가능성이 높다(postgres 컨테이너 CPU 스로틀링 관측, 아래).
  지연 0ms·풀 20 조정만으로는 목록 지연이 해소되지 않았다.
- **캐시(GR-183)는 효과가 있지만 주문과 섞이면 제한적이다.** 1000 연결 주문 p95 3,094 → 1,302ms, 커넥션 대기 190 → 111. 인기 상품에 주문 40건/초가
  몰리면 상세·재고 캐시는 평균 25ms마다 지워져, 효과는 주로 동시 조회 합치기에서 나온다.
- 모든 회차에서 HTTP 오류·커넥션 timeout·OOM·재시작 0, 재고 정합성(`verify.sql`) 이상 0행.

- **목록 HTTP만 끄면**(SSE 구독·전송 수 유지, 재조회 요청 340 → 280건/초) 주문·상세·재고가 모두 기준 안으로 들어오고 커넥션 대기가 사라졌다. 목록 재조회가 다른 요청을 기다리게 만든다는 직접 근거다.
  처음 실행한 `DETAIL_RATIO=1` 회차는 목록 구독 자체를 없애 SSE 구독 상품(24개 → 1개)과 전송 수까지 바뀐 실험이라, 목록 HTTP 영향만 분리한 것은 아니다(결과 방향은 같음).
- **DB vCPU 2**에서는 같은 지연에서 목록 p50이 92ms로 줄고 모든 기준을 충족했다. 기준 회차의 postgres 컨테이너는 CPU 한도 1개에서 주기의 약 9%(5,777 중 539주기) 동안 스로틀링됐다
  (`cpu.stat`, GR-198 시작 시 측정). 평균 CPU는 37%여도 순간 몰림에서 한도에 걸려 쿼리 실행이 늘어나는 것으로 보인다. 부하 중 목록 SQL 실행당 평균은 본 쿼리 약 13ms, count 쿼리 약 10ms였다(`pg_stat_statements`).
  이 SQL 시간만으로 목록 HTTP 중앙값(약 250ms) 전체를 설명하기는 어려워, 커넥션 획득 대기·결과 변환·Tomcat 대기를 나눠 보는 작업이 남아 있다(GR-198).
- **지연 0ms**는 주문·상세 중앙값을 크게 줄였지만(주문 p50 99 → 4ms) 목록 p50(281ms)과 p95는 그대로였다. **풀 20**은 대기를 줄였지만 주문 p95 816ms, 목록 p50 322ms로 나아지지 않았다.
- **Tomcat 스레드**(memory-tc 주문 구간, 실제 간격 약 5.1초 35샘플): busy 평균 33 · p95 139 · 최대 200(포화 샘플 1개). 수집한 샘플에서는 지속적인 스레드 포화가 관측되지 않았다.
  샘플 간격이 길어 짧은 포화가 응답 지연에 기여했는지는 확정하지 못했다. 목록 HTTP를 끈 회차는 평균 4.
- **주문 경로의 행 잠금 대기:** 부하 중 SQL 통계에서 주문의 옵션 `SELECT … FOR UPDATE`가 실행당 평균 46ms(최대 472ms)로 총 실행 시간 1위였다(memory-g198base). 인기 상품 한 행에 주문 40건/초가 몰려
  잠금을 기다린 시간이며, 잠금을 쥔 트랜잭션이 DB 왕복(약 3ms × 여러 번) 동안 잠금을 유지하므로 왕복 지연과 DB 처리 속도에 따라 대기가 커진다. 목록을 끈 회차에서 주문 p95가 44ms로 내려간 것과 함께 GR-198에서 확인한다.
- ~~memory-cpu2-400~~ **무효:** `stages.sh`가 backend를 다시 만들 때(`--force-recreate`) postgres 설정이 기본값(CPU 1개)과 달라 compose가 postgres까지 다시 만들었다.
  그 결과 CPU 1개 + netem 없음(회차 기록 `qdisc noqueue`)으로 측정됐다. 사실상 지연 0ms 회차의 반복이다. 이후 `stages.sh`·`verify.sh`는 `--no-deps`로 backend만 다시 만들고, 회차 기록에 postgres CPU 한도를 남긴다.
  나머지 회차는 모두 netem 2.5ms가 기록돼 있다.

## 개선 결과 — 목록 전체 건수를 본 쿼리에서 함께 계산 (GR-198, 2026-10-28)

- 서버 측 목록 요청 시간(`http_server_requests`) 평균 265ms가 클라이언트 중앙값과 비슷해, Tomcat 진입 전 대기는 작다.
- 154ms는 획득 대기와 커밋 등을 합친 값이다. 같은 회차 HikariCP 획득 평균은 52.6ms(모든 요청 평균)였다.
- 부하 없을 때 목록 SQL은 본 쿼리 약 2.1~2.9ms, count 약 1.9ms이고 둘 다 DROP 5,027건을 순차 스캔하며 `ILIKE`로 거르는 데 시간을 쓴다. 부하 중에는 12~13ms·9~10ms로 늘었다(`pg_stat_statements`).
  요청 하나가 같은 후보 스캔을 두 번 하고 DB 왕복도 두 번 한다.

### 변경

- 공개 목록 3종(날짜·인기 WISH·인기 GRAB)의 본 쿼리 SELECT에 `COUNT(*) OVER () AS "totalCount"`를 더하고 별도 count 쿼리를 없앴다.
- 결과 행이 없으면 건수를 얻을 수 없으므로, 첫 페이지가 비면 0건, 범위를 넘은 페이지만 기존 count 쿼리를 실행한다(`DropRepository.toPage`).
- 응답 형식·정렬·필터·`totalElements` 의미는 바꾸지 않았다.

## 해석 시 주의

- **"놓친 알림"은 유실이 아니다.** none-800 1,023쌍(611만 쌍 중), none-1000 2,056쌍(769만), memory-400 194쌍, memory-800 1,073쌍, memory-1000 300쌍이 나왔다.
  none-1000을 확인한 결과 모두 목록 연결이고 98%가 주문 구간 마지막 5초에 있었으며, 알림이 주문 응답보다 평균 약 135ms **먼저** 도착해 있었다.
  주문 응답이 수 초 늦어져 커밋 후 알림이 응답보다 먼저 왔고, 비인기 상품은 이후 변경이 없어 `analyze.mjs`(응답 시각을 커밋 시각 대신 씀)가 대응시킬 다음 알림이 없었다.
  서버 쪽 전송 실패·정체·큐 거절은 전 회차 0이다.
- **화면 반영**은 재조회가 HTTP 200으로 끝난 시각까지다. 응답의 재고 값이 최신인지, 브라우저 렌더링은 확인하지 않는다.
- **목록 부하**는 `keyword` 검색 한 페이지뿐이다. 날짜·인기 WISH·인기 GRAB 정렬, 품절 필터, WISH 등록·취소 부하는 대표하지 않는다.
- 캐시 효과 추정의 "무효화 횟수 이하 DB 조회"는 코드가 보장하는 상한이 아니다(TTL 만료, 확인과 적재 사이의 끼어들기). 실제 loader 실행 수는 계측하지 않았다.

## 한계

- 로컬 모사 환경이다. DB CPU 1개는 Supabase Nano 공유 CPU를 대신한 가정값이며, 목록이 DB를 바쁘게 하는 구간이라 결과가 이 값에 민감할 수 있다(위 vCPU 2 회차 참고).
- 운영 EC2·Supabase에 부하를 걸지 않았다(GR-186 범위 조정). 운영은 Nginx(TLS)를 거치고 blue/green으로 backend 두 개가 메모리를 나눠 쓴다.
- 부하 발생기·backend·DB가 같은 Mac에 있다. 루프 지연은 정상 범위였지만 CPU를 나눠 쓴다.
- 13.2절의 유지 시간(워밍업 2분 + 측정 10분)보다 짧은 180초 피크로 쟀다. 느린 수신자·10분 수명 재연결은 이 시나리오에 없다(재연결은 Nginx 검증에서 확인).
- 단계당 1회다.
