# SSE 재조회 포함 통합 부하테스트 결과 (GR-180)

> GR-157은 SSE 연결 비용만 쟀다(클라이언트가 알림을 받기만 함). 여기서는 프론트처럼 **알림마다 기존 조회 API를 다시 부르는**
> 클라이언트로 SSE 연결·재조회·주문을 함께 걸고, GR-183 응답 캐시 전후를 같은 조건으로 비교했다.
> 환경은 운영(EC2 t3.small + Supabase 무료 티어 Nano)을 모사한 로컬 하한선 조건이다(GR-186, `../db-nano/result.md`).
> Nginx 경유 검증은 `../sse-nginx/result.md`.

## 결론

> **정정(GR-200 후속):** 아래 "병목은 목록 재조회"는 알림 동시 도착으로 재조회가 집중된 조건의 관측이다. 재조회 시점을 분산하면 같은 요청량에서 1000연결 회차까지 기준을 충족했다. [순간 몰림 분석](#순간-몰림-분석과-재조회-시점-분산-gr-200-후속-2026-10-28) 참고.
>
> **GR-198 이후:** 목록 count 쿼리를 본 쿼리에 합친 뒤 같은 조건에서 400연결까지 기준을 충족했다(600부터 미달). 다만 GR-200 재측정에서 400연결 목록 p95가 236ms로 미달해 400은 경계다. [아래](#개선-결과--목록-전체-건수를-본-쿼리에서-함께-계산-gr-198-2026-10-28) 참고. 이 절의 결론은 GR-180 측정 시점 기준이다.

**DB CPU 1개로 제한한 로컬 모사 조건에서, 앱 메모리 캐시 적용 후 100연결은 고정 기준(재조회 p95 각 200ms 이하 등)을 충족했고 150연결은 목록 p95 206ms로 미달했다. 캐시가 없으면 100연결에서 미달이며, 더 작은 연결 수는 재지 않아 통과 가능한 최대치는 확인하지 않았다.**
참고 목표(800~1000)와는 거리가 크다. 운영 Supabase·EC2의 실제 수용 인원으로 옮겨 해석하지 않는다.

- **SSE 전달은 병목이 아니다.** 1000 연결에서도 알림 전달 p95 약 1초(기준 3초), 화면 반영 p95 5.2초 이하(기준 8초), 서버 전송 실패·정체·큐 거절 0.
- **병목은 HTTP 재조회, 그중 캐시가 없는 목록 재조회다.** 400 연결에서 SSE 구독 구성은 그대로 두고 목록 재조회 HTTP만 끄면
  주문 p95 630 → **44ms**, 상세 326 → **30ms**, 재고 267 → **16ms**, HikariCP 대기 최대 91 → **0**, 주문 구간 DB CPU 평균 37 → **7%**였다(SSE 전송 수는 같음).
- **결과는 DB CPU 가정에 매우 민감하다.** 지연 2.5ms를 유지한 채 DB vCPU만 1 → 2개로 늘리면 400 연결에서 주문 p95 202ms, 재조회 p95 131 / 115 / 187ms로
  기준을 모두 충족했고 목록 p50도 약 250 → 92ms로 줄었다. 목록 비용은 DB CPU 쪽에 있을 가능성이 높다(postgres 컨테이너 CPU 스로틀링 관측, 아래).
  지연 0ms·풀 20 조정만으로는 목록 지연이 해소되지 않았다.
- **캐시(GR-183)는 효과가 있지만 주문과 섞이면 제한적이다.** 1000 연결 주문 p95 3,094 → 1,302ms, 커넥션 대기 190 → 111. 인기 상품에 주문 40건/초가
  몰리면 상세·재고 캐시는 평균 25ms마다 지워져, 효과는 주로 동시 조회 합치기에서 나온다.
- 모든 회차에서 HTTP 오류·커넥션 timeout·OOM·재시작 0, 재고 정합성(`verify.sql`) 이상 0행.

- **목록 HTTP만 끄면**(SSE 구독·전송 수 유지, 재조회 요청 340 → 280건/초) 주문·상세·재고가 모두 기준 안으로 들어오고 커넥션 대기가 사라졌다. 목록 재조회가 다른 요청을 기다리게 만든다는 직접 근거다.
  처음 실행한 `DETAIL_RATIO=1` 회차는 목록 구독 자체를 없애 SSE 구독 상품(24개 → 1개)과 전송 수까지 바뀐 실험이라, 목록 HTTP 영향만 분리한 것은 아니다(결과 방향은 같음).
- **DB vCPU 2**에서는 같은 지연에서 목록 p50이 92ms로 줄고 모든 기준을 충족했다. 기준 회차의 postgres 컨테이너는 CPU 한도 1개에서 주기의 약 9%(5,777 중 539주기) 동안 스로틀링됐다
  (`cpu.stat`, GR-198 시작 시 측정). 평균 CPU는 37%여도 순간 몰림에서 한도에 걸려 쿼리 실행이 늘어나는 것으로 보인다. 부하 중 목록 SQL 실행당 평균은 본 쿼리 약 13ms, count 쿼리 약 10ms였다(`pg_stat_statements`).
  이 SQL 시간만으로 목록 HTTP 중앙값(약 250ms) 전체를 설명하기는 어려워, 커넥션 획득 대기·결과 변환·Tomcat 대기를 나눠 보는 작업이 남아 있다(GR-198).
- **지연 0ms**는 주문·상세 중앙값을 크게 줄였지만(주문 p50 99 → 4ms) 목록 p50(281ms)과 p95는 그대로였다. **풀 20**은 대기를 줄였지만 주문 p95 816ms, 목록 p50 322ms로 나아지지 않았다.
- **Tomcat 스레드**(memory-tc 주문 구간, 실제 간격 약 5.1초 35샘플): busy 평균 33 · p95 139 · 최대 200(포화 샘플 1개). 수집한 샘플에서는 지속적인 스레드 포화가 관측되지 않았다.
  샘플 간격이 길어 짧은 포화가 응답 지연에 기여했는지는 확정하지 못했다. 목록 HTTP를 끈 회차는 평균 4.
- **주문 경로의 행 잠금 대기:** 부하 중 SQL 통계에서 주문의 옵션 `SELECT … FOR UPDATE`가 실행당 평균 46ms(최대 472ms)로 총 실행 시간 1위였다(memory-g198base). 인기 상품 한 행에 주문 40건/초가 몰려
  잠금을 기다린 시간이며, 잠금을 쥔 트랜잭션이 DB 왕복(약 3ms × 여러 번) 동안 잠금을 유지하므로 왕복 지연과 DB 처리 속도에 따라 대기가 커진다. 목록을 끈 회차에서 주문 p95가 44ms로 내려간 것과 함께 GR-198에서 확인한다.
- ~~memory-cpu2-400~~ **무효:** `stages.sh`가 backend를 다시 만들 때(`--force-recreate`) postgres 설정이 기본값(CPU 1개)과 달라 compose가 postgres까지 다시 만들었다.
  그 결과 CPU 1개 + netem 없음(회차 기록 `qdisc noqueue`)으로 측정됐다. 사실상 지연 0ms 회차의 반복이다. 이후 `stages.sh`·`verify.sh`는 `--no-deps`로 backend만 다시 만들고, 회차 기록에 postgres CPU 한도를 남긴다.
  나머지 회차는 모두 netem 2.5ms가 기록돼 있다.

## 개선 결과 — 목록 전체 건수를 본 쿼리에서 함께 계산 (GR-198, 2026-10-28)

> 위 측정에서 병목으로 분리한 목록 재조회의 커넥션 점유를 구간별로 나누고, 원인에 맞춰 목록의 count 쿼리를 본 쿼리에 합쳤다.

### 구간 분리 (400 연결, 개선 전)

## 측정 보강 — 재고값 최신성·미확정 알림 분리·목록 분산 (GR-200, 2026-10-28)

> GR-198 코드(앱 메모리 캐시)에서 같은 조건(DB vCPU 1, netem 2.5ms)으로 쟀다. 회차마다 1회.

### 추가한 것

- **재고값 최신성**(`analyze.mjs` `staleness`): 재조회 응답의 가용 재고(상세 연결은 재고 API 합, 목록 연결은 페이지의 상품별 값)를
  "시작 재고 − 재조회 시작 5ms 전까지 응답을 받은 주문 수"와 비교해 크면 옛 값으로 센다. 응답을 받은 주문은 확실히 커밋됐으므로 오탐이 없고,
  커밋됐지만 응답이 아직 안 온 주문은 세지 않아 일부 옛 값을 놓칠 수는 있다. 주문 1건 = 수량 1, 측정 중 결제 대기 만료(10분)·취소 없음이 전제다.
  판정 여유를 일부러 −10초로 바꾸면 재고 응답의 94%, 목록의 86%가 옛 값으로 잡혀 판정이 동작함을 확인했다.
- **미확정 알림 분리**: 주문 로그에 요청 시작 시각을 더하고(`ORDER <응답> <상품> <요청 시작>`), 응답 이후 알림이 없지만 요청 시작~응답 사이에 같은 상품 알림이
  있으면 `unresolved`(미확정)로 센다. 그 알림이 이번 주문의 것인지 같은 상품의 이전 주문 것인지 가릴 커밋 표식이 없기 때문이다. `missing`은 요청 시작 이후
  같은 상품 알림이 전혀 없는 쌍만이다. 처음에는 이 경우를 `earlyArrival`(응답 전 도착, 유실 아님)로 셌지만 이전 주문의 알림일 수 있어 미확정으로 고쳤다(CodeRabbit 리뷰).
  이전 회차 로그에는 요청 시작 시각이 없어 다시 분류할 수 없다.
- **목록 분산**(`LIST_MIX=mixed`): 목록 연결을 7개 조회(keyword 검색, 날짜순, GRAB 탭, GRAB 탭 품절 제외, 카테고리, 인기 GRAB, 인기 WISH)에 나눠 배정하고,
  각 연결은 자기 조회의 첫 페이지 상품을 구독해 알림마다 같은 조회를 다시 부른다. 날짜순·GRAB 탭·카테고리는 가장 최근 공개된 SSE 시드 상품이 첫 페이지에 오고,
  인기순 두 조회는 대용량 seed 상품이 와서 주문 알림 없이 주기 재동기화만 한다. WISH 등록·취소 부하는 넣지 않았다.

### 원인: 알림 동시 도착에 따른 재조회 집중

- 평균 재조회 요청량은 같다(초당 약 340건). 다른 것은 도착 시점이다. 현재는 100ms 구간의 절반 이상이 0건이고 최대 388~670건이 한꺼번에 오며, 바닐라는 100ms당 약 35건으로 고르다.
- 바닐라는 GR-163 이전이라 알림을 보낼 때 연결마다 공개 여부를 DB에서 다시 조회했다. 그 비용 때문에 한 번의 알림이 상세 연결 280개에 약 1초에 걸쳐 퍼져 도착했고(수신 퍼짐 p50 약 920~985ms), 재조회도 흩어졌다. 현재는 그 조회가 없어 알림이 짧은 시간에 도착한다(퍼짐 측정값은 회차마다 8~565ms로 흔들려 보조 지표로만 본다).
- 이 순간 부하가 공유 DB 자원(커넥션 10개·DB CPU 1개)의 대기를 키웠다. 주문의 잠금 대기·목록 쿼리 실행 시간이 늘고 Tomcat 요청 스레드가 순간적으로 126~200개까지 올라갔다(JVM 전체 스레드 최대 243은 Tomcat 포화 근거가 아님). 목록 조회는 캐시가 없어 그 부담에 크게 기여했다.
- 바닐라도 지연 0이면 전송이 빨라져 같은 집중이 생기고 나빠졌다(목록 p95 659ms). DB CPU 제한이 없으면 바닐라·현재 모두 순간 부하를 흡수했다.
- 즉 SSE 전송 최적화(GR-163)는 전송 시 DB 조회를 없앴지만, 알림을 동시에 도착시켜 후속 HTTP 요청을 집중시켰다. 바닐라의 고른 부하는 의도된 성능이 아니라 느린 전송의 부수 효과이고, 그 대가로 알림 전달이 늦었다(전달 p95 1,046~1,292ms vs 현재 약 990ms).

### 검증: 재조회 시점 분산(jitter)

측정 클라이언트에 `REFETCH_JITTER_MS`를 추가했다. 알림 신호로 재조회를 예약할 때 대기를 `max(2초 간격의 남은 시간, 균등 0~jitter)`로 하고, 예약은 첫 신호에만 하며 예약 중·조회 중 신호는 dirty로 합친다(타이머를 새로 만들거나 미루지 않음). 같은 현재 코드·구독·주문률에서 jitter만 바꿔 없음 → 있음 → 없음 → 있음 순서로 쟀다(초기화·워밍업 동일).

| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| memory-re-now-c1-d25 | 253 / 225 / 243 | 290 | 0 / 388 | 8 | 126 | 81 | 24% | 2.63s |
| memory-jitB1-c1-d25 | 19 / 7 / 12 | 42 | 45 / 82 | 53 | 17 | 0 | 21% | 2.60s |
| memory-nojit2-c1-d25 | 176 / 160 / 252 | 288 | 0 / 670 | 418 | 200 | 61 | 22% | 2.61s |
| memory-jitB2-c1-d25 | 20 / 8 / 12 | 42 | 34 / 104 | 105 | 15 | 0 | 21% | 2.59s |

- 총 재조회 수는 같은데(61,117~61,200건) jitter 회차는 재조회 p95가 10~30배 줄고, 주문 p95 288~290 → 42ms, 커넥션 대기 0, Tomcat 요청 스레드 최대 15~17이었다. 요청량이 줄어서가 아니라 집중이 풀려 빨라졌다.
- 주문 응답 수신부터 재조회 완료까지 p95는 2.59~2.64초로, 이번 지속 부하에서 악화는 관측되지 않았다(2초 간격 대기가 대부분이라 1초 이내 jitter가 그 안에 들어감). 첫 알림이나 드문 변경에서는 jitter만큼 기다림이 늘 수 있다.
- 탐색 회차(memory-jit1000)는 신호마다 타이머를 따로 걸어 가장 짧은 대기가 선택되는 구현이라 분포가 의도와 달랐다(효과도 작음). 판단에서 뺐다.

### 정정한 결론

SSE 전송 최적화 후 알림이 동시에 도착하면서 재조회 요청이 집중됐다. 이 순간 부하가 공유 DB 자원의 대기를 키웠으며, 목록 조회가 그 부담에 크게 기여했다. 재조회 시점을 분산하자 같은 평균 요청량에서도 지연이 크게 줄었다(DB CPU 1개 제한 로컬 환경, 측정 클라이언트 기준 1000연결 회차 기준 충족). 서비스 적용(프론트 훅)과 브라우저 확인, 1000연결 재검증은 GR-209에서 한다.

## 해석 시 주의

- **"놓친 알림"은 유실로 확정되지 않는다.** (GR-200 이후에는 요청 시작 이후 알림이 전혀 없는 쌍만 놓친 알림으로 세며 0이었고, 요청~응답 사이 알림만 있는 쌍은 미확정으로 따로 센다.) none-800 1,023쌍(611만 쌍 중), none-1000 2,056쌍(769만), memory-400 194쌍, memory-800 1,073쌍, memory-1000 300쌍이 나왔다.
  none-1000을 확인한 결과 모두 목록 연결이고 98%가 주문 구간 마지막 5초에 있었으며, 알림이 주문 응답보다 평균 약 135ms **먼저** 도착해 있었다.
  주문 응답이 수 초 늦어져 커밋 후 알림이 응답보다 먼저 왔을 가능성이 크지만, 그 알림이 이번 주문의 것인지 같은 상품의 이전 주문 것인지는 가릴 수 없다.
  비인기 상품은 이후 변경이 없어 `analyze.mjs`(응답 시각을 커밋 시각 대신 씀)가 대응시킬 다음 알림이 없었다. 주문과 알림을 잇는 커밋 표식이 없어 유실 여부는 미확정이다.
  서버 쪽 전송 실패·정체·큐 거절은 전 회차 0이다.
- **화면 반영**은 재조회가 HTTP 200으로 끝난 시각까지다. 응답의 재고 값 최신성은 GR-200에서 따로 검증했고(옛 값 0), 브라우저 렌더링은 확인하지 않는다.
- **목록 부하**는 `keyword` 검색 한 페이지뿐이다(GR-200에서 7개 조회 분산 회차를 추가). WISH 등록·취소 부하는 대표하지 않는다.
- 캐시 효과 추정의 "무효화 횟수 이하 DB 조회"는 코드가 보장하는 상한이 아니다(TTL 만료, 확인과 적재 사이의 끼어들기). 실제 loader 실행 수는 계측하지 않았다.

## 한계

- 로컬 모사 환경이다. DB CPU 1개는 Supabase Nano 공유 CPU를 대신한 가정값이며, 목록이 DB를 바쁘게 하는 구간이라 결과가 이 값에 민감할 수 있다(위 vCPU 2 회차 참고).
- 운영 EC2·Supabase에 부하를 걸지 않았다(GR-186 범위 조정). 운영은 Nginx(TLS)를 거치고 blue/green으로 backend 두 개가 메모리를 나눠 쓴다.
- 부하 발생기·backend·DB가 같은 Mac에 있다. 루프 지연은 정상 범위였지만 CPU를 나눠 쓴다.
- 13.2절의 유지 시간(워밍업 2분 + 측정 10분)보다 짧은 180초 피크로 쟀다. 느린 수신자·10분 수명 재연결은 이 시나리오에 없다(재연결은 Nginx 검증에서 확인).
- 단계당 1회다.
