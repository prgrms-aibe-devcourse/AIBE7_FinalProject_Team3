# SSE 동시 연결 부하테스트 결과 (GR-157)

> 운영 캐파시티 수치가 아니라 nano(1vCPU/512MiB) 환경의 **하한선 검증**이다(`../RESULTS.md` 공통 전제와 같다).
> 실행 방법은 `../README.md` 6절.

## 결론

200 연결 + 주문 50/초에서 연결 실패·알림 유실·재고 이상 **미발생**, SSE 활성 시
주문 p95 악화 없음, 전달 지연 p95 약 1초(병합 창). 다만 메모리가 512MiB 한도(99.99%)에 닿아 nano에서
200 연결이 여유 없는 상한이다. 전송 시 재검증 쿼리가 5분간 약 5.8만 회 실행돼 GR-163 기준선으로 남긴다.

## 상세

실행일 2026-10-26. `../RESULTS.md`의 다른 시나리오와 같은 nano 제한(backend 1 vCPU/512MiB, `-Xmx384m`)이며, 이 시나리오만
`compose.loadtest.yaml`의 SSE IP 제한 오버라이드와 postgres `pg_stat_statements`를 함께 썼다.
SSE 연결은 Node(`sse-clients.mjs`), 주문은 로컬 k6 v2.3.0(`order-load.js`, 결제 없이 주문 생성만)으로
같은 Mac에서 실행했다. 연결 구성은 상세 구독 70%(인기 상품 1개) / 목록 구독 30%(24개),
주문은 80%가 인기 상품. REALTIME_STOCK.md 13.2의 유지 시간(워밍업 2분 + 측정 10~15분)은
nano에서 줄여 **회차당 주문 5분**으로 실행했다.

| 회차 | SSE 연결 | 주문 | 주문 p95 | 전달 지연 p50 / p95 / 최대 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 (비활성 기준선) | 50/초, 15,000건 | 10.8ms | — | |
| 1 | 100 | 5/초, 1,501건 | 16.9ms | 605 / 1,045 / 1,247ms | 놓친 알림 0 (128,400쌍) |
| 2 | 200 | 50/초, 15,000건 | 10.6ms | 518 / 984 / 7,211ms | 놓친 알림 0 (2,575,800쌍) |

- 모든 회차에서 연결 성공 100%(ready p95 18ms 이하), 서버 쪽 조기 종료·전송 실패·전송 정체 0,
  주문 실패 0, `verify.sql` 음수재고·초과판매 0행. HikariCP pending 최대 0, timeout 0.
- **SSE 활성 시 주문 p95 악화 없음**: 같은 50/초 조건에서 0회차 10.8ms → 2회차 10.6ms(-1.6%). 13.2 기준
  (10% 이내)을 이 환경에서는 만족했다.
- 전달 지연 p95 약 1초는 서버의 1초 병합 창(`coalesce-window`) 때문이다. 13.1 목표(평시 2초, 피크 3초)
  안쪽이다. 최대 7.2초는 2회차의 단발 아웃라이어(p99 1,025ms)로 원인은 확인하지 않았다(GC 추정, 검증 안 함).
  지연은 주문 응답 수신 시각 기준 근사값이다(`analyze.mjs` 주석).
- 리소스: backend CPU 평균 0회차 24% / 1회차 8% / 2회차 24%. **메모리 최대 92.6% / 97.8% / 99.99%** —
  2회차는 512MiB 한도에 닿았으나 재시작 0회, OOM-kill 없음. SSE 200 연결이 nano에서 메모리 여유가
  거의 없는 상한이다.
- 2회차 SSE 지표(5분): 변경 신호 14,453 → 병합 2,280,645 → 전송 198,855건.

**GR-163 기준선 — 전송 시 공개 여부 재검증 쿼리**(`countPublicDropsForSubscription`, `pg_stat_statements`)

| 회차 | 쿼리 호출 | 구독 시점 | 전송 시점 | 주문 1건당 | HikariCP 커넥션 획득 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 0 | 0 | 57,564 |
| 1 | 24,561 | 100 | 24,461 | 16.3 | 29,871 |
| 2 | 58,264 | 200 | 58,064 | 3.9 | 114,097 |

- 전송 시점 호출은 연결 수 × 초당 1회(병합 창)가 상한이라, 2회차는 거의 상한(200 × 300초 = 60,000)에 닿았다.
- 쿼리 자체는 회당 0.01~0.03ms로 가볍지만 매번 커넥션 획득 + `BEGIN READ ONLY`가 따라온다.
  2회차 커넥션 획득은 같은 주문량의 0회차보다 약 2배(+56,533)이고 그 대부분이 이 쿼리다.
- 이 환경(로컬 DB, 풀 여유)에서는 주문 p95에 영향이 드러나지 않았다. GR-163의 효과는 응답시간보다
  DB 왕복·커넥션 획득 수로 비교한다.

**정리·제한 동작**

- 클라이언트 200개 일괄 종료 후 서버 연결·구독·pending이 0이 되기까지 약 57초(52초 시점 65개 잔존).
  서버는 다음 쓰기(heartbeat 15초)가 실패해야 끊긴 연결을 알아서, 13.2 목표(60초 후 0)에 근소하게 들어왔다.
- 같은 IP 21번째 연결 429(`reason=ip`), 60초 창 31번째 요청 429(`reason=rate`), 201번째 연결 503(`capacity`)
  모두 기대대로 동작. 서버는 IP 제한을 전체 상한보다 먼저 검사하므로, 503을 보려면 IP 상한을 200보다 크게
  둬야 한다(첫 시도에서 IP 상한 200으로 429가 먼저 나서 오버라이드 기본값을 1000으로 고쳤다).

**한계**: 부하 발생기가 모두 한 IP라 IP 제한을 오버라이드했고, 유지 시간을 5분으로 줄였으며, 느린 수신자·
수명 만료 재연결·프록시 경유는 다루지 않았다(GR-113 범위). k6와 Node가 같은 Mac 시계를 써서 시계 오차는
없지만, 지연은 커밋 시각이 아닌 주문 응답 수신 시각 기준 근사값이다.
