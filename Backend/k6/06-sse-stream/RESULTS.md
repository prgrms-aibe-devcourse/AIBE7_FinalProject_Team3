# SSE 동시 연결 부하테스트 결과 (GR-157)

> 운영 캐파시티 수치가 아니라 nano(1vCPU/512MiB) 환경의 **하한선 검증**이다(`../RESULTS.md` 공통 전제와 같다).
> 실행 방법은 `../README.md` 6절.

## 결론

**스왑을 끈 nano에서 SSE 200 연결 + 주문 50/초는 현재 JVM 설정(`-Xmx384m`)으로는 OOM으로 죽는다.** 150 연결까지는
버텼다(메모리 최대 98.5%). JVM 옵션만 `-Xmx256m -Xss512k`, `MALLOC_ARENA_MAX=2`로 바꾸면 200 연결도 버텼다(1회, 메모리
최대 97.6%). 실제 사용 힙은 150MiB 이하로 작고, 힙 상한이 컨테이너 크기에 비해 커서 한도를 넘은 것으로 판단한다.
처음 측정(아래 "1차 측정")은 `compose.loadtest.yaml`이 `memswap_limit` 없이 `mem_limit`만 둬서, Docker 기본값대로
메모리만큼(512MiB) 스왑이 허용된 상태였다. 200 연결이 512MiB 한도에 붙은 채 OOM 없이 버틴 것은, 스왑을 끄자 같은 조건이 OOM-kill된 점으로 보아 스왑 덕분이었다고 판단한다(당시 스왑 사용량은 기록하지 않았다).
t3.nano는 기본 스왑이 없으므로 `memswap_limit: 512m`으로 스왑을 끄고 다시 측정한 결과를 이 문서의 기준으로 삼는다.

- 버틴 구간(100·150 연결)에서는 연결 실패·알림 유실·재고 이상 **미발생**, SSE 활성 시 주문 p95 악화 없음,
  전달 지연 p95 약 1초(병합 창).
- 통과 회차도 메모리가 95~98.5%로 여유가 거의 없다. 회차마다 컨테이너가 거친 이전 부하가 달라 연결 수별 메모리를
  직접 비교하지는 않았다.
- 전송 시 재검증 쿼리는 150 연결 기준 5분간 약 4.3만 회 실행돼 GR-163 기준선으로 남긴다.

## 상세

### 스왑 제거 재측정 (기준)

실행일 2026-10-26. `memswap_limit: 512m`(스왑 0) 외 조건은 아래 1차 측정과 같다. 모든 회차 주문 50/초 × 5분,
`run.sh`로 실행했고 측정 중 backend cgroup `memory.swap.current`를 3초 간격으로 기록해 스왑 0을 확인했다.
200 회차는 컨테이너 재기동 + 워밍업(20/초 × 60초) 직후, 나머지는 재기동 + 워밍업 뒤 연달아 실행했다.

| SSE 연결 | 결과 | 주문 p95 | 전달 지연 p50 / p95 / 최대 | backend 메모리 최대 |
| --- | --- | --- | --- | --- |
| 0 (비활성 기준선) | 통과, 15,000건 | 10.7ms | — | 95.1% |
| 100 | 통과, 15,001건 | 11.2ms | 523 / 988 / 1,171ms | 97.9% |
| 150 | 통과, 15,001건 | 9.8ms | 519 / 986 / 1,066ms | 98.5% |
| 200 | **OOM-kill** (주문 시작 24초) | — | — | 99.8% 후 종료 |

- 통과 회차: 주문 실패 0, 서버 쪽 연결 종료 0, 놓친 알림 0(150 연결 1,926,960쌍), `verify.sql` 이상 0행,
  HikariCP timeout 0. 주문 p95는 SSE 비활성 대비 악화 없음(13.2 기준 10% 이내).
- 200 회차: SSE 200 연결이 ready된 시점 메모리가 이미 93%(477~481MiB)였고, 주문 투입 후 98%를 넘어
  24초 만에 512MiB에 닿아 커널 OOM-kill(`OOMKilled=true`). 그 전까지 성공한 주문 1,182건의 재고 정합성은
  이상 없었다. 1회만 실행했다.
- 151~199 사이 정확한 한계는 찾지 않았다. 아래 JVM 옵션 조정으로는 200 연결도 버텼다.

**JVM 옵션 조정 실험 (200 연결 재시도)**

OOM 직전 JVM 지표를 보면 실제 사용 힙은 147MiB였지만, `-Xmx384m`(힙 상한 371MiB) + 힙 외 영역 약 215MiB
(Metaspace 140MiB, 코드 캐시 약 60MiB) + JVM 밖 네이티브 메모리를 합치면 512MiB를 넘게 쓸 수 있는 설정이었다.
부하로 확보 힙이 188MiB까지 늘자 컨테이너 한도를 넘었다. 코드는 그대로 두고 임시 오버라이드로
`JDK_JAVA_OPTIONS=-Xmx256m -Xss512k`, `MALLOC_ARENA_MAX=2`만 바꿔 같은 조건(스왑 0, 200 연결, 50/초 × 5분)을 다시 돌렸다.

| 항목 | 결과 |
| --- | --- |
| 생존 | **통과** — OOM-kill 0, 재시작 0, 서버 쪽 연결 종료 0 |
| 주문 | 15,001건 실패 0, p95 10.0ms(최대 521ms) |
| 전달 지연 | p50 521 / p95 986 / 최대 4,134ms, 놓친 알림 0(2,587,200쌍) |
| 메모리 | 컨테이너 최대 97.6%, 힙 사용 최대 144MiB / 확보 198MiB, 힙 외 확보 219MiB |
| GC | minor 317회/5분(누적 정지 0.96초), full GC 0회 |
| CPU | 평균 28% / 최대 78% |

- 200 연결의 OOM은 SSE 코드가 아니라 **JVM 메모리 예산 설정**(힙 상한이 컨테이너에 비해 큼) 문제로 판단한다.
- 다만 1회 실행이고 메모리 최대 97.6%로 여유가 여전히 작다. 세 옵션 중 어느 것이 효과를 냈는지는 나눠 보지 않았다.
- 이 옵션은 레포에 반영하지 않았다. 운영 배포(`Dockerfile`, `deploy/`)에는 JVM 메모리 옵션이 없어 기본값(사용 가능
  메모리의 25%를 힙 상한)으로 돌고, 부하테스트의 `-Xmx384m`도 운영과 다른 값이다. 운영 JVM 옵션은 별도로 정한다.

**GR-163 기준선 — 전송 시 공개 여부 재검증 쿼리**(`countPublicDropsForSubscription`, `pg_stat_statements`)

| SSE 연결 | 쿼리 호출 | 구독 시점 | 전송 시점 | 주문 1건당 | HikariCP 커넥션 획득 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 0 | 0 | 59,789 |
| 100 | 28,984 | 100 | 28,884 | 1.9 | 85,815 |

- 전송 시점 호출은 연결 수 × 초당 1회(병합 창)가 상한이다(150 × 300초 = 45,000).
- 쿼리 자체는 회당 0.01~0.08ms로 가볍지만 매번 커넥션 획득 + `BEGIN READ ONLY`가 따라온다. 150 연결의
  커넥션 획득은 같은 주문량의 SSE 비활성보다 약 1.7배(+42,761)다.
- 주문 p95에는 영향이 드러나지 않았다. GR-163은 **150 연결**(`run.sh <이름> 150 50 300`)로 전후를 비교하고,
  효과는 응답시간보다 DB 왕복·커넥션 획득 수로 본다.

### 1차 측정 (스왑 허용 — 참고용)

> 이 절의 메모리·생존 판정은 스왑이 허용된 상태라 nano 판정 근거로 쓰지 않는다. 응답시간·전달 지연·
> 쿼리 호출 수는 참고로 남긴다.

실행일 2026-10-26. `../RESULTS.md`의 다른 시나리오와 같은 nano 제한(backend 1 vCPU/512MiB, `-Xmx384m`)이며, 이 시나리오만
`compose.loadtest.yaml`의 SSE IP 제한 오버라이드와 postgres `pg_stat_statements`를 함께 썼다.
SSE 연결은 Node(`sse-clients.mjs`), 주문은 로컬 k6 v2.3.0(`order-load.js`, 결제 없이 주문 생성만)으로
같은 Mac에서 실행했다. 연결 구성은 상세 구독 70%(인기 상품 1개) / 목록 구독 30%(24개),
주문은 80%가 인기 상품. REALTIME_STOCK.md 13.2의 유지 시간(워밍업 2분 + 측정 10~15분)은
nano에서 줄여 **회차당 주문 5분**으로 실행했다.

| 회차 | SSE 연결 | 주문 | 주문 p95 | 전달 지연 p50 / p95 / 최대 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 (비활성 기준선) | 50/초, 15,000건 | 10.8ms | — | |
| 1 | 100 | 5/초, 1,501건 | 16.9ms | 605 / 1,045 / 1,247ms | 놓친 알림 0 (128,400쌍) |
| 2 | 200 | 50/초, 15,000건 | 10.6ms | 518 / 984 / 7,211ms | 놓친 알림 0 (2,575,800쌍) |

- 모든 회차에서 연결 성공 100%(ready p95 18ms 이하), 서버 쪽 조기 종료·전송 실패·전송 정체 0,
  주문 실패 0, `verify.sql` 음수재고·초과판매 0행. HikariCP pending 최대 0, timeout 0.
- **SSE 활성 시 주문 p95 악화 없음**: 같은 50/초 조건에서 0회차 10.8ms → 2회차 10.6ms(-1.6%). 13.2 기준
  (10% 이내)을 이 환경에서는 만족했다.
- 전달 지연 p95 약 1초는 서버의 1초 병합 창(`coalesce-window`) 때문이다. 13.1 목표(평시 2초, 피크 3초)
  안쪽이다. 최대 7.2초는 2회차의 단발 아웃라이어(p99 1,025ms)로 원인은 확인하지 않았다(GC 추정, 검증 안 함).
  지연은 주문 응답 수신 시각 기준 근사값이다(`analyze.mjs` 주석).
- 리소스: backend CPU 평균 0회차 24% / 1회차 8% / 2회차 24%. 메모리 최대 92.6% / 97.8% / 99.99% —
  2회차는 512MiB 한도에 닿았으나 OOM-kill이 없었다. 스왑을 끈 재측정에서는 같은 조건이 OOM-kill됐다.
- 2회차 SSE 지표(5분): 변경 신호 14,453 → 병합 2,280,645 → 전송 198,855건.

### 정리·제한 동작 (1차 측정 때 확인)

- 클라이언트 200개 일괄 종료 후 서버 연결·구독·pending이 0이 되기까지 약 57초(52초 시점 65개 잔존).
  서버는 다음 쓰기(heartbeat 15초)가 실패해야 끊긴 연결을 알아서, 13.2 목표(60초 후 0)에 근소하게 들어왔다.
- 같은 IP 21번째 연결 429(`reason=ip`), 60초 창 31번째 요청 429(`reason=rate`), 201번째 연결 503(`capacity`)
  모두 기대대로 동작. 서버는 IP 제한을 전체 상한보다 먼저 검사하므로, 503을 보려면 IP 상한을 200보다 크게
  둬야 한다(첫 시도에서 IP 상한 200으로 429가 먼저 나서 오버라이드 기본값을 1000으로 고쳤다).

### 한계

부하 발생기가 모두 한 IP라 IP 제한을 오버라이드했고, 유지 시간을 5분으로 줄였으며, 느린 수신자·
수명 만료 재연결·프록시 경유는 다루지 않았다(GR-113 범위). k6와 Node가 같은 Mac 시계를 써서 시계 오차는
없지만, 지연은 커밋 시각이 아닌 주문 응답 수신 시각 기준 근사값이다.
