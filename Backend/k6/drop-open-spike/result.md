# 드롭 오픈 순간 스파이크 (drop-open-spike, GR-152)

> 공통 실행 환경·전제는 `../README.md` 참고.

## ⚠️ 2026-10-26(이어서): G1GC 명시 재검증 — nano에서 또 OOM-kill(세 번째 뒤집힘)

바로 아래 섹션(`cpus: 2`, G1GC 암묵)에서 통과했던 것과 같은 설정에, 비교를 위해
`JDK_JAVA_OPTIONS`에 `-XX:+UseG1GC`를 명시하고 다시 돌리자 **이번엔 또 죽었다**
(stock-race→idempotency→expiry를 먼저 돌려 메모리가 94.79%까지 올라간 상태에서
시작). `docker inspect` → `OOMKilled: true`. 드롭은 WISH 상태 그대로 멈춰
(`DropTransitionScheduler`가 전환하기 전에 죽음) 주문은 0건, 재고 변동도 0건이라
데이터 손상은 없었다. micro(1GiB)는 같은 재검증에서 체크 11232/11232(100%)
통과, 메모리 58.14%로 전혀 위태롭지 않았다.

**결론: 같은 `cpus: 2` 설정인데 이번 실행은 죽고 전엔 안 죽었다.** 다만 두 실행의
시작 조건이 같지 않다 — 이번엔 stock-race→idempotency→expiry를 먼저 돌려 메모리가
94.79%인 상태에서 시작했고, 아래 통과한 실행은 컨테이너를 새로 띄운 직후였다. 그래서
이번 결과만으로 "G1GC 명시 여부가 결과를 바꿨다"거나 "이 조합이 비결정적으로 죽는다"고
단정하지 않는다. 이전 재검증에서 "98.63%로 간신히 버텼다, 안전하다는 뜻 아니다"라고
적어둔 경고와는 같은 방향이다 — 메모리 여유가 거의 없는 조합이라는 것 — 하지만 컨테이너를
매번 새로 띄우고 시작 메모리를 기록한 반복 검증 전까지는, 이 조합이 통과할지 죽을지를
결정짓는 게 시작 메모리인지 다른 요인인지 결론 내리지 않는다.

## ✅ 2026-10-26 재재검증: `cpus: 2`(올바른 t3.nano 스펙) 적용 후 통과 — 결론 다시 뒤집힘

바로 아래 섹션(`cpus: 1`)에서 OOM-kill로 죽었던 바로 그 설정에, AWS 공식 스펙을
다시 확인해 보니 t3.nano는 **vCPU 2개**였다(nano~large 전부 공통, 차이는 메모리와
베이스라인 CPU%뿐 — `../README.md` 참고). `compose.loadtest-nano.yaml`의 `cpus`를
2로 고치고 같은 시나리오를 다시 돌리자 **이번엔 서버가 안 죽었다**.

- 체크 12816/12816(100%) 성공, `http_req_failed` 0.00%, 5xx **0건**
- `docker inspect` → `OOMKilled: false`, 컨테이너 계속 `running`
- 응답시간: avg 13.22ms, p95 43.31ms, 최대 1.16s — `cpus: 1`일 때(p95 1.6s, 최대
  12.8s)보다 훨씬 빠름. CPU 코어가 하나 더 생기니 요청을 더 빨리 처리해서 커넥션·
  버퍼가 오래 쌓이지 않았고, 그게 메모리 피크를 낮춘 걸로 보인다
- 단, **메모리는 505MiB/512MiB(98.63%)까지 올라가 거의 한계치**였다 — 안 죽었을
  뿐 여유는 거의 없다. 이 실행 전에 이미 stock-race·idempotency·expiry를 같은
  컨테이너에서 연달아 돌려 기저 메모리가 쌓인 상태였던 점도 감안해야 한다
  (steady-read 지점. ../README.md의 공통 전제 참고)
- `verify.sql` 음수재고·초과판매 0행, 생성 주문 30건

**결론(다시 갱신)**: CPU를 올바른 스펙(2개)으로 고치니 이 시나리오는 nano에서도
서버가 죽지 않는다. `cpus: 1`로 쟀던 "서버가 죽는다"는 결론은 **CPU를 실제보다
적게 줘서 생긴 인공적인 결과**였다. 다만 메모리가 98.63%까지 올라간 건 사실이라,
운영 수준 재고·VU 수가 조금만 더 커지면 여전히 위험할 수 있다 — "안전하다"가
아니라 "이번 조건에서는 간신히 버텼다"로 읽어야 한다.

## ⚠️ 2026-10-26 재검증: `memswap_limit` 추가 후 OOM-kill로 결론 뒤집힘 — 이때는 아직 `cpus: 1`(틀린 설정)

> 이 재검증도 `cpus: 1`로 제한된 상태(실제 t3.nano는 vCPU 2개)에서 돌아갔다. OOM-kill은
> 메모리 문제라 CPU 코어 수와는 무관해 이 결론 자체는 바뀌지 않지만, 참고로 남긴다.
> CPU 코어 수를 2로 고친 건 이후 작업(`compose.loadtest-nano.yaml`, GR-154 result.md 참고)이었다.

`compose.loadtest.yaml`이 `mem_limit`만 두고 `memswap_limit`을 지정하지 않으면,
호스트에 스왑이 켜져 있을 때 도커가 컨테이너에 메모리 한도의 최대 2배(여기선 1GiB)까지
스왑을 얹어준다. 아래 2026-10-23 결과는 전부 이 상태(호스트 스왑 켜짐)에서 나온
것이라, 실제로는 선언한 512MB가 아니라 최대 1GB에 가까운 환경에서 돈 것이었다.

`memswap_limit: 512m`을 `mem_limit`과 같게 고정해 스왑을 완전히 차단하고
(운영 t3.nano도 기본적으로 스왑이 없다) 같은 시나리오를 다시 돌리자, **이번에는
서버가 테스트 도중 OOM-kill로 죽었다**(`docker inspect` `OOMKilled: true`,
`DropTransitionService`의 WISH→GRAB 전환 로그 직후 로그가 끊기고 프로세스 종료).
k6 쪽에는 목록/상세 조회 체크 실패로 나타남(목록 200: 91%, 상세 200: 90%,
즉 각 9~10%가 컨테이너 다운 이후의 연결 실패).

- 체크 3953건 중 91.32% 성공(목록 200 91%, 상세 200 90%, 5xx 자체는 0건 —
  실패는 5xx가 아니라 컨테이너가 죽은 뒤의 연결 거부/타임아웃)
- `docker inspect backend-backend-1` → `OOMKilled: true`, 컨테이너 `exited`
  (재시작 정책이 없어 자동 재기동도 안 됨 — 수동으로 `docker compose up -d backend` 필요)
- 다행히 **데이터 정합성은 깨지지 않음**: 죽기 전까지 커밋된 상태 기준
  `verify.sql` 음수재고·초과판매 0행, 생성 주문 30건 그대로. 크래시가 나도
  진행 중이던 트랜잭션이 어중간하게 반영되지는 않았다는 뜻
- 재현 조건: 목록/상세 조회 0→50 VU 램프업 + 오픈 시각 구매 VU 30명 동시 주문,
  재고 200개(이전과 동일 시나리오 설정 그대로)

**결론(갱신)**: nano(512MB, 스왑 없음) 스펙에서 드롭 오픈 스파이크는 **서버가
죽는다**. 2026-10-23에 "통과"로 적었던 건 호스트 스왑이 만든 가짜 여유 메모리
덕분이었다. 운영 t3.nano로 간다면 이 시나리오는 그대로 재현될 가능성이 높아,
별도 버그/용량 이슈로 떼서 힙·동시 조회 VU 수 조정 또는 더 큰 인스턴스 사용을
검토해야 한다(GR-154/GR-155 범위 밖, 별도 트래킹 필요).
