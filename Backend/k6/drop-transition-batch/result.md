# 드롭 상태 전이 배치 부하 (drop-transition-batch, GR-171)

> 공통 실행 환경·전제는 `../README.md` 참고. 이 시나리오는 HTTP 부하가 아니라
> `DropTransitionScheduler`(10초 `fixedDelay`) 한 번이 `DropTransitionService`
> (`BATCH_SIZE=500`)·`DropTransitionBatchService`(`FOR UPDATE SKIP LOCKED`)로
> 대량 DROP을 전이시키는 DB 배치
> 처리 시간을 보는 것이라 k6를 쓰지 않고 seed.sql 실행 + DB 상태(WISH→GRAB) 폴링으로
> 측정했다. 메일 발송 자체의 부하(수신자 규모, SMTP 처리량)는 GR-170 범위이고, 여기서는
> "전이 이벤트 발행이 배치 루프 자체를 지연시키는지"만 비교군으로 본다.
>
> 아래는 `docker compose -f compose.yaml -f compose.loadtest-micro.yaml up --build
> backend`(AWS t3.micro 수준: vCPU 2개, 1GiB, `-Xmx550m`)로 돌린 결과다.

## 2026-10-27 측정: 기준선(WISH 없음) vs WISH 포함(메일 트리거)

DROP 600개(`BATCH_SIZE=500`보다 많아 `drain()`이 내부적으로 500+100, 두 번 왕복하게
만든다)를 같은 `sale_starts_at`으로 동시 전이 대상에 올렸다. `sale_starts_at`이
판매 임박 알림 리드타임(10분)보다 가까워 같은 실행에서 "판매 임박"과 "판매 시작"
배치가 모두 돈다(GR-170과 같은 현상).

### 기준선 — `seed.sql` (WISH 없음)

| 배치 | 대상 | 로그 시각 | 비고 |
| --- | --- | --- | --- |
| 판매 임박 | 600건 | 01:33:16.794 | 수신자 0명이라 메일 발송 요청 로그 없음(조기 반환) |
| 판매 시작 | 600건 | 01:33:36.854 | `sale_starts_at`(01:33:35.970) 대비 감지 지연 0.88초 |

- **완료조건 1·2**: 600건 모두 **같은 스케줄러 tick, 단일 `transition()` 호출 안에서**
  처리됐다 — 로그가 각 배치당 한 줄(`GRAB 600건`)로만 남는다. `drain()`이
  `processed < BATCH_SIZE`가 될 때까지 내부 반복을 멈추지 않는 설계라, 500+100으로
  나뉘어도 호출자 입장에서는 "한 번의 실행"이다. **다음 주기로 밀리는 DROP은 없었다.**
- DB 폴링(300ms 간격)으로는 "시작"과 "완료" 사이 변화가 한 틱 안에서 보이지 않았다
  (처리 소요가 폴링 해상도보다 작다) — 600건 배치가 **수백 ms 미만**으로 끝난다는 뜻이다.
- 락 경합·데드락 로그 없음. `FOR UPDATE SKIP LOCKED` + 단일 스케줄러 스레드(동시
  실행 인스턴스 없음) 조합에서는 애초에 경합이 생길 수 없는 구조다(여러 인스턴스를
  동시에 띄우는 시나리오는 범위 밖).

### 비교군 — `seed-with-wish.sql` (DROP당 WISH 50명, 메일 트리거 포함)

| 배치 | 대상 | 로그 시각 | 간격 |
| --- | --- | --- | --- |
| 판매 임박 발송 요청 (1/2) | 500건, 25000명 | 01:33:57.226 | — |
| 판매 임박 발송 요청 (2/2) | 100건, 5000명 | 01:33:57.332 | +106ms |
| 판매 임박 배치 완료 로그 | 600건 | 01:33:57.345 | +13ms |
| 판매 시작 발송 요청 (1/2) | 500건, 25000명 | 01:34:17.748 | — |
| 판매 시작 발송 요청 (2/2) | 100건, 5000명 | 01:34:17.888 | +140ms |
| 판매 시작 배치 완료 로그 | 600건 | 01:34:17.891 | +3ms |

- **완료조건 3(이벤트 발행이 배치 트랜잭션을 지연시키는지)의 답은 "그렇다, 그러나
  이번 규모에서는 작다"다.** `WishSaleNoticeMailListener`는
  `@TransactionalEventListener(phase = AFTER_COMMIT)`라 메일을 "비동기로" 보내지만,
  그 앞단의 **수신자 조회(`findSaleStartMailRecipients`)와 BCC 묶음 생성은 동기
  호출**이고, AFTER_COMMIT 콜백은 커밋한 스레드(=스케줄러 스레드)에서 즉시 실행된다.
  로그에서 보듯 `startGrabBatch`의 500건짜리 서브배치가 커밋되면 그 자리에서 바로
  수신자 25000명 조회·BCC 묶음(500통)까지 끝내고 나서야 `drain()`이 다음 서브배치
  (100건)로 넘어간다. 즉 **메일 수신자 조회가 다음 DB 서브배치 실행을 지연시킨다.**
- 지연 폭은 이번 실행에서 서브배치당 약 106~140ms — 기준선과 비교해 추가된 시간이다.
  기준선도 `dispatch()`가 `findSaleStartMailRecipients` 조회 자체는 똑같이 실행하지만
  (코드상 수신자 수와 무관하게 항상 호출됨), 결과가 빈 리스트라 그 직후 조기 반환하고
  BCC 묶음·큐 제출로 이어지지 않는다 — 그래서 조회 비용은 양쪽 모두에 있고, 위 지연은
  "수신자 25000명·5000명을 실제로 묶고 큐에 넣는 단계"가 추가된 몫이다. 600건·수신자
  30,000명 규모에서는
  10초 주기 안에서 무시할 만한 수준이지만, **수신자 규모가 커질수록(DROP당 WISH가
  GR-170처럼 수만 명이면) 이 지연도 비례해서 커진다** — 그 지점부터는 전이 배치
  자체의 처리 시간이 늘어나 다음 스케줄러 tick(판매 종료 등)까지 밀어낼 수 있다.
  GR-170에서 실측한 "앞선 DROP의 메일 발송이 끝날 때까지 뒤 DROP의 알림이 큐에서
  기다린다"는 현상과 같은 원인(동기 수신자 조회 + 단일 처리 경로)이, 여기서는 "메일
  큐"가 아니라 "DB 전이 배치 자체의 진행"에 영향을 준다는 점이 다르다.
- **완료조건 1·2는 비교군에서도 유지됐다**: 600건 모두 같은 tick에서 완료, 다음
  주기로 밀린 DROP 없음. 수신자 조회가 추가한 지연(수백 ms)은 10초 주기 예산
  안에서 전혀 문제가 되지 않았다.
- 메모리: 30,050명 분량의 더미 사용자·WISH를 추가로 처리한 뒤에도 798.6MiB/1GiB
  (78%) — 여유 있음. `OutOfMemory`·경고 로그 없음.

## 결론

- `BATCH_SIZE=500`과 `FOR UPDATE SKIP LOCKED` 설계 덕분에, 같은 시각에 전이
  대상이 되는 DROP이 수백 건으로 늘어나도 **한 스케줄러 tick 안에서 전부 처리되고
  다음 주기로 밀리지 않는다.** 순수 DB 배치 처리(수신자 없음)는 600건을 수백 ms
  미만에 끝낸다.
- 전이와 함께 발행되는 메일 알림 이벤트는 "비동기 발송"이라는 이름과 달리, **수신자
  조회·BCC 묶음 단계는 스케줄러 스레드에서 동기로 실행돼 배치 루프를 지연시킨다.**
  이번 규모(DROP 600건, 수신자 30,000명)에서는 서브배치당 100~140ms 수준으로
  작았지만, 수신자 규모가 훨씬 커지면(예: GR-170의 수만 명 단위) 이 지연이 커져
  배치 전체 소요 시간을 늘릴 수 있다 — 지금 당장 코드를 고칠 근거는 아니고, GR-170
  result.md에 적은 "지연 리스크"와 같은 갈래로 계속 지켜볼 지점이다.
- 락 경합이나 데드락은 관찰되지 않았다. `FOR UPDATE SKIP LOCKED`가 의도대로
  동작해, 같은 트랜잭션 안에서 처리 중인 행과 다음 서브배치 대상 행이 겹치지 않는다
  (애초에 같은 스레드가 순차 실행하므로 동시 경합 자체가 발생할 조건이 아니다).
  여러 백엔드 인스턴스가 동시에 스케줄러를 돌리는 수평 확장 시나리오는 범위 밖이다.
- t3.micro(vCPU 2개, 1GiB) 기준으로도 메모리·CPU 압박 없이 처리됐다.

## 재현 방법

```powershell
# 사전: docker compose -f compose.yaml -f compose.loadtest-micro.yaml up -d --build backend,
#       common/accounts-seed.sql 1회 실행
powershell -File k6/drop-transition-batch/measure.ps1              # 기준선(WISH 없음)
powershell -File k6/drop-transition-batch/measure.ps1 -WithWish    # 비교군(메일 트리거 포함)
```

서브배치 횟수(500+100)와 각 단계 간 간격은 백엔드 로그로 확인한다:

```bash
docker compose logs backend --since 2m | grep -E "DropTransitionService|WishSaleNoticeMailListener"
```
