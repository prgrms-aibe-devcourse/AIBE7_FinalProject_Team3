# 결제 배치 롱런 soak (payment-batch-soak, GR-154)

> 공통 실행 환경·전제는 `../README.md` 참고. MockPaymentGateway 전제는 스크립트 상단 주석 참고.

## 2026-10-26: 스크립트 검증 완료, 실제 2~4시간 soak는 미실행 (nano 메모리 문제로 보류)

**스크립트 버그 2건 발견·수정**(90초/16분 스모크 중 실제로 재현):
1. `access_token` TTL이 15분(`grab.auth.access-token.ttl`)인데 VU당 로그인을 한 번만 하면
   soak 중간부터 전부 401로 깨짐 — VU 세션을 10분마다 재로그인하도록 수정.
2. `login()` 실패(서버 다운 등) 시 예외가 그대로 전파돼 `sleep` 없이 다음 반복으로 넘어가,
   죽은 서버에 무한 재시도를 퍼붓는 버그 — 16분 실행 중 백엔드가 OOM-kill된 뒤 **초당 2500회
   이상, 16분간 242만 회** 재시도가 발생한 걸로 확인. `try/catch`로 감싸 실패해도 반드시
   `sleep` 후 다음 반복으로 가게 수정.

**90초 스모크(수정 전) 통과**: 체크 137/137(100%), threshold `soak_failures_total count==0`
통과, 재고 정합성 이상 없음.

**16분 실행(배치 만료 확인용, 수정 전) 중 15분 지점에서 발견**: access_token 만료로 인증
실패 다발(`JwtAuthenticationFilter: Access Token 거부: reason=EXPIRED`). 토큰 갱신 로직
추가로 수정.

**버그 수정 후 재검증 중 더 근본적인 문제 발견**: 컨테이너를 완전히 새로 기동하고(스왑 차단된
nano 512MB) VU 3명의 가벼운 트래픽만 줬는데도 **약 2분 만에 다시 OOM-kill**됐다(16분
재검증, 5분 재검증 모두 동일하게 재현). 무한 재시도 버그는 더 이상 발생하지 않았지만(정상
속도로 실패 처리), 2분 만에 죽는다는 건 배치가 오래 돌면서 서서히 새는 누수가 아니라 —
**현재 애플리케이션의 기본 메모리 사용량 자체가 이미 nano(512MB, 스왑 없음) 한도에 거의
다 차 있어서, 가벼운 트래픽만 얹혀도 바로 OOM이 나는 상태**로 보인다. 이는
[drop-open-spike](../drop-open-spike/result.md)에서 확인한 OOM-kill과 같은 근본 원인(nano
메모리 여유 부족)일 가능성이 높다.

## 2026-10-26(이어서): AWS 스펙 재조사 + nano vs micro 16분 동시 실행

**CPU 설정 오류 발견·수정**: AWS 공식 스펙을 다시 확인한 결과 t3.nano/micro/small은
**전부 vCPU 2개**이고(nano~large가 공통, 차이는 메모리와 베이스라인 CPU 성능 vCPU당
5%/10%/20%뿐), `compose.loadtest.yaml`(현 `compose.loadtest-nano.yaml`)이
`cpus: 1`로 잘못 제한하고 있었다(GR-149 이슈 설명 자체도 "1vCPU"로 잘못 적혀
있었음). `cpus: 2`로 수정하고, t3.micro(vCPU 2개·1GiB)용 비교 환경을 추가해
같은 VU 3명 soak를 nano·micro에 동시에 16분씩 돌렸다. (이 비교 실험 때는
8081 포트의 별도 `backend-micro` 서비스로 둘을 동시에 띄웠는데, 이후
`compose.loadtest-nano.yaml`/`compose.loadtest-micro.yaml`로 정리하면서 둘 다
같은 `backend` 서비스·포트 8080을 쓰고 하나만 골라 합치는 구조로 바꿨다 —
아래 수치는 비교 실험 당시 그대로의 기록이다.)

**nano(512MB, cpus 2로 수정 후)**: 여전히 **9분(56%) 지점에서 OOM-kill**됨. `cpus: 1`일
때(새 컨테이너 기준 약 2분)보다는 오래 버텼지만, CPU를 늘려도 결국 죽는다는 건 이게
CPU가 아니라 **순수 메모리 문제**라는 걸 다시 확인한 것. 참고로 트래픽이 전혀 없는
기동 직후 상태만 봐도 이미 408MB/512MB(79.74%)로, GR-149 당시(2026-10-23) 기록된
374MB/512MB(73%)보다 34MB 늘어나 있다 — 그 사이 merge된 기능들(GR-132 프로필
이미지, GR-142·165 수요 분석, GR-160 마이페이지 등)로 유휴 메모리 자체가 계속
늘고 있다는 뜻이다.

**micro(1GiB, cpus 2, 힙 768m)**: **16분 전체 완주**. 체크 1532/1532(100%) 성공,
`soak_failures_total count==0` 통과, OOM 없음. 메모리는 16분 내내 **467MB→479MB
(45.7%→46.8%) 범위에서 평평하게 유지**돼 눈에 띄는 증가 추세가 없었다(그래프 상 누수
의심 신호 없음). `verify.sql` 결과:
- 재고 정합성 위반 0행
- 최종 주문 상태: `PAID` 229건, `EXPIRED` 140건, `CANCELED` 99건, `PAYMENT_PENDING`
  198건(아직 10분 안 지난 것들)
- `stuck_past_deadline` 0건 — 배치가 밀리지 않고 만료 처리를 따라감
- `unresolved_reconciliation` 0건 — 보정 대상 없음

처음으로 **결제 대기 만료(`EXPIRED` 140건)가 실제로 배치에서 처리되는 걸 눈으로 확인**했다
(10분 미만 테스트는 이 경로 자체가 실행될 수 없었다). 다만 VU 3명·16분은 여전히 "몇 시간,
더 많은 동시 사용자" 전제의 축소판이라, 장시간 누수 여부를 최종 확정하려면 더 긴 시간(또는
더 높은 VU)으로 재검증이 필요하다.

## 결론

스크립트(`payment-batch-soak.js`, `seed.sql`, `verify.sql`, `monitor-resources.sh`)는
완성·검증됐고 MockPaymentGateway로 토스를 안 때리는 것도 확인했다. **nano(512MB)에서는
GR-154 본연의 목적(장시간 돌려 배치의 점진적 누수를 본다)을 수행할 수 없다** — 트래픽
유무와 무관하게 기동 직후부터 이미 메모리가 빠듯해서(79.74%), 가벼운 트래픽만 얹혀도
수 분 안에 OOM이 난다(CPU를 올바른 값(2)으로 고쳐도 마찬가지). **micro(1GiB)에서는
16분 동안 메모리 증가 추세 없이 정상 완주**했고, 배치(만료 처리 포함) 전 과정이 정상
동작하는 것도 확인했다 — 다만 VU 3명·16분 수준에서는 누수 징후가 안 보인다는 것이지,
운영 규모·장시간에서도 그렇다고 단정할 근거는 아직 아니다.
