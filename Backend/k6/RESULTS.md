# nano 환경 부하테스트 결과 (GR-151, GR-152)

> 이 결과는 **운영 캐파시티 수치가 아니라 하한선 검증**이다. 목표는 운영(t3.small,
> 2vCPU/2GB)보다 약한 t3.nano(1vCPU/0.5GB) 환경에서도 재고 동시성이 깨지지 않는다는
> 것을 확인하는 것이고, 정확한 RPS·응답시간을 측정하는 것이 아니다. 테스트는 외부
> 네트워크를 타지 않고 로컬 PC → 로컬 백엔드(`localhost:8080`)로만 실행했다.

## 환경

- `docker compose -f compose.yaml -f compose.loadtest.yaml up --build` (backend: 1 vCPU,
  512MiB, `-Xmx384m`)
- k6는 로컬 바이너리 대신 `grafana/k6` 도커 이미지로 실행 (`--add-host=host.docker.internal:host-gateway`,
  `BASE_URL=http://host.docker.internal:8080`)
- 실행일: 2026-10-23

## 1. 재고 경쟁 (01-stock-race)

재고 5개에 VU 20명이 동시 주문. **3회 실행, 전부 통과** (성공 5건 / 나머지 422
`INSUFFICIENT_STOCK`, `verify.sql` 음수재고·초과판매 0행).

| 실행 | HTTP 요청 | 성공(201) | 실패(422, 정상) | 완료까지 |
|---|---|---|---|---|
| 1회차 | 22 | 5 | 15 | 1.1s~7s(그레이스풀 스톱 포함) |
| 2회차 | 22 | 5 | 15 | 1.1s |
| 3회차(관찰용) | 22 | 5 | 15 | 1.3s |

자격증명 오류(401/403)는 전 실행에서 0건 — 백엔드 로그에 `INSUFFICIENT_STOCK` 비즈니스
경고만 있고 인증/CSRF 실패는 없었다.

리소스(1회차, `docker stats`):

| 컨테이너 | CPU | 메모리 |
|---|---|---|
| backend | 100.20% (1 vCPU 한도에 포화) | 459.9MiB / 512MiB (89.82%) |
| postgres | 9.60% | 73.5MiB / 7.7GiB |

**`pg_stat_activity` 관찰 결과**: 외부에서 `docker compose exec`로 폴링하는 방식은
프로세스 기동 오버헤드가 수백ms라, 재고 행 잠금이 걸리는 임계구간(전체 레이스가
1초 안에 끝남)을 한 번도 포착하지 못했다. 락 경합 자체는 `verify.sql`의 정합성
결과(초과판매·음수재고 0건)로 간접 확인했다 — t3.nano 수준에서도 레이스가 1초
내로 해소될 만큼 빠르다는 뜻이며, 정합성 검증의 신뢰도를 낮추지 않는다.

## 2. 멱등성 (02-idempotency)

동시 동일요청 8건 + 같은 키·다른 본문 1건. **통과** — 체크 13/13 성공, `verify.sql`
기준 idempotency_key당 주문 1건 초과 0행, 실제 생성 주문 2건(동시 요청 1건 + 최초
요청 1건).

- 동시 동일요청: 8개 VU 중 1건만 201, 나머지는 같은 주문을 반환(멱등성 정상)
- 같은 키·다른 본문: 409 `DUPLICATE_IDEMPOTENCY_KEY`

리소스: backend CPU 24.72%, 메모리 479MiB/512MiB(93.56%) — 세 시나리오 중 메모리
사용량이 가장 높았다(OOM까지는 여유 있었음).

## 3. 결제 대기 만료 + 취소 동시성 (03-expiry)

주문 생성 → `payment_expires_at`을 과거로 수동 조정(배치 주기 10초) → 취소 요청.
**통과** — 만료 배치가 먼저 처리(`status=EXPIRED`, `release_reason=EXPIRED`,
`reservation_status=RELEASED`)했고, 뒤따른 취소 요청은 `ORDER_NOT_CANCELABLE`로
거부됐다. 재고는 정확히 한 번만 반환됨(`verify.sql` 0행).

## 4. 드롭 오픈 순간 스파이크 (04-drop-open-spike, GR-152)

WISH 상태 DROP(`sale_starts_at` = seed 30초 뒤)을 대상으로, 목록/상세 조회가
0→50 VU로 램프업하다가 오픈 시각에 구매 VU 30명이 한꺼번에 주문을 시도하는
시나리오. 레이트리밋 없이 유입 제한 없는 상태 그대로 실행. **통과**.

- `DropTransitionScheduler`(10초 주기)가 오픈 4초 뒤 WISH→GRAB 전환, 주문 30건
  전부 201 성공(재고 200개로 넉넉해 재고부족 없음)
- 체크 4802/4802(100%) 성공, `http_req_failed` 0.00%, 5xx **0건**
- 응답시간: p90 558ms, p95 1.6s, 최대 12.8s(오픈 순간 피크 구간 추정) — 운영
  캐파시티 수치 아님, 아래 전제와 동일
- `verify.sql` 음수재고·초과판매 0행, 생성 주문 30건(= 주문 성공 건수와 일치)
- 컨테이너 재시작(`RestartCount`) 0, OOM-kill 없음. 실행 중 최대 메모리
  459.8MiB/512MiB(89.8%), 백엔드 로그에 ERROR/Exception 없음
- SSE(stock-stream) 동시 연결은 범위 밖(GR-157에서 별도로 다룸)

## 결론

**1. 재고 경쟁** — 초과판매·음수재고 **미발생**(3회 반복 확인). CPU는 1 vCPU
한도에 포화(100.20%)됐지만 메모리는 89.82%로 여유 있었음.

**2. 멱등성** — idempotency_key당 주문 1건 초과 **미발생**. 네 시나리오 중
메모리 사용량이 가장 높음(93.56%) — OOM까지는 여유 있었으나 nano에서 가장
빠듯한 케이스.

**3. 결제 대기 만료 + 취소 동시성** — 재고 이중 복구 **미발생**, 배치·취소
요청 경합에서 재고가 정확히 한 번만 반환됨.

**4. 드롭 오픈 스파이크** — 서버 다운(OOM-kill·재시작) **미발생**, 5xx 0건,
재고 정합성 이상 없음. 레이트리밋 없이 그대로 받아도 nano 스펙에서 버팀.

**공통 전제**: t3.nano(1vCPU/512MiB)에서도 재고 동시성 로직이 깨지지 않고
서버가 죽지 않는다는 **하한선 검증**이며, 이 수치들(응답시간, RPS, 메모리
사용률)은 운영 캐파시티 산정에 쓰지 않는다 — 범위 밖(GR-151, GR-152
description 참조). 메모리가 89~93%대까지 올라간 점은, 더 큰 VU/시나리오를
nano에서 시도할 때 여유가 크지 않다는 참고 사항으로 남긴다.
