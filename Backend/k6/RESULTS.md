# nano 환경 부하테스트 결과 (GR-151, GR-152, GR-153, GR-157)

> 이 결과는 **운영 캐파시티 수치가 아니라 하한선 검증**이다. 목표는 운영(t3.small,
> 2vCPU/2GB)보다 약한 t3.nano(1vCPU/0.5GB) 환경에서도 재고 동시성이 깨지지 않는다는
> 것을 확인하는 것이고, 정확한 RPS·응답시간을 측정하는 것이 아니다. 테스트는 외부
> 네트워크를 타지 않고 로컬 PC → 로컬 백엔드(`localhost:8080`)로만 실행했다.

## 환경

- `docker compose -f compose.yaml -f compose.loadtest.yaml up --build` (backend: 1 vCPU,
  512MiB, `-Xmx384m`)
- k6는 로컬 바이너리 대신 `grafana/k6` 도커 이미지로 실행 (`--add-host=host.docker.internal:host-gateway`,
  `BASE_URL=http://host.docker.internal:8080`)
- 실행일: 2026-10-23

## 1. 재고 경쟁 (01-stock-race)

재고 5개에 VU 20명이 동시 주문. **3회 실행, 전부 통과** (성공 5건 / 나머지 422
`INSUFFICIENT_STOCK`, `verify.sql` 음수재고·초과판매 0행).

| 실행 | HTTP 요청 | 성공(201) | 실패(422, 정상) | 완료까지 |
|---|---|---|---|---|
| 1회차 | 22 | 5 | 15 | 1.1s~7s(그레이스풀 스톱 포함) |
| 2회차 | 22 | 5 | 15 | 1.1s |
| 3회차(관찰용) | 22 | 5 | 15 | 1.3s |

자격증명 오류(401/403)는 전 실행에서 0건 — 백엔드 로그에 `INSUFFICIENT_STOCK` 비즈니스
경고만 있고 인증/CSRF 실패는 없었다.

리소스(1회차, `docker stats`):

| 컨테이너 | CPU | 메모리 |
|---|---|---|
| backend | 100.20% (1 vCPU 한도에 포화) | 459.9MiB / 512MiB (89.82%) |
| postgres | 9.60% | 73.5MiB / 7.7GiB |

**`pg_stat_activity` 관찰 결과**: 외부에서 `docker compose exec`로 폴링하는 방식은
프로세스 기동 오버헤드가 수백ms라, 재고 행 잠금이 걸리는 임계구간(전체 레이스가
1초 안에 끝남)을 한 번도 포착하지 못했다. 락 경합 자체는 `verify.sql`의 정합성
결과(초과판매·음수재고 0건)로 간접 확인했다 — t3.nano 수준에서도 레이스가 1초
내로 해소될 만큼 빠르다는 뜻이며, 정합성 검증의 신뢰도를 낮추지 않는다.

## 2. 멱등성 (02-idempotency)

동시 동일요청 8건 + 같은 키·다른 본문 1건. **통과** — 체크 13/13 성공, `verify.sql`
기준 idempotency_key당 주문 1건 초과 0행, 실제 생성 주문 2건(동시 요청 1건 + 최초
요청 1건).

- 동시 동일요청: 8개 VU 중 1건만 201, 나머지는 같은 주문을 반환(멱등성 정상)
- 같은 키·다른 본문: 409 `DUPLICATE_IDEMPOTENCY_KEY`

리소스: backend CPU 24.72%, 메모리 479MiB/512MiB(93.56%) — 세 시나리오 중 메모리
사용량이 가장 높았다(OOM까지는 여유 있었음).

## 3. 결제 대기 만료 + 취소 동시성 (03-expiry)

주문 생성 → `payment_expires_at`을 과거로 수동 조정(배치 주기 10초) → 취소 요청.
**통과** — 만료 배치가 먼저 처리(`status=EXPIRED`, `release_reason=EXPIRED`,
`reservation_status=RELEASED`)했고, 뒤따른 취소 요청은 `ORDER_NOT_CANCELABLE`로
거부됐다. 재고는 정확히 한 번만 반환됨(`verify.sql` 0행).

## 4. 드롭 오픈 순간 스파이크 (04-drop-open-spike, GR-152)

WISH 상태 DROP(`sale_starts_at` = seed 30초 뒤)을 대상으로, 목록/상세 조회가
0→50 VU로 램프업하다가 오픈 시각에 구매 VU 30명이 한꺼번에 주문을 시도하는
시나리오. 레이트리밋 없이 유입 제한 없는 상태 그대로 실행. **통과**.

- `DropTransitionScheduler`(10초 주기)가 오픈 4초 뒤 WISH→GRAB 전환, 주문 30건
  전부 201 성공(재고 200개로 넉넉해 재고부족 없음)
- 체크 4802/4802(100%) 성공, `http_req_failed` 0.00%, 5xx **0건**
- 응답시간: p90 558ms, p95 1.6s, 최대 12.8s(오픈 순간 피크 구간 추정) — 운영
  캐파시티 수치 아님, 아래 전제와 동일
- `verify.sql` 음수재고·초과판매 0행, 생성 주문 30건(= 주문 성공 건수와 일치)
- 컨테이너 재시작(`RestartCount`) 0, OOM-kill 없음. 실행 중 최대 메모리
  459.8MiB/512MiB(89.8%), 백엔드 로그에 ERROR/Exception 없음
- SSE(stock-stream) 동시 연결은 범위 밖(GR-157에서 별도로 다룸)

## 5. 평상시 조회 (05-steady-read, GR-153)

조회 캐시(Redis)는 아직 없다(TECHSTACK.md 87절, "문제를 확인한 뒤 적용"). 이
결과는 캐시 없이 DB가 평상시 목록·상세 조회를 얼마나 버티는지의 하한선이며,
병목이 확인되면 캐시 도입 판단 근거로 쓴다. 인기 드롭 1개 반복 상세조회
(`hot_read`, VU 10)와 매번 다른 드롭 조회(`random_read`, VU 10)를 30초간
steady-state로 동시 실행, **2회 통과**.

- 체크 3214~3329건(100%) 성공, `http_req_failed` 0.00%
- 응답시간 매우 낮음: p90 ~8~19ms, p95 ~9~43ms — 캐시 없이도 nano에서 충분히
  빠름(단, 최대 6.04s 아웃라이어 1건 — 첫 요청 JIT/커넥션 워밍업 추정)
- HikariCP 커넥션: `max=10` 중 Prometheus 15초 스크랩 구간에서 관측된 active
  최댓값은 1 — 쿼리가 스크랩 간격보다 훨씬 빨리 끝나 동시 사용량을 못 잡음
  (GR-151의 `pg_stat_activity` 관측 한계와 동일한 샘플링 문제). `pending`은
  시종 0으로, 풀 고갈은 없었음
- 리소스: backend CPU 34~36%, **메모리 96.8~96.9%**(512MiB 중) — 네 시나리오
  중 가장 높음. 컨테이너 재시작 0회, OOM 없음. 이전 시나리오들을 같은
  컨테이너에서 연달아 돌린 누적 효과일 수 있어, 단일 시나리오만 단독 실행 시
  수치는 더 낮을 가능성이 있음(검증 안 함)
- `verify.sql`: 예상치 못한 주문 0건, 재고 변동 0건(읽기 전용 시나리오가
  실제로 쓰기를 하지 않았음을 확인)

## 6. SSE 동시 연결 (06-sse-stream, GR-157)

실행일 2026-10-26. 다른 절과 같은 nano 제한(backend 1 vCPU/512MiB, `-Xmx384m`)이며, 이 절만
`compose.loadtest.yaml`의 SSE IP 제한 오버라이드와 postgres `pg_stat_statements`를 함께 썼다.
SSE 연결은 Node(`sse-clients.mjs`), 주문은 로컬 k6 v2.3.0(`order-load.js`, 결제 없이 주문 생성만)으로
같은 Mac에서 실행했다. 연결 구성은 상세 구독 70%(인기 상품 1개) / 목록 구독 30%(24개),
주문은 80%가 인기 상품. REALTIME_STOCK.md 13.2의 유지 시간(워밍업 2분 + 측정 10~15분)은
nano에서 줄여 **회차당 주문 5분**으로 실행했다.

| 회차 | SSE 연결 | 주문 | 주문 p95 | 전달 지연 p50 / p95 / 최대 | 비고 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 (비활성 기준선) | 50/초, 15,000건 | 10.8ms | — | |
| 1 | 100 | 5/초, 1,501건 | 16.9ms | 605 / 1,045 / 1,247ms | 놓친 알림 0 (128,400쌍) |
| 2 | 200 | 50/초, 15,000건 | 10.6ms | 518 / 984 / 7,211ms | 놓친 알림 0 (2,575,800쌍) |

- 모든 회차에서 연결 성공 100%(ready p95 18ms 이하), 서버 쪽 조기 종료·전송 실패·전송 정체 0,
  주문 실패 0, `verify.sql` 음수재고·초과판매 0행. HikariCP pending 최대 0, timeout 0.
- **SSE 활성 시 주문 p95 악화 없음**: 같은 50/초 조건에서 0회차 10.8ms → 2회차 10.6ms(-1.6%). 13.2 기준
  (10% 이내)을 이 환경에서는 만족했다.
- 전달 지연 p95 약 1초는 서버의 1초 병합 창(`coalesce-window`) 때문이다. 13.1 목표(평시 2초, 피크 3초)
  안쪽이다. 최대 7.2초는 2회차의 단발 아웃라이어(p99 1,025ms)로 원인은 확인하지 않았다(GC 추정, 검증 안 함).
  지연은 주문 응답 수신 시각 기준 근사값이다(`analyze.mjs` 주석).
- 리소스: backend CPU 평균 0회차 24% / 1회차 8% / 2회차 24%. **메모리 최대 92.6% / 97.8% / 99.99%** —
  2회차는 512MiB 한도에 닿았으나 재시작 0회, OOM-kill 없음. SSE 200 연결이 nano에서 메모리 여유가
  거의 없는 상한이다.
- 2회차 SSE 지표(5분): 변경 신호 14,453 → 병합 2,280,645 → 전송 198,855건.

**GR-163 기준선 — 전송 시 공개 여부 재검증 쿼리**(`countPublicDropsForSubscription`, `pg_stat_statements`)

| 회차 | 쿼리 호출 | 구독 시점 | 전송 시점 | 주문 1건당 | HikariCP 커넥션 획득 |
| --- | --- | --- | --- | --- | --- |
| 0 | 0 | 0 | 0 | 0 | 57,564 |
| 1 | 24,561 | 100 | 24,461 | 16.3 | 29,871 |
| 2 | 58,264 | 200 | 58,064 | 3.9 | 114,097 |

- 전송 시점 호출은 연결 수 × 초당 1회(병합 창)가 상한이라, 2회차는 거의 상한(200 × 300초 = 60,000)에 닿았다.
- 쿼리 자체는 회당 0.01~0.03ms로 가볍지만 매번 커넥션 획득 + `BEGIN READ ONLY`가 따라온다.
  2회차 커넥션 획득은 같은 주문량의 0회차보다 약 2배(+56,533)이고 그 대부분이 이 쿼리다.
- 이 환경(로컬 DB, 풀 여유)에서는 주문 p95에 영향이 드러나지 않았다. GR-163의 효과는 응답시간보다
  DB 왕복·커넥션 획득 수로 비교한다.

**정리·제한 동작**

- 클라이언트 200개 일괄 종료 후 서버 연결·구독·pending이 0이 되기까지 약 57초(52초 시점 65개 잔존).
  서버는 다음 쓰기(heartbeat 15초)가 실패해야 끊긴 연결을 알아서, 13.2 목표(60초 후 0)에 근소하게 들어왔다.
- 같은 IP 21번째 연결 429(`reason=ip`), 60초 창 31번째 요청 429(`reason=rate`), 201번째 연결 503(`capacity`)
  모두 기대대로 동작. 서버는 IP 제한을 전체 상한보다 먼저 검사하므로, 503을 보려면 IP 상한을 200보다 크게
  둬야 한다(첫 시도에서 IP 상한 200으로 429가 먼저 나서 오버라이드 기본값을 1000으로 고쳤다).

**한계**: 부하 발생기가 모두 한 IP라 IP 제한을 오버라이드했고, 유지 시간을 5분으로 줄였으며, 느린 수신자·
수명 만료 재연결·프록시 경유는 다루지 않았다(GR-113 범위). k6와 Node가 같은 Mac 시계를 써서 시계 오차는
없지만, 지연은 커밋 시각이 아닌 주문 응답 수신 시각 기준 근사값이다.

## 결론

**1. 재고 경쟁** — 초과판매·음수재고 **미발생**(3회 반복 확인). CPU는 1 vCPU
한도에 포화(100.20%)됐지만 메모리는 89.82%로 여유 있었음.

**2. 멱등성** — idempotency_key당 주문 1건 초과 **미발생**. OOM까지는 여유
있었으나 메모리 93.56%로 nano에서 빠듯한 케이스 중 하나.

**3. 결제 대기 만료 + 취소 동시성** — 재고 이중 복구 **미발생**, 배치·취소
요청 경합에서 재고가 정확히 한 번만 반환됨.

**4. 드롭 오픈 스파이크** — 서버 다운(OOM-kill·재시작) **미발생**, 5xx 0건,
재고 정합성 이상 없음. 레이트리밋 없이 그대로 받아도 nano 스펙에서 버팀.

**5. 평상시 조회** — 에러 **미발생**, 응답시간 p95 수십ms로 캐시 없이도
충분히 빠름. 다만 메모리 96.8~96.9%로 다섯 시나리오 중 가장 높아, nano에서
가장 빠듯한 케이스. HikariCP 풀 고갈은 없었음(샘플링 한계로 동시 사용량
자체는 못 잡음).

**6. SSE 동시 연결** — 200 연결 + 주문 50/초에서 연결 실패·알림 유실·재고 이상 **미발생**, SSE 활성 시
주문 p95 악화 없음, 전달 지연 p95 약 1초(병합 창). 다만 메모리가 512MiB 한도(99.99%)에 닿아 nano에서
200 연결이 여유 없는 상한이다. 전송 시 재검증 쿼리가 5분간 약 5.8만 회 실행돼 GR-163 기준선으로 남긴다.

**공통 전제**: t3.nano(1vCPU/512MiB)에서도 재고 동시성 로직이 깨지지 않고
서버가 죽지 않는다는 **하한선 검증**이며, 이 수치들(응답시간, RPS, 메모리
사용률)은 운영 캐파시티 산정에 쓰지 않는다 — 범위 밖(GR-151, GR-152, GR-153
description 참조). 메모리가 89~97%대까지 올라간 점은, 더 큰 VU/시나리오를
nano에서 시도할 때 여유가 크지 않다는 참고 사항으로 남긴다.
