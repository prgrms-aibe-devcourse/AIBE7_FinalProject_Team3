# GRAB 요구사항 정의서

## 1. 기능 요구사항

### 1.1 회원 및 인증

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| AUTH-001 | 사용자는 이메일 인증(AUTH-009)을 완료한 뒤 비밀번호와 닉네임을 입력해 회원가입할 수 있어야 한다. | 이메일 인증을 완료하지 않으면 회원이 생성되지 않으며, 회원 이메일은 인증을 완료한 이메일로만 저장된다. 중복 이메일 가입이 거부된다. 닉네임 규칙을 충족하지 않거나 대소문자를 무시하고 이미 사용 중인 닉네임이면 거부된다. 휴대폰 번호와 본명은 입력받지 않는다. |
| AUTH-002 | 가입한 사용자는 로그인·로그아웃할 수 있어야 한다. | 올바른 계정만 인증되고 로그아웃 후 인증이 해제된다. |
| AUTH-003 | 인증이 필요한 기능은 비회원이 사용할 수 없어야 한다. | 비회원의 WISH·주문 요청이 거부된다. |
| AUTH-004 | 사용자는 자신의 회원 정보를 조회하고 수정할 수 있어야 한다. | 다른 사용자의 정보는 조회·수정할 수 없으며 회원 정보에 휴대폰 번호를 포함하지 않는다. |
| AUTH-005 | 비밀번호는 정의된 보안 정책을 충족해야 한다. | 최소 길이 및 문자 조합 조건을 만족하지 않는 비밀번호는 거부되며 비밀번호는 안전한 해시 방식으로 저장된다. |
| AUTH-006 | 사용자는 KAKAO 또는 GOOGLE 계정으로 회원가입하고 로그인할 수 있어야 한다. | 제공자가 검증한 이메일과 고유 사용자 식별자로 최초 회원가입이 진행되며, 같은 제공자 계정으로 다시 로그인해도 회원이 중복 생성되지 않는다. |
| AUTH-007 | 소셜 회원가입 시 닉네임을 입력할 수 있어야 한다. | 닉네임을 입력하기 전에는 회원이 생성되지 않으며 소셜 회원가입 시 비밀번호 해시는 저장하지 않는다. 닉네임은 LOCAL 회원가입과 같은 규칙으로 검증한다. |
| AUTH-008 | 같은 이메일이 LOCAL 또는 다른 소셜 제공자로 이미 가입된 경우 계정을 자동으로 병합하지 않아야 한다. | 기존 계정과 데이터는 변경되지 않으며 별도의 계정 연결이 필요하다는 오류가 반환된다. |
| AUTH-009 | LOCAL 회원가입 전에 사용자는 이메일로 받은 인증 코드로 이메일 소유를 확인해야 한다. | 올바른 형식의 이메일에만 인증 코드가 발송되며, 코드는 정해진 유효시간 안에 한 번만 사용할 수 있다. 확인 시도 횟수와 재발송 간격·횟수 제한을 넘은 요청은 거부된다. 코드 요청의 응답만으로는 이메일의 가입 여부를 알 수 없다. 인증 결과는 정해진 시간 안에 한 번의 회원가입에만 사용할 수 있다. |

### 1.2 판매자 등록 및 권한

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| SELLER-001 | 일반 회원은 사업자등록번호를 포함한 판매자 등록을 신청할 수 있어야 한다. | 필수 정보가 누락되면 신청할 수 없으며 승인 전에는 판매자 기능을 사용할 수 없다. 이미 `PENDING` 또는 `APPROVED` 상태로 신청한 회원은 다시 신청할 수 없다. `REJECTED` 상태인 회원은 같은 신청을 다시 제출해 재심사를 받을 수 있다. 같은 사업자등록번호로 이미 신청한 다른 계정이 있으면 거부된다. |
| SELLER-002 | 운영자는 판매자 신청을 승인하거나 반려할 수 있어야 한다. | `sellers.status = APPROVED`인 사용자에게만 판매자 기능이 활성화된다. |
| SELLER-005 | 판매자 신청의 사업자등록번호는 국세청 사업자등록 상태조회로 1차 검증해야 한다. | 조회 결과가 계속사업자가 아니면(휴업자·폐업자) 신청이 거부된다. 외부 조회가 실패하거나 응답하지 않으면 신청을 막지 않고 `PENDING`으로 접수하며, 운영자가 승인 전 수동으로 확인한다. |
| SELLER-003 | 판매자는 소비자 화면과 판매자 작업 공간을 전환할 수 있어야 한다. | 화면 전환만으로 새로운 권한이 부여되지 않는다. |
| SELLER-004 | 판매자는 자신이 생성한 DROP과 주문만 관리할 수 있어야 한다. | 다른 판매자의 데이터 변경 요청이 거부된다. |
| SELLER-006 | 판매자 신청자는 사업자등록증·신분증·통장 사본·통신판매업신고증 4종 서류를 제출해야 한다. | 4종 중 하나라도 누락되면 신청이 거부된다. 서류는 암호화해 비공개 저장소에 보관하며 공개 URL로 노출하지 않는다. 신분증은 주민등록번호 뒷자리를 가려서 제출하도록 안내한다. |
| SELLER-007 | 운영자는 제출된 신청 서류를 전용 뷰어로만 열람할 수 있어야 한다. | 서류 원본은 URL로 직접 접근할 수 없고, 열람 요청마다 서버가 복호화 및 운영자 식별 워터마크를 합성한 이미지로만 제공한다. 열람마다 열람자·시각 기록이 남는다. |

### 1.3 DROP 등록 및 관리

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| DROP-001 | 판매자는 DROP을 임시 저장할 수 있어야 한다. | 임시 저장된 DROP은 소비자에게 노출되지 않는다. |
| DROP-002 | DROP에는 상품명, 설명, 이미지, 가격, 카테고리, 일정 및 배송 정보가 포함되어야 한다. | 필수 항목을 입력해야 WISH 상태로 공개할 수 있다. |
| DROP-003 | 판매자는 상품 특성에 맞는 옵션 그룹과 옵션값을 자율적으로 구성하고 판매 조합(SKU)을 등록할 수 있어야 한다. | 그룹명과 값은 색상·사이즈 등으로 고정하지 않으며, 각 판매 조합에 가격과 재고가 존재한다. |
| DROP-004 | 판매 시작 시각은 종료 시각보다 빨라야 한다. | 잘못된 일정은 저장 또는 공개되지 않는다. |
| DROP-005 | 판매자는 DRAFT 상태의 DROP을 수정할 수 있어야 한다. | 수정 내용이 정상적으로 저장된다. |
| DROP-006 | 판매자는 DROP을 WISH 상태로 공개할 수 있어야 한다. | 공개 후 상품 목록과 상세에서 조회된다. |
| DROP-007 | GRAB 시작 후 가격·옵션 등 핵심 판매 조건의 변경은 제한되어야 한다. | 기존 주문 조건에 영향을 주는 변경이 거부된다. |
| DROP-008 | 주문에는 주문 당시 상품·옵션·가격 정보가 보존되어야 한다. | 이후 상품 정보가 변경되어도 기존 주문 정보는 변경되지 않는다. |
| DROP-009 | 판매자는 갤러리와 상세 설명 이미지를 용도별로 등록·정렬·수정할 수 있어야 한다. | GALLERY가 1장 이상이어야 공개할 수 있고 첫 장만 썸네일로 사용한다. DETAIL은 선택이며 DROP당 GALLERY 최대 5장·DETAIL 최대 15장, 파일당 5MB를 넘지 않는다. 기존 이미지는 GALLERY로 이관된다. |
| DROP-010 | 판매자는 업로드한 상품 사진으로 상품명·설명·카테고리·이미지 대체 설명 초안을 AI로 받을 수 있어야 한다. | 판매자가 요청할 때만 만들며 업로드 API로 올린 이미지만 최대 3장 사용한다. 초안은 저장되지 않고 폼의 기본 정보·대체 설명 칸에 채워지며, 이미 입력한 칸은 판매자가 덮어쓰기를 허락할 때만 바뀐다. 판매자가 확인 후 저장해야 반영된다. 카테고리는 활성 카테고리 중에서만 고른다. 사진으로 확인할 수 없는 사실(정품·최저가·원산지 등)과 가격·재고·일정은 만들지 않는다. 판매자별 하루 요청 수가 제한되며, LLM이 꺼져 있거나 실패해도 DROP 작성·저장·공개는 정상 동작한다. |

### 1.4 상품 탐색

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| DISC-001 | 사용자는 공개된 WISH·GRAB 상품 목록을 조회할 수 있어야 한다. | DRAFT 상품은 목록에 나타나지 않는다. |
| DISC-002 | 사용자는 상태와 카테고리로 상품을 필터링할 수 있어야 한다. | 선택 조건에 맞는 상품만 반환된다. |
| DISC-003 | 사용자는 상품명으로 검색할 수 있어야 한다. | 검색어와 일치하는 공개 상품이 반환된다. |
| DISC-004 | 상품 상세에는 현재 상태, 일정, 가격, 옵션 및 배송 정보가 표시되어야 한다. | 상태에 따라 가능한 행동이 다르게 제공된다. |
| DISC-005 | 메인은 인기 GRAB과 WISH를 별도 가로 슬라이드로 제공해야 한다. | 각 영역 최대 8개, PC 4장·태블릿 3장·모바일 2장 노출, 한 장씩 이동하며 양끝에서 멈춘다. 버튼·키보드·터치로 조작하고 전체 보기·상세 이동, 0~1개 상태를 처리한다. 모든 로고는 메인으로 이동한다. |
| DISC-006 | 사용자는 WISH·GRAB 상품을 작은 카드 목록에서 탐색할 수 있어야 한다. | 목록은 24개/페이지, PC 4열·태블릿 3열·모바일 2열이며 필터·검색·페이지·직접 진입·뒤로 가기에서 조회 조건을 유지한다. |
| DISC-007 | 인기 순위는 공개 상품 전체에서 상태별 집계로 정해야 한다. | WISH는 활성 WISH 수, GRAB은 결제 확정·미취소 주문의 상품 수량을 사용한다. GRAB은 서버 시각상 구매 가능하고 활성 옵션에 가용 재고가 있는 상품만 포함한다. 동률은 공개 시각 내림차순, ID 내림차순이다. |
| DISC-008 | 상품 상세는 상단 갤러리와 하단 설명 이미지를 구분해 표시해야 한다. | GALLERY 순서와 대체 설명이 적용되고 DETAIL은 원본 비율·순서대로 표시된다. DETAIL이 없는 상품은 텍스트 설명만 보이며 이미지 실패와 모바일 화면을 처리한다. |

### 1.5 WISH

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| WISH-001 | 로그인한 사용자는 WISH 상태의 DROP에 WISH를 등록할 수 있어야 한다. | 등록 후 활성 WISH가 한 건 존재한다. |
| WISH-002 | 한 사용자는 동일 DROP에 하나의 활성 WISH만 가질 수 있어야 한다. | 중복 요청에도 WISH 수가 증가하지 않는다. |
| WISH-003 | 사용자는 GRAB 시작 전 자신의 WISH를 취소할 수 있어야 한다. | 취소 후 활성 WISH 집계에서 제외된다. |
| WISH-004 | GRAB 시작 후 신규 WISH 등록과 취소를 제한해야 한다. | 해당 요청이 명확한 사유와 함께 거부된다. |
| WISH-005 | 사용자는 자신이 등록한 WISH 목록을 확인할 수 있어야 한다. | 각 DROP의 현재 상태가 함께 표시된다. |
| WISH-006 | 판매자는 상품별 활성 WISH 수를 확인할 수 있어야 한다. | 취소된 WISH는 활성 수에 포함되지 않는다. |
| WISH-007 | WISH가 구매·재고 예약·우선권을 보장하지 않는다는 안내가 제공되어야 한다. | 등록 전 또는 상세 화면에서 안내를 확인할 수 있다. |
| WISH-008 | 활성 WISH를 가진 사용자는 해당 DROP의 판매 시작이 임박했을 때와 판매가 시작됐을 때 메일 알림을 받아야 한다. | 두 시점마다 메일이 한 번씩만 발송된다. 취소한 WISH와 활성 상태가 아닌 회원은 수신 대상에서 제외된다. 메일에는 해당 DROP으로 이동하는 링크와 WISH 안내 문구가 포함된다. |
| WISH-009 | 알림 발송의 성공 여부가 DROP 상태 전환에 영향을 주지 않아야 한다. | 발송이 실패해도 상태 전환은 유지되고 후속 전환이 중단되지 않는다. 실패 기록에 받는 사람 주소와 메일 본문 원문이 남지 않는다. |
| WISH-010 | 판매자가 판매 시작 전 WISH DROP을 취소하면, 해당 DROP을 활성 WISH한 사용자에게 취소 메일 알림을 받아야 한다. | 취소한 WISH와 활성 상태가 아닌 회원은 수신 대상에서 제외된다. 메일에는 DROP이 다시 열리지 않는다는 안내와 목록으로 돌아가는 링크가 포함되고, 판매자가 입력한 취소 사유는 넣지 않는다. 취소가 거부되거나 트랜잭션이 롤백되면 메일이 발송되지 않는다. |
| WISH-011 | 취소 알림 발송의 성공 여부가 취소 API 응답에 영향을 주지 않아야 한다. | 발송이 실패해도 취소 API는 정상 응답한다. 실패 기록에 받는 사람 주소와 메일 본문 원문이 남지 않는다. |

### 1.6 상태 전환

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| STATE-001 | 판매 시작 시각이 되면 WISH 상태의 DROP이 GRAB으로 전환되어야 한다. | 서버 시각을 기준으로 구매 가능 상태가 된다. |
| STATE-002 | 판매 종료 시각이 되면 DROP이 ENDED로 전환되어야 한다. | 종료 이후 신규 주문이 거부된다. |
| STATE-003 | 시스템은 품절 등의 조건에 따라 GRAB을 조기 종료할 수 있어야 한다. | 조기 종료 이후 신규 주문이 거부된다. |
| STATE-004 | 판매자는 판매 시작 전 WISH 상태의 출시를 취소할 수 있어야 한다. | `status == WISH && now < saleStartsAt`일 때만 CANCELED로 전환되고, 시작 시각이 지난 WISH는 취소할 수 없다. |

### 1.7 주문 및 재고 확보

### 1.13 수요 분석

판매자가 WISH 반응을 근거로 준비 수량을 검토하도록 참고 정보를 준다(DEMAND-001~009). 판매 계획을 저장하거나 결정을 기록하지 않는다. DROP을 만들 때는 종료 DROP의 판매 실적으로 재고 수량을 추천하고 가격대를 참고하게 한다(DEMAND-010~012). 제안과 추천은 참고용이며 재고·가격·판매 상태에 자동 반영하지 않는다. 계산식과 응답 계약은 [수요 분석 API](api-spec/DEMAND.md)를 따른다.

| ID | 요구사항 | 인수 조건 |
| --- | --- | --- |
| DEMAND-001 | 판매자는 본인 WISH DROP의 수요 데이터를 조회할 수 있어야 한다. | 활성 WISH 수, 일별 등록 추이, 판매 시작까지 남은 시간과 비슷한 종료 DROP의 WISH 대비 구매 전환율이 반환된다. 전환율은 내 실적(본인 DROP)과 시장 평균(다른 판매자 DROP)으로 나눠 각각의 표본 기준·표본 수와 신뢰도를 함께 표시하며, 두 표본을 섞지 않는다. 공개 시점 재고 추천(DEMAND-012) 기록이 있으면 함께 반환되어 생성 단계 추천과 비교할 수 있다. `WISH` 상태가 아니거나 판매 시작 시각이 지난 DROP, 다른 판매자의 DROP은 거부된다. |
| DEMAND-002 | 서버는 수요 데이터로 판매 계획(예상 주문 수량 범위, 추천 판매 수량, 옵션별 배분)을 계산해야 한다. | 같은 데이터와 가정이면 항상 같은 결과가 나온다. 결과에 사용한 데이터와 가정이 함께 반환된다. 계산에 LLM을 사용하지 않는다. |
| DEMAND-003 | 판매자는 전환율 기준(내 실적·시장 평균)을 고르거나 전환율과 안전 재고율을 바꿔 계획을 다시 계산할 수 있어야 한다. | 지정하지 않으면 신뢰도가 높은 기준을 쓰고, 같으면 내 실적을 쓴다. 허용 범위를 벗어난 값은 거부된다. 다시 계산만 하고 저장하지 않는다. |
| DEMAND-004 | 데이터가 부족하면 추천 수량을 억지로 제시하지 않아야 한다. | 전환율 신뢰도가 `NONE`이고 판매자가 전환율을 입력하지 않았으면 추천 수량 없이 부족한 데이터 항목이 반환된다. 예상 범위는 표본 크기로 계산한 전환율 구간으로 정해 표본이 적을수록 넓게 표시되고, 신뢰도가 `LOW`이면 표본이 적다는 항목이 함께 반환된다. |
| DEMAND-005 | DROP의 판매가 시작될 때 그 시점의 수요 분석 결과를 기록해야 한다. | `WISH → GRAB` 전환이 커밋된 뒤 전환 시점 데이터와 기본 가정으로 다시 계산한 분석 결과와 옵션 준비 수량이 DROP당 한 건 저장된다. 기록에 실패해도 상태 전환은 정상 처리된다. 종료 후 실제 판매량과 비교해 예측 정확도를 평가하는 근거가 된다. 판매자가 판매 계획을 저장하거나 수락·수정·거절을 기록하는 기능은 두지 않는다(GR-175). |
| DEMAND-006 | 판매자 화면은 수요 분석이 의미 있는 시점에 먼저 제안해야 한다. | 활성 WISH가 기준 수 이상이거나 판매 시작이 기준 시간 이내일 때 제안 표시 여부가 참으로 반환된다. 초기 기준은 활성 WISH 30명, 판매 시작 48시간 전이며 설정으로 바꾼다. |
| DEMAND-007 | 수요 분석 결과에는 LLM이 생성한 설명이 제공되어야 한다. | LLM에는 계산 결과(계산에 사용한 가정 포함)의 집계값만 전달하고 상품명·옵션명 등 판매자 입력 텍스트는 보내지 않는다. 설명의 수치가 계산 결과에 없으면 설명을 버린다. LLM 호출이 실패하거나 시간 초과돼도 분석 조회는 정상 처리되고 설명 상태로 구분된다. 설명은 판매자가 요청할 때만 그 판매자가 고른 가정의 결과로 만들고, 같은 DROP에 같은 입력이면 저장된 설명을 다시 써 LLM을 부르지 않는다. 판매자별 하루 요청 수가 제한된다. |
| DEMAND-008 | 다른 판매자의 판매 데이터는 익명 집계값으로만 사용해야 한다. | 시장 평균은 다른 판매자 5명·DROP 10개 이상일 때만 계산하고, 미달이면 제공하지 않는다. 시장 표본은 오늘 0시(KST) 이전 종료 DROP으로 고정해 하루 동안 값이 바뀌지 않는다. 시장 평균 전환율은 정수 %로 반올림하고 표본 수는 구간으로만 표시한다. 본인 DROP을 시장 표본에 섞지 않는다. 응답·LLM 입력에 다른 판매자의 상품명·브랜드·DROP별 수치가 포함되지 않는다. |
| DEMAND-009 | 전환율 표본은 분석 대상과 내용이 비슷한 종료 DROP에서 골라야 한다. | 대상과 종료 DROP의 임베딩이 있으면 유사도 기준으로 표본을 고르고, 임베딩이 없거나 유사 표본의 신뢰도가 `NONE`이면 같은 카테고리 기준으로 대체한다. 어느 기준을 썼는지 응답에 표시된다. 임베딩 생성 실패가 DROP 공개에 영향을 주지 않는다. GR-147 구현 전에는 카테고리 기준만 사용한다. |
| DEMAND-010 | 판매자는 DROP을 만들거나 DRAFT를 편집할 때 비슷한 종료 DROP의 판매 실적으로 재고 수량을 추천받을 수 있어야 한다. | 같은 카테고리이고 대표 가격이 입력 가격의 ±30%인 종료 DROP의 판매량 범위(하위 25%·중간값·상위 25%), 판매율, 품절 비율, 신뢰도와 준비 권장 수량, 옵션별 배분이 반환된다. 내 실적과 시장 평균을 나눠 계산하고 기준을 표시한다. 품절이 잦으면(50% 이상) 상위 25%를 기준으로 하고 과소 추정 가능성을 표시한다. 표본이 부족하면 수량 없이 부족한 데이터 항목을 반환한다. 같은 입력이면 항상 같은 결과가 나오고 계산에 LLM을 쓰지 않는다. 저장하지 않으며 입력·저장·공개를 막지 않는다. |
| DEMAND-011 | 판매자는 입력한 가격이 같은 카테고리에서 어느 가격대인지와 가격대별 판매율을 참고할 수 있어야 한다. | 입력 가격의 위치(낮은 편·중간·높은 편), 다른 판매자 DROP의 참고 가격 범위(하위 25%~상위 25%, 천 원 단위), 낮은·비슷한·높은 가격대별 판매율이 반환된다. 다른 판매자 데이터는 DEMAND-008 보호 규칙을 따르고 가격대마다 기준 미달이면 제공하지 않는다. 가격을 추천하지 않는다. |
| DEMAND-012 | DROP을 공개할 때 그 시점의 재고 추천과 실제 준비 수량을 기록해야 한다. | 공개 시점 데이터로 다시 계산한 추천 결과, 옵션별 실제 준비 수량, 추천 적용 여부가 DROP당 한 건 저장된다. 기록에 실패해도 공개는 정상 처리된다. 종료 후 실제 판매량과 비교해 추천 정확도를 평가하는 근거가 된다. |

| NFR-005 | 일관성 | 주문, 결제 및 재고 상태가 정의된 전이 규칙을 위반하지 않는다. |

| NFR-009 | 데이터 보호 | 사용자는 본인의 개인정보와 주문 정보만 조회할 수 있다. |
| NFR-010 | OAuth2 보안 | OAuth2 state를 검증하고 Client Secret은 저장소·로그에, 인가 코드·토큰·제공자 개인정보는 프론트엔드 리다이렉트 URL·응답 본문·로그에 노출하지 않는다. |
| NFR-011 | 이메일 인증 보안 | 이메일 인증 코드와 가입 컨텍스트 토큰은 해시로만 저장하고, 원문을 응답 본문·로그에 남기지 않는다. |
| NFR-012 | AI 데이터 보호 | LLM에는 수요 분석 계산 결과의 집계값만 보내고 회원 식별자·이메일·연락처·주소와 다른 판매자의 개별 데이터는 보내지 않는다. 임베딩에는 공개 카탈로그 텍스트만 사용한다. LLM API 키는 저장소·로그에 남기지 않는다. |
| NFR-013 | AI 품질 | LLM 설명의 수치는 계산 결과와 일치해야 한다. 평가셋 실행 결과(수치 일치율, 데이터 부족 명시율, 응답 시간, 토큰 사용량)를 모델·프롬프트 버전별로 기록한다. |
