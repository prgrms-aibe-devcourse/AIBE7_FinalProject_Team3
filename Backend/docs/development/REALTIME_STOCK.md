# 공개 DROP 실시간 변경 전달 계약 (GR-109)

> 상태: 2단계 전달 정책 확정. API·복구 세부 계약과 운영 수치는 미확정이며 구현 착수용 최종 명세가 아니다.
> 이 문서를 전달 정책의 정본으로 사용한다. 현재 SSE API는 미구현이다.

## 1. 적용 범위

상품 상세와 WISH·GRAB 목록에 SSE 변경 알림을 도입한다. 기존 잔여 수량 표시와 레이아웃은 유지한다. WISH 수·개인 WISH 상태·메인 인기 슬라이드·마이페이지 WISH·판매자 화면의 실시간 갱신은 제외한다.

GR-109는 명세 작업이다. GR-110에서 단일 서버 SSE와 커밋 후 이벤트를 구현하고, GR-111에서 상세, GR-112에서 목록, GR-113에서 Redis 다중 서버 전달과 운영 검증을 수행한다.

## 2. 전달 방식

SSE는 상품 ID와 변경 종류를 전달하고, 프론트는 기존 목록·상세·재고 조회 API를 다시 호출한다. 재고 스냅샷이나 수량 delta를 직접 적용하지 않는다. 기존 조회 API의 요청·응답 형식과 계산 규칙은 유지하며, 이 방식을 위해 기존 조회 API 코드를 수정할 필요는 없다.

기존 조회 계약을 활용하면 이벤트와 HTTP 응답 사이의 상품 버전 비교를 새로 도입하지 않아도 된다. 대신 연속 알림은 묶어서 조회하고, 조회 중 추가 변경을 수신하면 후속 조회로 수렴해야 한다. 묶음 간격·동시 요청 제한·오래된 응답 처리 규칙은 3단계에서 확정한다.

브라우저 전체를 새로고침하지 않는다. 조회 결과를 TanStack Query 캐시에 반영해 관련 화면을 갱신하며, 선택한 옵션·입력 상태는 유효성 검증과 별개로 보존한다.

## 3. 알림 대상

| 실제 변경 | 알림에 포함할 이유 |
| --- | --- |
| 주문 생성에 따른 HELD 예약 | 가용 재고 감소·품절·인기 GRAB 후보 변경 |
| 미결제 주문 취소·만료에 따른 실제 반환 | 가용 재고 증가·품절 해제·목록 재진입 |
| 결제 확정 | 가용 재고가 같아도 판매량·인기순 변경 |
| 결제 완료 주문 취소 성공에 따른 실제 반환 | 가용 재고 증가·판매량·인기순 변경. 배치 재시도 경로도 포함 |
| 판매 시작·종료·판매자 취소 | 상세 행동·목록 포함 여부 변경 |

조회 요청, 롤백된 변경, 실제 변경 없는 멱등 재실행은 알림 대상이 아니다. 결제 실패나 취소 결과 불명 자체를 재고 반환으로 간주하지 않는다. 공개 중 판매자 재고 수정 API를 새로 만들지 않는다.

상태 전환은 기존 서버 시각 기반 스케줄러가 실행하고, SSE는 전환 결과를 전달한다. DB 커밋 성공 후 전달하며 트랜잭션·행 잠금 중 네트워크 전송을 하지 않는다. 전달 실패가 이미 완료된 주문·결제·취소를 실패 응답으로 만들지 않아야 한다.

## 4. 화면별 반영과 복구

| 화면·상황 | 정책 |
| --- | --- |
| 상세에서 재고·판매량 변경 알림 수신 | 기존 재고 API 재조회 |
| 상세에서 상태 변경 알림 수신 | 기존 상세·재고 API 재조회 |
| WISH·GRAB 목록에서 변경 알림 수신 | 현재 필터·정렬·페이지 조건으로 목록 재조회. 카드 수량만 바꿔 목록 정합성을 대신하지 않음 |
| 목록 구독 | 현재 페이지 상품을 한 연결로 구독. 카드마다 연결하지 않음 |
| 화면 밖 상품 재입고·순위 진입 | 활성 목록의 주기 재조회로 복구 |
| 최초 연결·재연결·네트워크 복구·화면 복귀 | 최신 조회로 재동기화. 최초 연결의 구독 등록·조회 순서는 3단계에서 확정 |
| 정상 연결 중 조용한 알림 유실 | 주기 재동기화로 복구 |
| SSE 장애 | 상품 조회는 계속 제공하고 대체 주기 조회로 복구 |
| 상세의 판매 시작·종료 시각 도달 | 서버 상세를 재조회해 actions 반영. 배치 지연이 가능하므로 저장 상태 동기화의 후속 복구도 필요 |

상시 모든 목록 캐시를 무효화하지 않고 활성 화면의 조회를 대상으로 한다. 재고 변경에 따른 WISH 목록 재조회가 발생해도 WISH 수 자체의 실시간 전달을 보장하지 않는다.

## 5. 보장 범위와 남은 결정

실시간은 변경 알림으로 빠르게 갱신하고 누락은 최신 조회로 복구하는 의미다. 무조건 즉시 전달이나 무손실 이벤트 이력·재생은 보장하지 않는다. Redis는 다중 서버 전달에 사용하며 PostgreSQL 재고 원장·트랜잭션·행 잠금은 유지한다. 아웃박스·Streams·Kafka·버전 영속 필드는 이번 정책에 포함하지 않는다.

아래 항목은 미확정이며 GR-109 완료 전에 후속 단계에서 결정한다.

- 3단계: endpoint·쿼리·ID 제한·인증·공개 상태·필드 허용 목록·이벤트 이름과 형식·오류와 종료·ready 의미·조회 경합·연결 정리·쿠키/CORS·재연결과 조회 제어
- 4단계: 최신성 목표·묶음/heartbeat/재조회 주기·연결 제한·부하 조건·통과 기준·품절 제외와 인기순·총건수·빈 페이지와 페이지 감소·필터 변경 동작
- 5단계: 확정 계약을 요구사항·API 공통 규칙·DROP·프론트 페이지 명세에 반영하고 예시·링크·인계 기준 검증

정책 확정은 성능 실측이나 실행 검증 결과를 의미하지 않는다.
