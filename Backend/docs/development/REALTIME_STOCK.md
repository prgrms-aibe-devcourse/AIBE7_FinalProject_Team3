# 공개 DROP 실시간 변경 전달 계약 (GR-109)

> 상태: GR-110 단일 서버 SSE·커밋 후 알림·관측·브라우저/회귀 검증·OpenAPI 생성 완료. 화면 구독은 GR-111·GR-112에서 구현 완료. 다중 서버 Redis 전달은 단일 인스턴스 운영 결정으로 보류했고(GR-113 취소, 2026-10-27), 실제 프록시 경유 검증과 운영 부하(13절)는 GR-180 범위다.
> 이 문서를 전달 정책의 정본으로 사용한다. 전송 경로 구현과 도메인 알림 자동 발행·운영 성능 검증 완료를 구분한다.

## 1. 적용 범위

상품 상세와 WISH·GRAB 목록에 SSE 변경 알림을 도입한다. 기존 잔여 수량 표시와 레이아웃은 유지한다. WISH 수·개인 WISH 상태·메인 인기 슬라이드·마이페이지 WISH·판매자 화면의 실시간 갱신은 제외한다.

GR-109는 명세 작업이다. GR-110에서 단일 서버 SSE와 커밋 후 이벤트를 구현하고, GR-111에서 상세, GR-112에서 목록, Redis 다중 서버 전달(GR-113)은 단일 인스턴스 운영으로 보류하고, 실제 프록시·운영 부하 검증은 GR-180에서 수행한다.

## 2. 전달 방식

SSE는 상품 ID와 변경 종류를 전달하고, 프론트는 기존 목록·상세·재고 조회 API를 다시 호출한다. 재고 스냅샷이나 수량 delta를 직접 적용하지 않는다. 기존 조회 API의 요청·응답 형식과 계산 규칙은 유지하며, 이 방식을 위해 기존 조회 API 코드를 수정할 필요는 없다.

기존 조회 계약을 활용하면 이벤트와 HTTP 응답 사이의 상품 버전 비교를 새로 도입하지 않아도 된다. 대신 연속 알림은 묶어서 조회하고, 조회 중 추가 변경을 수신하면 후속 조회로 수렴해야 한다. 조회 동시성·오래된 응답 처리 규칙은 9절을 따르며 묶음 간격은 12절을 따른다.

브라우저 전체를 새로고침하지 않는다. 조회 결과를 TanStack Query 캐시에 반영해 관련 화면을 갱신하며, 선택한 옵션·입력 상태는 유효성 검증과 별개로 보존한다.

## 3. 알림 대상

| 실제 변경 | 알림에 포함할 이유 |
| --- | --- |
| 주문 생성에 따른 HELD 예약 | 가용 재고 감소·품절·인기 GRAB 후보 변경 |
| 미결제 주문 취소·만료에 따른 실제 반환 | 가용 재고 증가·품절 해제·목록 재진입 |
| 결제 확정 | 가용 재고가 같아도 판매량·인기순 변경 |
| 결제 완료 주문 취소 성공에 따른 실제 반환 | 가용 재고 증가·판매량·인기순 변경. 배치 재시도 경로도 포함 |
| 판매 시작·종료·판매자 취소 | 상세 행동·목록 포함 여부 변경 |

조회 요청, 롤백된 변경, 실제 변경 없는 멱등 재실행은 알림 대상이 아니다. 결제 실패나 취소 결과 불명 자체를 재고 반환으로 간주하지 않는다. 공개 중 판매자 재고 수정 API를 새로 만들지 않는다.

상태 전환은 기존 서버 시각 기반 스케줄러가 실행하고, SSE는 전환 결과를 전달한다. DB 커밋 성공 후 전달하며 트랜잭션·행 잠금 중 네트워크 전송을 하지 않는다. 전달 실패가 이미 완료된 주문·결제·취소를 실패 응답으로 만들지 않아야 한다.

## 5. 보장 범위와 결정 상태

실시간은 변경 알림으로 빠르게 갱신하고 누락은 최신 조회로 복구하는 의미다. 무조건 즉시 전달이나 무손실 이벤트 이력·재생은 보장하지 않는다. Redis는 다중 서버 전달이 필요해질 때 사용하며(현재 단일 인스턴스로 보류) PostgreSQL 재고 원장·트랜잭션·행 잠금은 유지한다. 아웃박스·Streams·Kafka·버전 영속 필드는 이번 정책에 포함하지 않는다.

단계별 결정 상태는 아래와 같다.

- 3단계 완료 계약: 구독 API·이벤트·공개 접근·오류·종료·ready·조회 경합·연결 정리·쿠키/CORS·재연결 제어는 6~9절을 따른다.
- 4단계 완료 계약: 목록 동작은 11절, 초기 주기·제한은 12절, 최신성·부하 목표와 측정은 13절을 따른다. 성능 검증은 GR-180에서 수행한다.
- 5단계 완료 계약: 요구사항·API 공통 규칙·DROP·ERD·프론트 페이지 명세에 반영하고 변경 원천·인수 시나리오·후속 이슈 완료 기준을 14~16절에 연결했다.

정책 확정은 성능 실측이나 실행 검증 결과를 의미하지 않는다.

## 6. SSE 구독 API (3단계)

```http
GET /api/v1/drops/stock-stream?dropIds=100,101
Accept: text/event-stream
```

- 단일·다중 구독을 같은 endpoint로 처리한다. `dropIds`는 필수이며 쉼표로 구분한 양의 정수다. 공백·빈 항목·부호·소수·지수·중복 쿼리 파라미터는 거부한다. 선행 0은 정수로 정규화한다.
- 각 ID는 `1..9007199254740991` 범위다. JavaScript 안전 정수 범위에서 기존 정수 ID를 사용한다. 정규화 후 중복을 제거하고 오름차순으로 처리한다.
- 중복 제거 전 최대 100개 토큰을 허용한다. 기존 목록 API 최대 size=100을 한 연결로 지원하기 위한 계약 상한이며 처리 용량 실측값은 아니다. 누락·빈 구독·형식/범위/개수 위반은 400 `INVALID_REQUEST`다. 빈 목록에서는 연결하지 않고 목록 주기 조회만 유지한다.
- WISH·GRAB·ENDED·CANCELED는 허용한다. DRAFT와 없는 ID는 동일한 404 `DROP_NOT_FOUND`다. 혼합 요청은 전체 거절하며 어느 ID가 잘못됐는지, 유효 ID가 무엇인지 응답하지 않는다.
- 인증 불필요 공개 데이터이며 사용자별 상태를 보내지 않는다. 쿠키가 없으면 접근 가능하다. 쿠키가 전달되면 기존 JWT 정책을 유지하므로 유효하지 않은 Access Token은 401 `INVALID_TOKEN`이다. 공개 SSE만 JWT 검증을 우회하지 않는다.
- 동일 출처 경로를 기본으로 사용한다. 교차 출처 배포는 기존 허용 Origin과 credential CORS 정책을 따른다. 필요한 경우 `withCredentials: true`를 사용하며 와일드카드 Origin을 추가하지 않는다. 동일 출처에서는 기본 EventSource도 쿠키를 보낼 수 있다.
- GR-110은 해당 GET 경로를 명시적으로 허용하고, 정적 `stock-stream` 경로가 상세 `{dropId}`로 처리되지 않음을 검증한다. `/drops/**` 전체를 공개하지 않는다. 최초 REQUEST와 ASYNC/ERROR dispatch에서 보안·오류 응답·연결 정리를 검증한다.

## 7. 스트림과 이벤트

성공은 200, `Content-Type: text/event-stream;charset=UTF-8`, `Cache-Control: no-cache, no-store`다. 일반 `ApiResponse` 래퍼 없이 각 이벤트의 `data`에 JSON 객체를 담는다. nullable 필드는 없으며 아래 필드만 공개한다. 시각은 ISO 8601 문자열이며 정렬·버전 비교에 사용하지 않는다.

| event | 필수 data 필드와 타입 | 의미 |
| --- | --- | --- |
| `ready` | `dropIds: number[]`, `serverTime: string` | 검증·구독 등록 완료. ID는 정규화된 오름차순 |
| `drop-changed` | `dropId: number`, `changes: string[]` | 해당 상품의 재조회 필요. changes는 `STOCK`, `SALES`, `STATUS` 중 하나 이상의 중복 없는 값 |
| `stream-closed` | `reason: string`, `reconnect: boolean` | 가능한 경우 전송하는 종료 안내. 아래 고정 조합만 허용 |

```sse
event: ready
data: {"dropIds":[100,101],"serverTime":"2026-10-15T03:00:00Z"}

event: drop-changed
data: {"dropId":100,"changes":["STOCK"]}

event: drop-changed
data: {"dropId":101,"changes":["SALES","STATUS"]}

: heartbeat

event: stream-closed
data: {"reason":"RECONNECT_REQUIRED","reconnect":true}

```

주문 예약·실제 반환은 `STOCK`, 결제 확정은 `SALES`, 결제 완료 주문 취소 성공은 `STOCK`·`SALES`, 판매 시작·종료·취소는 `STATUS`를 전달한다. 묶을 때 같은 상품의 changes를 합집합으로 만든다. 최종 상태·수량·취소 사유·전체/확보/판매/보류 원장·회원·주문·개인 WISH 정보는 보내지 않는다.

`id:`와 `retry:` 필드는 보내지 않는다. 이벤트 ID·상품 버전·이벤트 영속 이력은 도입하지 않고 `Last-Event-ID`는 무시한다. 중복·순서 역전은 추가 재조회 신호로 처리하고 delta를 누적하지 않는다. heartbeat는 위 주석 형식이며 JSON 이벤트나 데이터 최신성 보장이 아니다. 주기는 12절을 따른다.

알 수 없는 event/changes 값은 무시하되, 지원하는 changes는 처리한다. 알려진 이벤트의 필수 필드·타입이 잘못됐거나 미구독 상품 ID를 포함하면 payload를 적용하지 않고 연결을 닫아 장애 조회·제한된 재연결로 복구한다. 오류 payload 원문을 로그에 남기지 않는다.

`ready`는 매 연결마다 최초 이벤트로 보낸다. 등록 중 발생한 변경은 버퍼에 상품별로 병합해 ready 뒤 전달한다. ready 전에 수신 경로를 연결하며, 다중 서버 전달을 도입하면(GR-113, 보류) Redis 수신 준비와 로컬 구독 등록이 완료된 뒤 ready를 전송한다. ready는 무손실 보장이 아니며 주기 복구가 계속 필요하다.

## 8. 오류와 종료

스트림 시작 전 실패는 공통 JSON 오류 응답을 사용한다. 아래 추가 코드는 GR-110 2단계에서 공통 예외 처리의 Retry-After 헤더와 함께 연결했다.

| HTTP | 코드 | 조건 |
| --- | --- | --- |
| 400 | `INVALID_REQUEST` | 구독 쿼리 검증 실패 |
| 401 | `INVALID_TOKEN` | 전달된 인증 쿠키가 유효하지 않음. 기존 정책 |
| 403 | `ACCESS_DENIED` | 기존 출처/보안 정책 거부. CORS 차단은 브라우저에서 본문을 읽지 못할 수 있음 |
| 404 | `DROP_NOT_FOUND` | 없는 ID 또는 DRAFT가 하나 이상 포함 |
| 429 | `STOCK_STREAM_LIMIT_EXCEEDED` | IP 연결·구독 요청 제한 초과. Retry-After 초 단위 헤더 제공 |
| 503 | `STOCK_STREAM_UNAVAILABLE` | 구독 등록·전달 기반 준비 불가. Retry-After 초 단위 헤더 제공 |
| 500 | `INTERNAL_SERVER_ERROR` | 그 외 예상하지 못한 오류 |

연결·요청 제한의 적용 단위·수치와 Retry-After 값은 12절을 따른다. 한 화면당 연결은 최대 하나이며 탭 간 공유는 요구하지 않는다.

스트림 시작 뒤에는 HTTP 상태를 JSON 오류로 바꾸지 않는다. 종료 안내가 전송 가능하면 아래 조합을 보내고 연결을 정리한다. 전송 실패 시 바로 정리하며 종료 이벤트 도착을 보장하지 않는다.

| reason | reconnect | 처리 |
| --- | --- | --- |
| `RECONNECT_REQUIRED` | true | 수명 만료·서버 종료·전달 기반 장애. 지연 분산 후 재접속·ready 후 최신 조회 |
| `SUBSCRIPTION_INVALIDATED` | false | 예약. 등록 후 비공개/삭제 감지 시 전체 구독 종료, ID 목록을 보내지 않음. 상세/목록 재조회로 구독 집합 재계산. 현재 서버는 보내지 않는다(아래 참고) |

현재 공개 상태에서 DRAFT로 돌아가는 API와 DROP 물리 삭제 경로는 없다. 그래서 구독 시점 검증을 통과한 상품은 이후에도 공개 상태이며, 서버는 전송 전 공개 여부를 다시 확인하지 않는다(GR-163). 향후 비공개 전이가 추가되면 전송 전 공개 여부 검증과 무효화를 필수로 구현한다. 이때 전송마다 연결별로 조회하지 않고, 비공개 전이 트랜잭션의 커밋 후 이벤트로 해당 상품 구독 연결만 종료한다(3단계 `StockChangePublisher` → `StockChangeListener` 경로와 같은 방식). 프론트는 이 종료 안내 처리를 유지한다. ENDED·CANCELED는 공개 상태이므로 구독을 종료하지 않고 이후 실제 반환도 전달할 수 있다.

EventSource는 Axios 인증·401 인터셉터를 거치지 않고 onerror에 HTTP 상태·JSON 본문·Retry-After를 노출하지 않는다. 프론트는 onerror에서 기존 EventSource를 close하고 하나의 자체 재연결 타이머만 운용한다. 이를 통해 브라우저 자동 재연결과 중복하지 않는다. 진단을 위해 별도 연결 검사 API를 만들지 않는다.

연결 실패 시 기존 API 조회를 계속하며, 조회 API의 기존 인증 처리가 필요한 세션 복구를 담당한다. HTTP 오류를 읽었다고 가정해 로그아웃하거나 401/404/429를 추정하지 않는다. 조회로 404가 확인된 상품은 제거하고, 목록 결과에 따라 구독을 재생성한다. HTTP 오류를 식별하지 못한 경우에도 제한된 재연결 지연·주기 조회로 동작하며 무한 즉시 재시도하지 않는다.

## 9. 초기 연결·조회 경합과 캐시 수렴

1. 상세는 경로 ID로 구독하며 최초 화면 조회를 병행할 수 있다. 목록은 최초 목록 조회에서 ID를 얻어 구독한다. 이미 받은 화면 데이터를 표시해도 된다.
2. 현재 연결의 ready 수신 후 상세는 상세·재고, 목록은 동일 조건 목록을 반드시 다시 조회한다. 초기 조회와 구독 사이 누락을 이 조회로 보정한다. onopen만으로 구독 준비 완료로 간주하지 않는다.
3. 조회 키별 변경 세대 카운터와 dirty 플래그를 관리한다. 이벤트·복구 신호마다 세대를 증가시키며, 실행 중인 조회가 있으면 dirty만 남긴다. 현재 조회 뒤 추가 조회를 실행하고 같은 키의 갱신 요청을 병렬로 쌓지 않는다.
4. 조회 시작 세대보다 새 변경이 도착했으면 해당 결과를 최종 동기화로 간주하지 않는다. 결과를 표시하더라도 후속 조회를 예약한다. 연속 알림으로 조회를 계속 취소해 결과가 영원히 반영되지 않는 동작은 피한다. 묶음 대기에는 최대 대기 시간을 두며 수치는 12절을 따른다.
5. ready 이후 갱신 전의 요청이 나중에 도착해 덮어쓰지 않도록 기존 요청을 취소·배제한다. Axios 요청에 AbortSignal 전달 등 프론트 API 래퍼의 요청 취소 연동은 GR-111·GR-112에서 구현했다. 백엔드 기존 조회 API 변경은 필요하지 않다.
6. 상세 actions는 재고에 의존하므로 `STOCK` 알림에도 상세·재고를 함께 재조회한다. 판매량만 바뀐 `SALES`는 재고 조회로 처리할 수 있다. 같은 화면의 두 조회는 각각 동시 하나만 유지하며, 모두 성공하기 전 동기화 완료로 간주하지 않는다.
7. 응답으로 목록 ID 집합이 바뀌면 이전 연결을 닫고 새 집합으로 연결한다. 동일 집합이면 교체하지 않는다. 새 ready마다 한 번 재동기화하고, 이전 연결의 콜백·응답은 화면/연결 세대로 배제한다. 필터·페이지 변경과 StrictMode 재마운트에도 같은 원칙을 적용한다.
8. 화면 이탈 시 EventSource·재연결/묶음/주기 타이머·이벤트 리스너를 정리한다. 비활성 목록 전체 캐시를 무효화하지 않는다. `detail(id)` 키는 stocks 키의 접두사이므로 정확한 키 지정으로 중복 조회를 막는다.
9. 조회 실패는 dirty를 유지하되 즉시 반복하지 않는다. 다음 제한된 재시도·복구 주기에 다시 조회한다. 재연결·온라인 복귀·화면 복귀 신호는 같은 제어기에 병합한다. 정상 연결의 주기 조회도 같은 제어기를 사용한다.

서버는 공개 상세·재고 조회 응답을 짧은 TTL(5초)로 캐시한다(GR-183). 이 캐시는 알림 후 재조회 수렴을 깨지 않게 다음을 지킨다.

- 재고·판매·상태 변경 이벤트를 커밋 후 받아, SSE 전송보다 먼저 해당 상품의 캐시를 지운다. 알림을 받고 재조회한 요청은 커밋 이후 값을 읽는다.
- 캐시를 지우기 전에 시작한 조회는 결과를 다시 저장하지 않고, 지운 뒤 들어온 요청은 그 조회에 합류하지 않는다.
- `actions`·`serverTime`은 캐시에서 꺼낼 때마다 조회 시각으로 다시 계산한다.
- 한계: 무효화는 같은 인스턴스 안에서만 전달된다. blue/green 전환 중 다른 인스턴스에서 커밋된 변경은 최대 TTL만큼 늦게 보일 수 있다. 상세의 `wishCount`·`brandName`은 변경 이벤트가 없어 최대 TTL만큼 늦게 바뀐다.

위 방식은 버전 비교에 의한 선형적 화면 일관성을 보장하지 않는다. 이벤트 유실은 주기 조회로 복구하며, 최신성 목표와 장애 시 수렴 시간은 13절을 따른다.

## 10. 구현 인계와 근거

- GR-110: 연결 전 전체 검증, 구독 등록·ready 순서, 커밋 이후 변경 신호, 비동기 전송·예외 격리·종료 정리·공개 접근·오류 테스트. COMMON의 구현 예정 오류 코드를 코드 enum에 구현하고 상태 표기를 갱신한다.
- GR-111: 상세의 ready 후 조회, actions/재고 갱신, 시각 도달 재조회, 경합·취소·재연결·입력 유지.
- GR-112: 목록 구독 집합 교체, 활성 쿼리 재조회, 화면 밖 주기 복구, 필터·페이지 정합성.
- GR-113(보류): Redis 수신 등록 경계, 로컬/Redis 중복 전달 방지, 조용한 유실 복구. Redis 실패는 주문 성공과 분리한다.
- GR-180: 실제 프록시 경유 검증과 재조회 포함 부하 검증.

구현 전용 검증 시나리오: 혼합 DRAFT 요청의 전체 404, 잘못된 쿠키 401, ready 전후 변경, 조회 도중 연속 변경, 이전 연결/조회 응답 지연, 재연결 중복 방지, 종료 알림 유실, 목록 빈 집합과 구독 교체, 정상 SSE 중 Redis 알림 유실. GR-109에서는 실행 결과로 기록하지 않는다.

기술 근거: [WHATWG EventSource 명세](https://html.spec.whatwg.org/multipage/server-sent-events.html), [Spring MVC 비동기 응답 문서](https://docs.spring.io/spring-framework/reference/web/webmvc/mvc-ann-async.html). 설치 버전에 맞춘 API·보안 dispatch 동작 검증은 GR-110 책임이다.

## 11. 목록 정합성과 화면 동작 (4단계)

- 목록 갱신은 현재 status·categoryId·keyword·soldOut·sort·page·size로 서버 전체 후보를 다시 집계·정렬한다. 카드 수량 수정이나 현재 페이지 내 재정렬로 대체하지 않는다. 상품·총건수·페이지 수·hasNext는 같은 응답을 함께 반영한다.
- 품절 제외에서 품절된 상품은 성공한 목록 응답에서 빠지고 다음 후보가 채워진다. 품절을 허용하는 날짜 정렬에서는 카드를 유지하고 수량·품절을 갱신한다. 인기 GRAB은 재고 없는 상품을 제외한다. 반환 후 화면 밖 상품의 재진입은 주기 조회로 감지한다.
- 결제 확정·결제 완료 주문 취소는 수량이 같아도 순위를 바꿀 수 있다. WISH 수의 실시간 갱신은 보장하지 않으며 WISH 인기순도 주기 조회·다른 알림에 따른 재조회 시 최신 집계를 반영한다.
- 기존 일반 날짜 정렬은 저장 상태, 인기 정렬은 서버 시각상 후보 기준을 유지한다. 따라서 판매 시작 알림 직전의 인기 GRAB에서 status=WISH가 보일 수 있다. 상세 행동은 조회한 actions를 따른다.
- 재조회 중 기존 목록과 입력·스크롤을 유지한다. 최초 로딩만 전체 로딩으로 표시한다. 갱신 실패는 마지막 성공 데이터를 유지하고 기존 오류·재시도 표시 방식으로 안내한다. SSE 실패만으로 상품 영역을 오류 화면으로 바꾸지 않는다.
- 필터·검색·정렬 변경 시 기존 URL 규칙에 따라 page=0으로 이동한다. 페이지 이동·뒤로 가기는 URL 조건을 복원하고 이전 화면의 이벤트·응답을 배제한다. 화면 이탈 후 비활성 캐시를 계속 조회하지 않는다.
- 자동 갱신으로 총 페이지가 감소해도 URL의 page를 강제로 바꾸지 않는다. 범위 밖이면 빈 결과와 기존 범위 밖·이전 이동 처리를 사용한다. totalPages=0이면 빈 상태와 필터를 유지하고 페이지 버튼은 숨긴다. 빈 목록도 주기 조회를 유지해 재입고를 발견한다. 자동 마지막 페이지 이동은 도입하지 않는다.
- 조회 후 구독 ID가 바뀌면 9절의 교체 절차를 따르되 12절의 재연결 최소 간격을 적용한다. 그동안 목록 주기 조회를 유지한다. ready 후 조회가 다시 ID를 바꾸더라도 즉시 무제한 연결을 만들지 않는다.
- 상세의 옵션 선택·수량은 갱신 시 유지하되, 선택 옵션이 사라지거나 부족하면 기존 검증으로 주문을 제한하고 수정하도록 안내한다. 표시 수량이나 SSE 연결 성공은 구매 성공을 보장하지 않는다.

## 12. 초기 주기·제한과 설정 계약

아래 값은 GR-109에서 정한 **초기 구현 기본값과 검증 목표**다. 서버 연결 상한·IP 연결 상한·구독 요청 제한은 GR-185에서 동시 사용자 참고 목표(800~1000명, GR-180)에 맞춰 올렸다. 운영 실측값이나 현 인프라의 수용 가능 판정이 아니다. GR-180에서 동일 값을 검증하고 미달하면 원인·수정값·재검증 결과를 정본에 남긴다. GR-109에서는 application.yml·프록시·프론트 코드를 변경하지 않았다. GR-110 1단계에서 서버 설정·검증·구독/접속 제한 기반을, 2단계에서 SSE endpoint·전송·수명 관리를 연결했다. 3단계에서 도메인 이벤트 발행을 연결했고 4단계에서 브라우저·회귀 검증과 전용 지표를 추가했다.

백엔드 설정은 `application.yml`의 `grab.stock-stream.*`에 바인딩한다. 서버 전송 관련 설정은 GR-110 2단계에서 실행 경로에 연결했다. 프론트 설정은 향후 `features/drop/logic/realtimeStockPolicy.ts`로 모으며 아직 미구현이다.

| 화면 연결 수 | 활성 화면/탭당 1개, 숨김 시 close·주기 조회 중단 | 프론트 연결 제어기 | 백그라운드 부하 제한. 복귀 시 재연결·최신 조회 |
| 구독 ID 상한 | 입력 토큰 100개, 빈 구독 불허 | `max-drop-ids=100` | API 최대 페이지 지원 |
| 서버 연결 상한 | 인스턴스당 1000개, 한 상품도 최대 1000개 | `max-connections=1000` | 동시 사용자 참고 목표(800~1000명)에 맞춘 admission 제한. GR-157(micro)에서 800 연결까지 OOM·주문 실패·알림 유실 없음, GR-163으로 전송 시 DB 조회 0. 1000 연결은 GR-180에서 검증한다. 전송 큐 크기도 이 값을 따른다 |
| IP 연결 상한 | 인스턴스 내 remoteAddr당 50개 | `max-connections-per-ip=50` | 서버 상한의 5%. 캠퍼스·사무실 와이파이·통신사 CGNAT처럼 한 IP를 여러 사용자가 공유해도 막히지 않게 하면서, 한 IP가 용량의 5%를 넘게 차지하지 못하게 한다. NAT 제한 영향은 GR-180 기록 |
| 구독 요청 제한 | 인스턴스 내 remoteAddr당 60초 고정 창 75회, 최초 요청부터 계산 | `connect-rate-window`, `connect-rate-max=75` | 실패·구독 교체·재접속 모두 포함. 화면 이동마다 구독을 다시 요청하므로 IP 연결 상한과 같은 비율(연결당 분당 1.5회)로 둔다. 신규 IP 상태도 유한한 TTL/용량으로 관리 |
| Retry-After | 429·503에서 60초 | `retry-after=60s` | HTTP 클라이언트 진단용. EventSource가 읽는다고 가정하지 않음 |
| IP 추적 상태 상한 | 인스턴스당 10,000개, 활성 연결이 없고 요청 창 만료 시 제거 | `max-tracked-ips=10000` | 임의 IP로 메모리 증가 방지. 남은 추적 용량이 없으면 503 |

재연결·구독 교체는 같은 제어기에서 처리한다. 실패 후 n번째 대기는 `균등(0.5*b, b)`초, `b=min(60, 5*2^(n-1))`로 한다. 성공 ready 후 실패 횟수를 초기화한다. 정상 수명 종료·구독 집합 변경·화면 복귀도 직전 연결 시작부터 최소 5초를 지키며 균등 0~5초를 추가한다. 화면 복귀의 HTTP 조회는 연결 대기를 기다리지 않고 즉시 예약하되 키별 2초 간격을 지킨다. offline에서는 재접속하지 않는다.

IP는 프레임워크가 신뢰 프록시 설정을 적용한 remoteAddr를 사용한다. 임의 X-Forwarded-For를 직접 신뢰하지 않는다. 위 제한은 인스턴스별이며 Redis 장애 중에도 적용한다. 다중 서버에서 서비스 전체의 1000개 상한을 보장하는 정책은 아니며, 인스턴스를 늘리면(GR-113, 보류) 인스턴스 수·분산 편차·총 admission 용량을 기록한다. 서버 용량 초과는 503, IP·요청 제한은 429다.

주기 타이머는 요청 실행 중 같은 키의 조회를 추가하지 않고 dirty로 병합한다. ready·상태 시각 도달·온라인·화면 복귀·수동 재시도도 같은 제한을 적용한다. 상세 시작/종료 시각 타이머는 상세 serverTime과 클라이언트 수신 시각으로 보정해 계산하고, 클라이언트 시각만으로 actions를 허용하지 않는다. 배치 저장 상태가 늦으면 정상 재동기화로 계속 보정한다.

## 13. 최신성 목표와 부하 검증

### 13.1 측정 목표

건강한 네트워크·DB에서 화면이 보이고 구독이 ready인 클라이언트가 대상이다. 시작·종료 시각에서 DB 상태 전환까지의 지연은 SSE 지연과 분리한다. HTTP 조회 실패·오프라인·숨김 탭의 시간은 아래 정상 목표에 포함하지 않고 복구 후 측정한다.

| 지표 | 평시 목표 | 판매 피크 목표 | 측정 구간 |
| --- | --- | --- | --- |
| 변경 알림 전달 | p95 ≤ 2초 | p95 ≤ 3초 | DB 커밋 완료 → 클라이언트 drop-changed 수신 |
| 구독 상품 화면 반영 | p95 ≤ 5초 | p95 ≤ 8초 | 커밋 완료 → 변경 이후 성공 조회·화면 반영 |
| 화면 밖 상품·조용한 알림 유실 복구 | 40초 이내 | 45초 이내 | 마지막 상태 변경 → 다음 성공 목록/상세 재동기화 반영 |
| SSE 실패 후 대체 조회 수렴 | 20초 이내 | 25초 이내 | 마지막 변경 또는 HTTP 접근 복구 중 늦은 시점 → 화면 반영 |
| 화면 복귀 후 수렴 | 5초 이내 | 8초 이내 | visibility 복귀/online 중 늦은 시점 → 성공 조회 반영 |

다중 이벤트를 병합하므로 모든 중간 상태를 화면에 표시할 필요는 없다. 지속 변경 부하는 알림 수신→후속 조회 반영 지연을 측정하고, 최종 상태 수렴은 변경 발생기를 멈춘 뒤 별도로 확인한다. ready 전·미구독 상품은 구독 상품 p95 표본에 섞지 않는다. serverTime을 커밋 순서·상품 버전으로 사용하지 않는다.

### 13.2 부하 조건과 통과 기준

| 항목 | 평시 | 판매 피크 |
| --- | --- | --- |
| 단일 인스턴스 동시 연결 | 100개 | 한계 탐색(참고 800~1000개, GR-180) |
| 상품 구독 구성 | 상세 70%, 24개 목록 30% | 동일 구성 및 별도 인기 상품 집중 시나리오 |
| 한 상품 집중 | 50명 | 피크 연결 전원 같은 상품. 상세 전원 구성도 별도 실행 |
| 실제 커밋 변경률 | 합계 5회/초 | 합계 50회/초, 그중 인기 상품 40회/초 |
| 유지 시간 | 워밍업 2분 + 측정 15분 | 워밍업 2분 + 측정 10분 |
| 느린 수신자 | 연결의 5%, 읽기 속도를 제한해 5초 넘는 전송 정체 유도 | 동일 |
| 주기 재연결·구독 교체 | 10분 수명 만료 및 화면 이동 포함 | 피크 연결 전체 강제 단절 후 지연 분산 재연결 포함 |

실제 주문·취소·결제 확정 경로를 조합해 변경을 만들고, 이벤트만 직접 발행한 결과로 주문 영향 통과를 판정하지 않는다. PG 호출 비용은 분리 기록하며 동일한 PG 응답 지연 조건의 SSE 비활성 기준선과 비교한다. DB를 직접 고쳐 이벤트 원천 검증을 대체하지 않는다.

- 위 최신성 목표를 각각 통과하고, 주문 생성의 서버 처리 p95 악화는 SSE 비활성 기준선 대비 10% 이내여야 한다. 롤백·멱등 재실행에서 잘못된 재고 알림 0건, 초과 판매·중복 반환 0건이다.
- 키별 자동 갱신은 초당 0.5회 이하(2초 창당 시작 최대 1회)다. 상세 STOCK은 두 endpoint이므로 최대 1 HTTP 요청/초/화면이다. 최초 진입 요청은 별도 계수하고 연결/ready 루프가 이 상한을 우회하지 않는지 확인한다.
- 정상 연결의 주기 조회 예상 상한은 서버 상한 1000개 전원 상세 기준 `1000*2/30 ≈ 66.7 HTTP 요청/초`, 장애 모드는 `1000*2/10 = 200 HTTP 요청/초`다. 전원 인기 상세의 연속 STOCK 변경은 최대 약 1,000 HTTP 요청/초를 만들 수 있다. 모두 계산값이며 초기 진입·실패 재시도·수명 재연결은 별도 기록한다. 이 추가 부하를 감당한다는 실측 근거는 아직 없다.
- 병합 후 상품별 변경 전달은 연결당 상품당 초당 최대 1건이다. 이 한계와 별개로 heartbeat·ready·종료 수를 센다. 인기 상품 1000명에서는 최대 약 1,000건/초의 변경 프레임과 약 66.7건/초 heartbeat를 예상한다.
- SSE 활성 대비 추가 JVM live heap은 측정 종료 시 64MiB 이내, SSE 전용 작업 스레드 증가는 16개 이내를 초기 목표로 한다. 전송 큐는 유한해야 하며 연결당 영구 스레드를 두지 않는다. 정상/피크 모두 CPU 평균 70% 이하, 1분 평균 85% 초과 없음, DB 연결 획득 timeout 0건을 목표로 한다.
- 연결 종료·전송 실패 감지 후 10초 이내 emitter·구독 인덱스·대기 작업을 정리한다. 부하 발생기의 자동 재연결을 끄고 전체 단절한 뒤 60초 후 활성 연결·구독·대기 작업이 0이고, 부하 전후 동일 GC 관측 조건의 live heap 차이가 10MiB 이내여야 한다. 접속·종료를 10회 반복해 잔여 자원의 증가 추세가 없어야 한다.
- 1001번째 연결은 503, 같은 IP 51번째 연결 및 60초 창 76번째 요청은 429를 기대한다(`StockStreamRegistryTest`가 기본 설정값으로 확인한다). 제한을 시험할 때 다른 제한이 먼저 걸리지 않도록 IP·요청 간격·인스턴스 분산 조건을 기록한다.
- GR-180은 느린 수신자와 실제 프록시 경유 재연결을 추가 검증한다. 서버 A 변경→서버 B 구독, Redis 구독 일시 단절/메시지 누락, SSE만 정상인 조용한 유실은 다중 서버 전달을 도입할 때(GR-113, 보류) 검증한다. 느린 수신자는 일반 전달 지연 표본에서 분리하되 자원·정리 검증에는 포함한다. Redis 장애 중에도 이미 커밋된 주문 응답과 재고 원장은 유지돼야 한다.

로컬 compose에는 CPU·메모리 예약이 없다. GR-180에서 운영 모사 환경(backend micro + DB Nano 수준 제한 + 왕복 약 3.2ms)으로 재조회 포함 통합 부하를 쟀다([결과](../../k6/sse-stream/result-refetch.md)). 앱 메모리 캐시 적용 후 100연결에서 기준을 충족했고 150연결에서 목록 응답 p95가 기준을 넘었다. DB CPU를 2개로 가정하면 400연결에서도 충족해 결과가 DB CPU 가정에 민감하고, 병목은 캐시 없는 목록 재조회였다. 이 결과는 운영 수용 용량이 아니다. GR-180 보고서에 커밋·인스턴스 수·vCPU/RAM·JVM heap·DB 풀·DB/Redis 배치·부하 발생기 사양·네트워크·활성 연결/상품 분포를 반드시 기록한다. 위 목표 통과 전 운영 수용 용량을 보장하지 않는다.

### 13.3 관측과 프록시 인계

SSE 연결 수·구독 수·ready 지연·종료 사유·제한 거절·병합 전후 이벤트 수·전송 큐/지연/실패·HTTP 재조회 요청률과 지연을 별도로 측정한다. 일반 HTTP 응답 시간 집계에서 SSE 경로를 제외하고, 장기 연결 수명은 별도 분포로 기록한다. 상품 ID·회원·IP·연결 ID를 메트릭 label로 넣지 않는다.

시험용 발생기·수신기에서 시계 오차를 측정하고 커밋 이후의 검증 표식과 화면 조회 결과를 대응시켜 지연을 산출한다. 운영 공개 payload에 주문 정보·검증 표식을 추가하지 않는다. 서버 로컬 측정은 단조 시계를 사용하고 다중 서버/브라우저 간 오차가 100ms를 넘으면 보정하거나 해당 지연 측정을 무효로 기록한다.

배포 프록시는 Nginx다(`deploy/nginx/grab.conf`: SSE 경로에 `proxy_buffering off`, `proxy_read_timeout 1h`). GR-180은 실제 경유 계층에서 버퍼링 비활성, heartbeat가 flush되는지, 읽기 유휴 제한 45초 이상, 최대 연결 수·파일 디스크립터·종료 시 drain을 검증한다. 45초는 15초 heartbeat의 3배라는 초기 가정이다. 확인 없이 프록시 파일이나 운영 설정을 추가하지 않는다.

**GR-180 검증 상태(2026-10-28):** 로컬 Nginx 경유 검증 완료, 운영 설정·TLS·실제 blue/green 전환은 미검증이다([결과](../../k6/sse-nginx/result.md)). 운영 `grab.conf`의 location을 그대로 쓴 로컬 Nginx(1.24, 워커 2)에서 버퍼링 비활성·heartbeat flush(간격 15.03초)·읽기 유휴 90초 유지·reload 중 기존 연결 유지를 확인했다. 첫 reload 회차는 연결은 유지됐지만 heartbeat가 오지 않았고, 다시 실행한 회차는 정상이라 원인을 확인하지 못했다. 재접속은 단일 backend를 종료 후 재시작한 조건에서 300개 연결 전원이 `RECONNECT_REQUIRED`를 받고 재접속했다(재기동 중 502 때문에 복구 p50 13.4초). 최대 연결 수는 Ubuntu 기본값을 가정한 `worker_connections 768`·파일 디스크립터 1024에서 1000개 중 766개만 연결됐고, 4096·8192로 올리면 전원 연결됐다. 운영 Nginx의 실제 값은 레포에 없어 확인이 필요하다.

도메인 이벤트에는 실제로 변경된 상품 ID와 변경 종류만 담는다. native/bulk SQL 뒤 영속성 컨텍스트의 엔티티로 수량 스냅샷을 만들지 않는다. 트랜잭션 내에서 변경 사실을 등록하고 AFTER_COMMIT에서 유한한 비동기 전달 작업으로 넘긴다. 커밋 후 등록/큐 거절·전송 오류는 별도 지표·로그로 기록하고 호출자에게 전파하지 않는다. 발행 자체의 예외도 같은 원칙으로 격리한다. AFTER_COMMIT도 프로세스 종료 시 영속 발행·무손실을 보장하지 않으며 주기 조회로 복구한다.

## 16. GR-109 검증 범위

문서 12개의 상대 링크·코드 펜스, JSON/SSE data 예시 19개 파싱, 정본 표 열 수·절 번호, STOCK-VIEW 요구사항 ID 중복, HTTP 요청률 계산과 문서 전용 변경 검사를 통과했다. 프론트 대상 페이지 문서 3개는 기존 Prettier 설정의 --check를 통과했고 git diff --check도 통과했다. 정적 검증이며 실행·성능 검증을 대신하지 않는다.

백엔드 테스트·빌드, 프론트 lint·test·build·e2e·시각 비교, 부하 테스트, 백엔드 재기동·OpenAPI 생성은 문서 작업 범위이므로 미실행이다. 화면·설정·생성 타입·마이그레이션은 변경하지 않는다. 구현·실측 검증 책임은 위 후속 이슈에 있다.

## 17. GR-110 단계별 구현 기록

1단계에서 `grab.stock-stream.*` 설정 바인딩·기동 검증, 원문 쿼리 파싱, 공개 상품 집합 검증, 상품별 구독 저장소, 인스턴스/IP 연결 제한과 고정 창 요청 제한을 구현했다. IP 추적 상태도 최대 10,000개로 제한하며 연결이 없고 요청 창이 만료된 상태는 다음 접근/명시적 정리에서 제거한다. 구독 해제는 멱등하고 슬롯과 상품 인덱스를 함께 반환한다. 공개 검증 실패·잘못된 요청도 요청 횟수에는 포함하되 연결 슬롯은 점유하지 않는다.

검증: 신규 설정·쿼리·구독·제한/동시성 테스트, PostgreSQL Testcontainers 공개 상태/혼합 요청 통합 테스트, 기존 공개 상세·공개 endpoint/보안·Swagger 회귀를 포함해 118건이 통과했다. 기존 조회 API와 재고 원장 코드는 변경하지 않았다.

실행 명령(Backend):

```bash
./gradlew test --tests '*StockStream*Test' --tests '*PublicDropSubscriptionServiceIntegrationTest' --tests '*PublicDropDetailIntegrationTest' --tests '*PublicEndpointSecurityTests' --tests '*SecurityFilterChainTests' --tests '*SwaggerEndpointTests'
```

1단계 완료 시점에 SSE endpoint·emitter·보안 경로·HTTP 오류 헤더·전송/heartbeat/수명 정리는 2단계, 실제 변경의 커밋 후 전달은 3단계에서 연결한다. 429/503 코드 enum은 추가했지만 HTTP로 반환하는 구독 API는 아직 없다. 전체 테스트·컨테이너 이미지 빌드는 단계 통합 검증에서 수행하며, 실제 SSE 수신/종료·두 브라우저·부하는 이 단계에서 실행하지 않았다. 프론트·OpenAPI 계약은 아직 변경되지 않아 생성 타입도 갱신하지 않았다.


### GR-110 2단계 — SSE API·전송과 수명 관리

`GET /api/v1/drops/stock-stream`과 명세의 세 이벤트, 정확한 공개 GET/오류 dispatch 범위, 기존 JWT/CORS 정책, JSON 오류와 Retry-After를 연결했다. 실행 OpenAPI는 성공을 문자열 `text/event-stream`, 실패를 공통 JSON으로 구분한다. 생성 스냅샷·프론트 타입 갱신은 도메인 이벤트 연결 후 5단계에서 진행한다.

Servlet async 시작 후 최초 onWritePossible 통지를 받은 연결만 활성화하고 ready를 처음 전송한다. SseEmitter와 Servlet 비차단 쓰기를 함께 사용해 소켓이 쓰기 불가 상태면 대기하지 않고 종료한다. 다른 HTTP 경로의 소켓 설정은 바꾸지 않는다. SseEmitter timeout=0은 무제한 보장의 의미가 아니라 자체 수명/정체 감시와 충돌하지 않기 위한 설정이다. 10분 수명·전송 정체 감시·heartbeat는 자체 pump가 관리한다.

송신 스레드 8개·유한 대기 큐(연결 상한 크기)와 timer 2개를 사용한다. 전용 실행기는 소유자 빈 안에 두고 Executor/ScheduledExecutorService 타입으로 노출하지 않아 기존 공용 스케줄러 자동 설정을 대체하지 않는다. 연결마다 타이머나 상시 전용 스레드를 만들지 않는다. 50ms pump에서 연결별 상품 병합 창·수명·정체·IP TTL을 확인한다. 구독 ID 상한과 pending 한도를 설정 시 함께 검증하므로 상품별 pending 집합이 무한 증가하지 않는다. ready 전 변경도 이 집합에 합치고 ready 뒤 전달한다.

동일 연결의 송신은 한 작업으로 직렬화하며, 종료·오류·not-ready·큐 거절은 멱등하게 emitter·인덱스·슬롯·대기 작업을 정리한다. 송신 전 공개 상태를 다시 확인해 DRAFT/삭제가 감지되면 데이터 대신 SUBSCRIPTION_INVALIDATED 종료를 시도한다. CANCELED·ENDED는 계속 공개로 취급한다. 이 송신 전 재확인은 비공개 전이가 없어 결과가 항상 같고 연결 수에 비례해 DB 조회를 만들어 GR-163에서 제거했다(8절, `k6/sse-stream/result.md`). 서버 종료는 SmartLifecycle에서 웹 서버 graceful shutdown보다 먼저 종료 안내·정리를 수행한다.

내부 `StockStreamHub.publish`는 로컬 변경 신호의 전달 진입점이다. 이번 단계에서는 테스트가 이를 호출하며, 주문·결제·배치가 자동으로 호출하지 않는다. 운영용 테스트 이벤트 API는 추가하지 않았다. 3단계에서 실제 변경의 커밋 후 전달을 연결한다.

검증은 PostgreSQL Testcontainers와 실제 Tomcat HTTP/TCP에서 수행한다. 두 독립 연결·다중 구독·다른 상품 제외·ready/heartbeat/수명 종료, 연결 전 400/401/404/429/503·JSON/Retry-After, 비공개 감지(GR-163에서 제거), 반복 단절을 확인한다. 별도 TCP 시험은 작은 수신 버퍼에서 ready 후 읽기를 멈춰 전송 자원이 30초 연결 수명 전에 정리되는지 확인하며, 운영 피크 부하나 실제 프록시 검증을 대신하지 않는다. 단위 테스트는 병합·ready 경합·정체 감시·큐 거절·실패 격리·종료 정리를 검증한다.

최종 검증: `./gradlew build` 전체 테스트 1,596건 성공·실패 0·건너뜀 0으로 통과했다(로컬 init script는 결과 요약 출력용). 기본 테스트 힙의 OOM을 재현해 테스트 JVM 힙을 1GiB로 명시했다. 실제 서버 시험은 전용 PostgreSQL 컨테이너·작은 DB 풀·클래스 종료 시 컨텍스트 정리로 격리한다. 기존 공용 스케줄러의 4개 스레드 설정 보존도 검증했다. 문서 상대 링크·JSON/SSE 예시·공백 검사도 통과했다.

미실행: 실제 브라우저 화면 연동·커밋 후 도메인 이벤트·Redis/프록시·운영 피크 부하는 후속 단계/이슈 범위다. 컨테이너 재기동과 프론트 OpenAPI 스냅샷/생성 타입 갱신은 5단계에서 수행한다. 백엔드 jar 빌드는 위 build에 포함되며 배포 이미지 빌드는 이번 단계에서 실행하지 않았다.

### 3단계 — 커밋된 도메인 변경 연결

`StockChangePublisher`는 트랜잭션 안에서 상품 ID·변경 종류만 등록한다. `StockChangeListener`는 AFTER_COMMIT에서 로컬 hub의 유한 버퍼에 병합하고 기존 전송 실행기가 조회·송신한다. 롤백 시 전달하지 않으며 등록·커밋 후 전달 실패는 주문 응답으로 전파하지 않는다. 트랜잭션 밖의 호출은 무시한다.

주문 생성·미결제 취소·만료는 STOCK, 결제 확정은 SALES, 결제 완료 취소는 STOCK+SALES다. 판매 시작·종료·판매자 취소는 STATUS다. 기존 메일 이벤트와 PG 결과 처리·멱등 판정은 유지한다. 종료 배치는 시작 배치와 같이 SKIP LOCKED로 ID를 확보한 뒤 같은 트랜잭션에서 갱신하며 외부 건수 반환은 유지한다. 조회 API는 변경하지 않았다.

실제 PostgreSQL·Tomcat 통합 테스트로 두 HTTP 구독자의 주문·결제·취소 수신, 커밋 전 미전달·롤백 미전달, 만료·종료 재실행 미발행을 확인했다. HTTP 클라이언트 검증과 별도로 실제 두 브라우저 수신은 4단계에서 확인한다.

### 4단계 — 브라우저·회귀 검증과 관측

격리된 PostgreSQL Testcontainers와 실제 Tomcat에서 주문 커밋·롤백, 취소·만료·상태 전환, 연결 제한·반복 정리·느린 수신자를 검증한다. `StockStreamHttpIntegrationTest.twoBrowsersReceiveCommittedOrder`는 서로 다른 두 Chromium 프로세스의 EventSource와 별도 상품 구독을 사용한다. 테스트 데이터는 전용 DB에만 만들며 브라우저와 프로세스는 finally에서 종료한다. 브라우저 의존성은 Frontend의 기존 Playwright를 사용한다.

```bash
# Frontend 의존성과 Playwright Chromium이 설치된 개발 환경에서, Backend 디렉터리 실행
GRAB_SSE_BROWSER_TEST=true ./gradlew build
```

위 전체 검증은 1,608건 성공·실패/건너뜀 0건이다. 환경변수가 없는 일반 CI 실행에서는 브라우저 설치가 필요한 테스트 1건만 건너뛰며, HTTP·TCP·커밋 경계 테스트는 계속 실행한다. 운영 200연결 부하·Redis·프록시 검증을 대체하지 않는다.

`StockStreamMetricsConfig`는 SSE 경로의 `http.server.requests`를 제외해 지속 연결 수명이 일반 API 지연 통계에 섞이지 않게 한다. SSE는 다음 전용 지표로 관측한다. 상품·IP·회원·연결 ID 태그는 없다.

| Micrometer 이름 | 의미 |
| --- | --- |
| `grab.stock.stream.connections` | 활성 연결 수 |
| `grab.stock.stream.subscriptions` | 연결별 상품 구독 수 합계 |
| `grab.stock.stream.pending` | 전송 대기 중인 상품 항목 수 합계 |
| `grab.stock.stream.rejected` | admission 거절 누계. reason은 rate/ip/capacity/tracking 4개 고정 값 |
| `grab.stock.stream.disposed` | 실제 해제한 연결 누계. 중복 해제 제외 |
| `grab.stock.stream.signals` | hub가 받은 변경 신호 누계 |
| `grab.stock.stream.merged` | 연결별 기존 대기 상품에 추가 병합한 신호 누계 |
| `grab.stock.stream.sent` | 전송한 SSE 프레임 누계. ready·주석·종료 포함 |
| `grab.stock.stream.failures` | 전송 작업 실패 누계 |
| `grab.stock.stream.timeouts` | 준비/전송 정체로 종료한 연결 누계 |
| `grab.stock.stream.queue.rejected` | 전송 큐 거절 누계 |

Prometheus에서는 점을 밑줄로 바꾸고 카운터에 `_total`을 붙인 이름으로 노출한다. `sent`는 브라우저 수신 확인이나 화면 반영 완료를 의미하지 않는다.

### 5단계 — 생성 계약과 후속 인계

백엔드 컨테이너를 `docker compose up -d --build backend`로 재빌드·기동한 뒤 Frontend에서 `npm run api:snapshot` → `npm run api:generate`를 실행했다. drop 그룹의 SSE 200 응답은 `text/event-stream: string`, 연결 전 오류는 JSON으로 생성된다. 생성 타입은 스트림을 읽는 API 클라이언트나 이벤트 data 타입을 자동 구현하지 않는다. 이벤트 계약은 7절을 따른다.

기존 drop 조회 작업의 OpenAPI 정의는 이전 스냅샷과 동일함을 비교했다. 재생성 과정에서 main GR-95의 구매자·판매자 결제 이력 GET 작업이 이전 order/payment 생성 파일에 없었던 것도 확인했다. 실행 서버·PAYMENT.md 1.3~1.4와 일치하는 추가 항목이므로 생성 결과를 함께 동기화했다. 기존 작업 정의 변경은 없다. 생성 파일을 직접 편집하지 않았다.

| 후속 이슈 | 인계 내용 |
| --- | --- |
| GR-111 상세 | 정확한 구독 URL·쿠키/401 정책(6절), ready 후 최신 조회·이전 조회 경합 방지·선택 유지·이벤트 종류별 기존 조회 재사용(7~9절). EventSource는 JSON API 호출기와 별도로 연결 수명·종료·재연결·visibility를 관리하며 공통 인증 정책을 유지한다. 최소 조회 간격 2초·정상 주기 30~35초·장애 주기 10~12초는 12절대로 구현한다. |
| GR-112 목록 | 입력 토큰 100개 상한·한 화면 한 연결·정렬한 집합 비교·구독 교체·화면 밖 후보의 주기 조회·품절/인기순·페이지 유지 계약은 8~12절을 따른다. SALES는 가용 재고가 같아도 인기순 재조회 근거다. |
| GR-113 인프라 | 커밋 후 `StockChangeListener` → `StockStreamHub.publish`가 로컬 전달 경계다. Redis 도입 시 발행과 수신 경로를 분리해 로컬/Redis 이중 송신을 피한다. 원장은 PostgreSQL이며 알림은 재생되지 않는다. 비차단 쓰기·5초 정체·유한 큐/버퍼·전용 지표를 유지하고 실제 프록시·다중 서버·200연결/피크 부하를 13절 조건으로 실측한다. |

최종 검증: 백엔드 브라우저 포함 전체 빌드 1,608건 성공, 추가 결제 무변경/계측 검증 12건 성공. 프론트 lint·단위 테스트 111건·TypeScript/Vite build·PC/모바일 E2E 228건 성공. 실제 브라우저 검증은 격리된 PostgreSQL에서 수행했으며 개발 DB에 테스트 데이터를 삽입하지 않았다. 화면 변경이 없어 시각 비교는 실행하지 않았다. 운영 부하·프록시·Redis는 후속 이슈 범위로 미실행이다. 사용자 요청에 따라 단계별 커밋·푸시까지만 진행하고 PR은 생성하지 않는다. 작업 브랜치의 GitHub Actions 조회 결과 실행 이력은 없었다. 대상 브랜치 조건 밖의 푸시이므로 CI 미실행이며, 로컬 검증 결과와 구분한다.
