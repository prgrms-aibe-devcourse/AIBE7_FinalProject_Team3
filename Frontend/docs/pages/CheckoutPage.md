# 주문·결제

- 경로(계획): `/checkout/:orderId` 및 결제 성공·실패 콜백 (같은 화면의 상태)
- 요구사항: ORDER-001~003, STOCK-001~005, PAY-001~005
- [와이어프레임](../wireframes/CheckoutPage.html)

## 조회·처리 계약

상품 상세에서 옵션·수량을 고른 뒤 배송지(수령인·연락처·우편번호·주소)를 입력한다. `POST /api/v1/orders`에는 `Idempotency-Key`를 보내며 금액은 보내지 않는다. 생성 응답의 `orderId`, `orderNumber`, `totalAmount`, `paymentExpiresAt`을 결제 화면의 기준으로 삼고 새로고침 시 `GET /api/v1/orders/{orderId}`로 복원한다. 결제창은 토스페이먼츠 테스트 환경의 `CARD` 방식으로 연다. 성공 콜백의 `paymentKey`, `amount`로 `POST /api/v1/orders/{orderId}/payments`를 호출한다. PG의 `orderId`는 서버 주문 UUID가 아니라 `orderNumber`와 대조한다.

## 화면 구성

- PC: 배송지와 주문 상품을 왼쪽, 서버가 확정한 상품 금액·배송비·총액과 결제 버튼을 오른쪽에 둔다.
- 모바일: 배송지→상품→금액→결제 버튼 순서로 한 열에 배치한다.
- 주문 생성 전, 결제 대기, 결제 처리 중, 성공, 실패, 결과 확인 중을 같은 흐름에서 보여준다. 결과 화면에는 주문 상세로 가는 링크를 둔다.

## 행동과 이동

주문 생성은 한 번의 의도에 같은 멱등 키를 사용하고 중복 제출을 막는다. 결제는 `PAYMENT_PENDING`이면서 마감 전일 때만 시작한다. 성공 콜백은 즉시 승인 API를 호출하고 같은 요청 재전송에는 같은 멱등 키·본문을 사용한다. 명확히 `FAILED`이고 주문이 아직 결제 대기·마감 전인 경우에만 결제창 재시도를 허용한다. 결과 불명(`PENDING`·`UNKNOWN`) 또는 `reconciliationStatus: REQUIRED`면 결제창을 다시 열지 않고 결과 확인 중으로 안내한다.

## 상태와 예외

재고 부족·판매 전/종료·주문 만료·결제 거절·콜백 금액/주문번호 불일치·네트워크 오류를 구분한다. 결제 성공 표시는 `status: SUCCEEDED`와 `reconciliationStatus: NONE`, 주문 `PAID` 확인 후에만 한다. 콜백 실패에는 결제 상태를 확인하고 주문 상세로 돌아갈 수 있게 한다. 민감한 결제 키는 화면에 표시하지 않는다.

## 인수 조건

배송지 입력, 서버 확정 금액, 결제 마감, 테스트 결제 성공·거절·만료·결과 불명, 새로고침·중복 클릭을 확인한다. 콜백 URL과 새로고침 복원 방식은 결제 연동 구현 시 `PAYMENT.md` 계약과 함께 확정한다.

공통: 로딩·실패·권한 오류를 구분하고 키보드 포커스와 직접 진입·뒤로 가기를 확인한다. 기존 색상·글꼴을 유지하며 PC 1440×900, 모바일 390×844에서 가로 넘침이 없어야 한다. 실제 구현은 별도 이슈에서 수행한다.
