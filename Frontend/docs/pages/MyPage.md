# 마이페이지·내 정보

- 경로: `/my` (기존 화면 확장)
- 요구사항: AUTH-004, MY-001, MY-003
- [와이어프레임](../wireframes/MyPage.html)

## 조회·처리 계약

`GET /api/v1/users/me`로 본인 이메일·닉네임·역할·프로필 이미지를, `GET /api/v1/users/me/wishes`로 WISH를, `GET /api/v1/orders`로 주문 목록을 조회한다.

- 닉네임 수정은 `PATCH /api/v1/users/me`에 `{ nickname }`을 보내고 변경된 내 정보 응답을 받는다.
- LOCAL 비밀번호 변경은 `PATCH /api/v1/users/me/password`에 `{ currentPassword, newPassword }`를 보내고 성공 시 본문 없는 204를 받는다.
- 두 요청은 실제 백엔드 API를 사용한다(GR-131). 인증 쿠키·CSRF·401 재발급은 공통 클라이언트가 처리한다. 입력 규칙과 오류 코드는 [회원·인증 API](../../../Backend/docs/development/api-spec/MEMBER_AUTH.md) 1.2.3·1.10·1.11절을 따른다.
- 프로필 이미지 등록·삭제 API는 백엔드에 구현되어 있으며 마이페이지의 관리 UI 연동은 GR-132에서 진행한다.

## 화면 구성

- 기존 WISH·주문 2영역 위에 계정 요약과 내 정보 편집 진입을 추가한다. 주문 행은 [주문 상세](OrderDetailPage.md)로 이동한다.
- PC는 계정 요약 아래 WISH·주문 2열, 모바일은 계정→주문→WISH 한 열로 배치한다. 정보 편집은 같은 페이지의 패널로 연다.
- "정보 수정"을 누르면 이메일 읽기 전용·닉네임 입력·저장 버튼이 있는 폼을 연다. LOCAL 계정은 그 아래에 현재·새 비밀번호 입력과 변경 버튼이 있는 별도 폼을 표시한다. KAKAO·GOOGLE 계정에는 비밀번호 폼을 표시하지 않는다.
- 두 폼은 오류와 처리 중 상태를 각각 관리한다. 처리 중인 폼의 제출 버튼만 비활성화하고 "저장 중…" 또는 "변경 중…"을 표시한다. 새 라우트나 비밀번호 전용 토글은 두지 않는다.

## 행동과 이동

닉네임 수정 성공 시 서버 응답으로 내 정보 캐시(`['auth', 'me']`)를 교체해 계정 요약과 입력값을 갱신한다. 추가 조회 없이 패널을 열어 두고 "닉네임을 변경했어요."를 안내한다. 현재 헤더에는 닉네임을 표시하지 않는다. 이메일은 조회만 가능하다.

비밀번호 변경 성공 시 두 입력을 비우고 "비밀번호를 변경했어요."를 안내한다. 현재와 다른 기기의 로그인 세션은 유지하며 재로그인을 요구하지 않는다. 입력값은 폼 상태에만 두고 패널을 닫거나 로그아웃하면 사라진다.

하단 안내는 LOCAL 계정에 "프로필 이미지 관리는 API 연동 시 제공됩니다.", 소셜 계정에 "소셜 계정에는 비밀번호 변경이 제공되지 않습니다."를 표시한다. 판매자 미신청 회원에게 [판매자 신청](SellerApplyPage.md), 승인된 판매자에게 판매자 작업 공간 링크를 보여준다. WISH 항목은 상품 상세로, 주문 항목은 주문 상세로 이동한다.

## 상태와 예외

비회원은 로그인으로 이동한다. 빈 WISH·주문은 각각 독립된 빈 상태다. 타인의 정보·주문을 노출하지 않는다.

- 닉네임은 규칙 위반 또는 앞뒤 공백 제거 후 현재 값과 대소문자까지 같으면 요청하지 않는다. 서버의 닉네임 중복·형식·동일 값 오류도 닉네임 필드 오류로 표시한다. 저장 실패 시 계정 요약의 기존 값은 유지한다.
- 현재 비밀번호는 필수값만, 새 비밀번호는 가입과 같은 규칙으로 사전 검증한다. 규칙을 통과한 두 값이 같으면 요청하지 않는다. 서버에서 현재 비밀번호 불일치를 받으면 현재 입력만 비우고 포커스를 옮기며, 그 밖의 실패는 입력을 유지한다.
- 필드 오류는 각 폼의 입력들 다음 줄에 전체 폭으로 표시하고 `aria-invalid`·`aria-describedby`로 해당 입력과 연결하며 오류 입력에 포커스를 옮긴다. 모바일에서도 비밀번호 오류 영역은 두 입력 다음에 있어 현재 비밀번호 오류가 새 비밀번호 입력 아래에 보일 수 있다.
- 네트워크·서버 오류 등 일반 실패와 비밀번호 변경 불가 오류는 해당 폼 하단의 `role="alert"` 영역에 표시한다. 서버의 `reason`을 그대로 노출하지 않고 오류 코드에 맞춘 문구를 사용한다.

## 인수 조건

계정 유형별 편집, 닉네임 저장 후 캐시·표시 갱신과 새로고침 유지, 비밀번호 변경 후 입력 비움·세션 유지, 사전 검증 시 요청 없음, 저장 중 중복 제출 방지, 필드 오류 연결·포커스와 일반 실패 표시를 확인한다. 주문·WISH 빈 상태, 판매자 신청/승인별 링크, 모바일 가로 넘침도 확인한다.

공통: 로딩·빈 결과·실패·권한 오류를 구분하고 키보드 포커스와 직접 진입·뒤로 가기를 확인한다. [공통 디자인 기준](../DESIGN.md)을 따르며 PC 1440×900, 모바일 390×844에서 가로 넘침이 없어야 한다. 닉네임 수정·LOCAL 비밀번호 변경은 GR-131 구현 범위이며, 이 문서와 정적 와이어프레임의 갱신 자체가 실제 API·계정 유형별 동작 검증 완료를 의미하지는 않는다.

## 디자인 적용 (2026-10-13)

계정 요약의 상단 경계선과 닉네임을 강조한다. WISH·주문 패널의 안쪽 여백을 통일하고 긴 이메일은 줄바꿈한다.

[공통 디자인 기준](../DESIGN.md)을 함께 따른다.

## 헤더·판매자 진입 (GR-128)

일반 화면과 `/seller/apply`는 WISH·GRAB 기본 헤더를 사용한다. `users/me.roles`에 SELLER가 있을 때만 그 옆에 SELLER 링크(`/seller`)를 표시한다. 일반 회원은 MY → 판매자 신청 → 운영자 승인 순서로 권한을 취득하며 제출 성공·신청 상태만으로 권한을 추정하지 않는다. 판매자 작업 공간 헤더는 DASHBOARD·DROPS·ORDERS·INVENTORY·SALES와 SHOP(`/wish`) 복귀 링크를 사용한다. 인증 로딩·로그아웃·계정 변경 시에도 실제 역할을 따른다.
