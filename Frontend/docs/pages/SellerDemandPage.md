# 판매자 수요 분석 제안서

- 경로: `/seller/drops/:dropId/demand` (`HashRouter`, 실제 URL은 `/#...`)
- 구현 이슈: GR-144
- [와이어프레임](../wireframes/SellerDemandPage.html)

## 조회 계약

`Backend/docs/development/api-spec/DEMAND.md` 2절의 API를 실제로 호출한다(Mock 없음).

| 용도                         | API                                                            |
| ---------------------------- | -------------------------------------------------------------- |
| 기본 가정의 제안             | `GET /api/v1/seller/drops/{dropId}/demand-analysis`            |
| 가정 변경 재계산(저장 안 함) | `POST /api/v1/seller/drops/{dropId}/demand-analysis/calculate` |
| 계획 저장                    | `POST /api/v1/seller/drops/{dropId}/demand-plans`              |
| 계획 이력                    | `GET /api/v1/seller/drops/{dropId}/demand-plans`               |
| 계획 상세                    | `GET /api/v1/seller/demand-plans/{planId}`                     |
| 결정 기록                    | `POST /api/v1/seller/demand-plans/{planId}/decision`           |

DROP 이름은 판매자 DROP 상세(`GET /api/v1/seller/drops/{dropId}`) 캐시를 함께 쓴다. 계산은 서버가 하고 화면은 응답을 그대로 표시한다. 화면에서 수량을 다시 계산하지 않는다.

## 화면 구성

- 제목: DROP 이름, 계산 시각, 판매 시작까지 남은 시간. DROP 상세로 돌아가는 링크.
- 판매 계획: 예상 판매량(`expected`)과 예상 범위(`low`~`high`), 준비 권장 수량(`recommended`, 안전 재고 포함), 현재 준비 수량(DROP에 설정한 활성 옵션 수량 합계, 판매된 수량이 아님)과 권장 대비 차이. 차이는 부호 대신 "권장보다 부족 N개"(품절 위험) 또는 "권장보다 많음 N개"(재고가 남을 위험)로 표시한다. 예상 판매량과 준비 권장 수량은 이름과 설명으로 구분한다. 수량을 계산하지 못하면 숫자 대신 부족한 데이터와 해결 방법을 표시한다.
- 옵션별 배분: 옵션 표시명, 현재 준비 수량, 추천 수량, 권장 대비("N개 부족"·"N개 많음"·"같음") 표.
- 근거 데이터: 활성 WISH 수, 판매 시작까지 남은 시간, 최근 14일 등록 수(근사치 표시), 내 실적과 시장 평균 전환율 비교(전환율·구간·구매자당 수량·신뢰도·표본). 계획에 사용한 기준을 표시한다. 시장 평균은 표본 수를 구간으로만, WISH 수는 "약 N명"으로 표시하고 기준 시점을 함께 적는다. 기준 미달이면 "제공되지 않음"으로 표시한다.
- 가정: 사용한 전환율·구매자당 수량·안전 재고율과 각 출처(내 실적·시장 평균·기본값·직접 입력).
- 가정 수정: 전환율 기준(자동·내 실적·시장 평균·직접 입력), 직접 입력 전환율(%), 안전 재고율(%)을 바꿔 다시 계산한다. 다시 계산하면 기본 제안 대비 준비 권장 수량과 예상 판매량의 변화량을 표시한다. "이 가정으로 계획 저장"으로 현재 가정을 저장한다.
- 안내: 응답의 `notes`(WISH 없이 구매한 사용자 제외 등)와 "제안은 참고용이며 재고를 바꾸지 않는다"는 안내.
- 저장한 계획: 최근 저장순 목록(상태, 준비 권장 수량, 저장·결정 시각). 항목을 열면 저장 시점 계획과 결정을 보여 준다.
- 결정: 결정 전(`DRAFT`) 계획에 수락 / 수정 후 확정 / 거절 버튼. 수정은 옵션별 수량(0 이상 정수, 저장 시점 추천 수량으로 시작)을, 수정·거절은 선택 사유(500자)를 입력한다. 결정 후에는 결정 상태·수량·사유·시각을 보여 준다.
- LLM 설명: `explanationStatus`가 `GENERATED`일 때만 요약·이유·위험·권장하지 않는 선택을 표시한다. `PENDING`은 "설명을 준비하고 있어요"만 표시하고, `DISABLED`·`FAILED`·`DISCARDED`는 영역을 숨기고 계산 결과만 보여 준다.
- PC: 판매 계획과 옵션별 배분을 위, 근거 데이터와 가정 수정을 두 열로 나란히, 저장한 계획을 아래에 둔다.
- 모바일: 판매 계획 → 옵션별 배분 → 가정 수정 → 근거 데이터 → 저장한 계획 순서로 세로로 쌓는다. 옵션 표는 내부 가로 스크롤을 허용한다.

## 행동과 이동

- DROP 상세의 제안 카드·관련 작업 링크에서 들어온다. 뒤로 가기·직접 진입 모두 같은 화면을 보여 준다.
- 저장하면 목록 맨 위에 새 계획이 열린 상태로 추가되고 토스트로 알린다.
- 결정은 계획당 한 번만 기록한다. 결정 버튼은 처리 중 비활성화하고, 성공하면 토스트로 알리고 목록·상세를 다시 조회한다.
- 결정은 판매 수량을 바꾸지 않는다. 판매 수량 반영은 범위 밖이며 화면에 수량을 바꾸는 버튼을 두지 않는다.

## 상태와 예외

| 상황                                            | 표시                                                                                                         |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 로딩                                            | 제안서·이력 영역별 로딩                                                                                      |
| `DEMAND_ANALYSIS_UNAVAILABLE`(409)              | 제안서 대신 "판매 시작 전 WISH DROP만 분석할 수 있어요". 저장한 계획 이력은 계속 표시하고 결정 버튼은 숨긴다 |
| `DROP_ACCESS_DENIED`·`DROP_NOT_FOUND`·잘못된 ID | 페이지 전체 안내와 DROP 목록 링크                                                                            |
| `NO_ACTIVE_WISH`·`NO_CONVERSION_SAMPLE`         | 수량 대신 부족한 데이터와 다음 행동(다른 기준 선택·전환율 직접 입력)                                         |
| `SMALL_CONVERSION_SAMPLE`                       | 수량을 표시하고 표본이 적어 범위가 넓다는 안내                                                               |
| `VALIDATION_FAILED`                             | 입력값 확인 안내(전환율 1~100%, 안전 재고율 0~100%)                                                          |
| `DEMAND_PLAN_ALREADY_DECIDED`(409)              | 이미 결정된 계획이라고 알리고 최신 상태를 다시 조회                                                          |
| 이력 조회 실패                                  | 제안서는 유지하고 이력 영역만 재시도                                                                         |

## 인수 조건

- 예상 판매량과 준비 권장 수량이 서로 다른 이름·설명으로 구분된다.
- 다시 계산 결과는 저장하지 않으며 기본 제안 대비 변화량이 보인다.
- 저장·결정 후 목록과 상세가 최신 상태로 바뀌고, 같은 계획을 두 번 결정할 수 없다.
- 시장 평균은 구간·근사치로만 표시하고 다른 판매자의 개별 정보를 보여 주지 않는다.

공통: 로딩·빈 결과·실패·권한 오류를 구분하고 키보드 포커스와 직접 진입·뒤로 가기를 확인한다. [공통 디자인 기준](../DESIGN.md)을 따르며 PC 1440×900, 모바일 390×844에서 가로 넘침이 없어야 한다.
