# 판매자 DROP 상세

- 경로: `/seller/drops/:dropId` (`HashRouter`, 실제 URL은 `/#...`)
- 구현 이슈: GR-82 · GR-57 · GR-83
- [와이어프레임](../wireframes/SellerDropDetailPage.html)

## 조회 계약

`GET /api/v1/seller/drops/{dropId}`로 상품·옵션·이미지·일정을, `GET /api/v1/seller/drops/{dropId}/stocks`로 옵션별 재고를 조회한다. 주문·실적의 상세 이동은 필터를 가진 분야별 경로로 보낸다.

## 화면 구성

- PC: 상품명·상태·공개/취소 작업, 일정·설명·이미지와 옵션 운영 정보, 해당 상품의 주문·재고·실적 바로 가기를 배치한다. 종합 대시보드의 긴 목록을 복제하지 않는다.
- 모바일: 상품 상태와 주요 작업을 먼저 표시하고 운영 정보·옵션 현황을 세로로 쌓는다. 표는 읽을 수 있는 행 단위로 바꾸거나 내부 스크롤을 제한적으로 사용한다.

## 수요 분석 참고 카드 (GR-144)

WISH 상태이고 판매 시작 전인 DROP에 WISH 반응으로 계산한 준비 수량을 **참고용**으로 보여 준다(DEMAND-001~006, GR-175). 계획을 저장하거나 결정을 기록하지 않고, 재고는 바꾸지 않는다. 공개(WISH) 후에는 DROP과 옵션 수량을 수정할 수 없어(DRAFT만 수정 가능) 재고 조정 안내나 링크를 두지 않는다.

**조회 계약** — `Backend/docs/development/api-spec/DEMAND.md` 2절을 실제로 호출한다. 계산은 서버가 하고 화면은 응답을 그대로 표시한다.

| 용도                         | API                                                            |
| ---------------------------- | -------------------------------------------------------------- |
| 기본 가정의 분석             | `GET /api/v1/seller/drops/{dropId}/demand-analysis`            |
| 가정 변경 재계산(저장 안 함) | `POST /api/v1/seller/drops/{dropId}/demand-analysis/calculate` |

**화면 구성** — 옵션 운영 아래, 관련 작업 위에 한 패널로 둔다.

- 제목 "수요 분석 (참고용)"과 계산 시각. `suggestion.ready`가 참이면(WISH 30명 이상 또는 판매 시작 48시간 이내) "지금 확인해 보세요" 표시를 붙인다(DEMAND-006).
- 요약: 활성 WISH 수, 판매 시작까지 남은 시간, 예상 판매량(`expected`)과 범위(`low`~`high`), 준비 권장 수량(`recommended`, 안전 재고 포함), 현재 준비 수량과 차이. 차이는 부호 대신 "권장보다 부족 N개"·"권장보다 많음 N개"·"권장과 같음"으로 표시한다.
- 생성 단계 추천과 비교: `initialRecommendation`이 있으면 "공개할 때 추천 N개(과거 판매량 기준) → WISH 기준 M개"로 보여 준다. 기록이 없거나 그때 추천 수량이 없었으면 이 줄을 숨긴다.
- 데이터 부족: 수량을 계산하지 못하면 숫자 대신 부족한 데이터와 다음 행동(다른 기준 선택·전환율 직접 입력)을 보여 준다. 표본이 적으면(`SMALL_CONVERSION_SAMPLE`) 범위가 넓다는 안내를 붙인다.
- "근거와 가정 보기"(접힘): 옵션별 배분 표(옵션 표시명·현재·추천·권장 대비), 내 실적과 시장 평균 전환율 비교(시장 평균은 표본 수를 구간으로, WISH 수를 "약 N명"으로, 기준 시점과 함께), 사용한 가정과 출처, 가정 수정(전환율 기준 자동·내 실적·시장 평균·직접 입력, 직접 입력 전환율 %, 안전 재고율 %)과 다시 계산. 다시 계산하면 기본 가정 대비 준비 권장 수량·예상 판매량의 변화량을 보여 주고 "기본 가정으로"로 되돌린다.
- 안내: 응답의 `notes`와 "참고용이며 재고를 바꾸지 않아요".
- LLM 설명 영역은 GR-146에서 붙인다.
- 모바일: 요약 항목을 두 열로 쌓고 옵션 표는 내부 가로 스크롤을 허용한다.

**상태와 예외**

| 상황                                                  | 표시                                                   |
| ----------------------------------------------------- | ------------------------------------------------------ |
| WISH가 아니거나 판매 시작 시각이 지남                 | 카드를 그리지 않고 조회하지 않는다                     |
| 조회 중                                               | 패널 안 로딩                                           |
| 조회 실패                                             | 패널 안 오류와 다시 시도. 상품 정보·재고 영역은 그대로 |
| `DEMAND_ANALYSIS_UNAVAILABLE`(409, 판매 시작 직후 등) | "판매가 시작되어 수요 분석을 볼 수 없어요"             |
| `NO_ACTIVE_WISH`·`NO_CONVERSION_SAMPLE`               | 수량 대신 부족한 데이터와 다음 행동                    |
| 재계산 `VALIDATION_FAILED`                            | 입력값 확인 안내(전환율 1~100%, 안전 재고율 0~100%)    |

**인수 조건** — 예상 판매량과 준비 권장 수량이 서로 다른 이름·설명으로 구분된다. 다시 계산 결과는 저장하지 않고 기본 가정 대비 변화량이 보인다. 시장 평균은 구간·근사치로만 표시한다. 저장·결정 버튼이 없다.

## 행동과 이동

DRAFT만 편집·공개할 수 있고 WISH 취소는 판매 시작 전만 제공한다. 주문·재고·실적은 각각 `dropId`를 URL에 전달한다. 소비자 상세 링크도 제공한다.

## 상태와 예외

소유하지 않은 DROP·없는 ID·잘못된 ID, 공개 검증 실패·상태 전환 충돌·재고 조회 실패를 구분한다. 재고 영역 실패가 상품 기본 정보를 숨기지 않는다.

## 인수 조건

소유권과 상태별 작업을 지키며 해당 DROP의 주문·재고·실적 이동 대상이 정확하다. 재고 수량은 가용·확보·판매를 구분한다.

공통: 로딩·빈 결과·실패·권한 오류를 구분하고 키보드 포커스와 직접 진입·뒤로 가기를 확인한다. [공통 디자인 기준](../DESIGN.md)을 따르며 PC 1440×900, 모바일 390×844에서 가로 넘침이 없어야 한다. 실제 구현과 API 갱신은 위 구현 이슈에서 수행한다.

## 디자인 적용 (2026-10-13)

상품 정보·옵션 운영 패널의 제목 배경과 표의 셀 간격을 정리하고 관련 작업의 상단 경계선을 강조한다. 대시보드 전용 UI를 추출하지 않는다.

[공통 디자인 기준](../DESIGN.md)을 함께 따른다.
